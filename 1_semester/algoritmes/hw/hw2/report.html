T1. Implement and validate dual-pivot Quicksort

Algorithm Implementation & Strategy:

An in-place Dual-Pivot Quicksort (Yaroslavskiy-style partition) implemented in Rust without external sorting dependencies. For a given slice range $[0, n-1]$, the algorithm deterministically designates the first element as $p$ and the last element as $q$. If $p > q$, they are swapped immediately so that the precondition $p \le q$ strictly holds.

Partition Invariants:

During the partition loop, the active pointer $k$ traverses from $lt$ up to $gt$, maintaining the elements partitioned across four distinct regions:

$$\forall i \in [1, lt - 1]: arr[i] < p \quad \text{(Region 1: strictly smaller than left pivot)}$$ $$\forall i \in [lt, k - 1]: p \le arr[i] \le q \quad \text{(Region 2: between pivots)}$$ $$\forall i \in [k, gt]: \text{uninspected elements (Region under active scanning)}$$ $$\forall i \in [gt + 1, n - 2]: arr[i] > q \quad \text{(Region 3: strictly greater than right pivot)}$$

Upon loop termination ($k > gt$), the pivots are swapped into their final positions: $p$ is placed at $lt - 1$ (index $p_1$), and $q$ is placed at $gt + 1$ (index $p_2$).

Recursive Ranges & Duplicate Handling:

  • Left subarray: $[0, p_1 - 1]$ contains elements $< p$ → recursively sorted.
  • Right subarray: $[p_2 + 1, n - 1]$ contains elements $> q$ → recursively sorted.
  • Middle subarray: $[p_1 + 1, p_2 - 1]$ contains elements $x \in [p, q]$.
    • Case $p < q$: recursively sorted.
    • Case $p == q$: since $p \le x \le q$, every element in this region is guaranteed to be equal to $p$ (and $q$). Recursing on this range is skipped entirely. This eliminates $O(n^2)$ recursion degradation on duplicate-heavy and all-equal inputs.

The answers:

  • Partition Invariants: Pointer $k$ acts as the linear inspector, placing smaller values behind $lt$ (via left swap) and larger values behind $gt$ (via right swap). Uninspected elements shrink monotonically inside $[k, gt]$ until convergence.
  • Recursive Slicing: Subranges are safely split via split_at_mut to satisfy the Rust borrow checker without overlapping mutable references or unsafe pointer arithmetic. Pivots $p_1$ and $p_2$ are explicitly isolated from all sub-calls.
  • Termination on Duplicate/All-Equal Data: When $p == q$, all elements in the middle region are identical to the pivots. Bypassing the recursive call on the middle segment prevents infinite or quadratic recursion chains, guaranteeing termination on homogeneous datasets.
T2. How does random pivot selection help?

Pivot Ranks and Partition Balance:

Two uniformly chosen random points divide an interval into 3 equal sub-intervals on average. Their expected relative ranks are:

$$\mathbb{E}[\text{Rank}(P_1)] = \frac{1}{3}, \quad \mathbb{E}[\text{Rank}(P_2)] = \frac{2}{3}$$

This splits the array into three balanced segments ($\approx n/3$ elements each), guaranteeing an optimal expected recursion depth of $\approx \log_3(n) \approx 0.63 \log_2(n)$.

Why deterministic fails: on ordered inputs (Sorted, Reverse-Sorted), selecting $arr[0]$ and $arr[n-1]$ as pivots always picks the absolute minimum and maximum. The problem size shrinks by only 2 elements per step instead of dividing by 3, causing a catastrophic $\Theta(n^2)$ comparison blowup and linear recursion depth $\Theta(n)$.

Why randomisation helps: it decorrelates pivot quality from the initial array order. Regardless of input structure, random selection provides balanced subproblems on average. The theoretical worst case $O(n^2)$ still exists (if the RNG repeatedly draws extreme values), but its probability decays exponentially ($\approx 0$).

Resource Limit & Stack Overflow:

On Sorted and Reverse-Sorted arrays, deterministic recursion depth grows as $n / 2$. On Windows with a default 1 MB stack, this causes an unrecoverable STATUS_STACK_OVERFLOW at $n \ge 5\,000$. To safely handle this, an execution guard at depth ≥ 1200 was added, gracefully terminating and logging FAIL (Aborted).

T3. Lower-Bound Binary Search & Memory Hierarchy Scaling

Algorithm Implementation & Strategy:

We implemented an in-place lower-bound binary search in Rust. Unlike exact-match binary search (which halts immediately upon hitting the searched key), lower-bound isolates the first index whose value is greater than or equal to the queried key ($arr[k] \ge \text{searched}$). The slice is treated as a half-open interval $[left\_border, right\_border)$. If the pivot element is strictly smaller than the target, $left\_border$ advances to $k + 1$; otherwise, $right\_border$ collapses to $k$.

Instrumentation & Uniform Membership Queries:

The search was instrumented to return a tuple (usize, usize) representing (index, comparisons). To isolate pure algorithm execution from RNG overhead, 2 000 000 query keys were pre-generated prior to timing using rand::rngs::StdRng initialized with a fixed seed (2026) over the range $[0, 2 \times n_0]$.

Array Representation & Memory Footprint:

  • Data Structure: Contiguous buffer (Vec<u32>, inspected as &[u32]).
  • Numeric Type: 32-bit unsigned integer (u32).
  • Baseline Memory Consumed ($n_0$): $10\,000\,000 \times 4\text{ bytes} \approx 38.15\text{ MB}$.
  • Candidate Memory Consumed ($n$): $4\,410\,155 \times 4\text{ bytes} \approx 16.82\text{ MB}$.
  • Hardware L3 Cache Capacity: 12 MB.

Measurement Budget Allocation:

  • Baseline Run: Full 10.0 s run on $n_0 = 10\,000\,000$ (Run 1 of 3).
  • Pilot Measurements: 8 bisection steps of 0.5 s each = 4.0 s total (well within the 10.0 s pilot allowance).
  • Verification Run: Full 10.0 s run on the detected optimal candidate $n = 4\,410\,155$ (Run 2 of 3).
  • Total full runs used: 2 out of maximum 3 allowed.

  • Theoretical Prediction vs. Empirical Reality: Classical complexity $O(\log_2 n)$ posits that doubling throughput requires halving the comparison count: $\log_2(n) \approx \frac{1}{2}\log_2(10^7) \approx 11.66$, predicting $n \approx 3\,200$ (a reduction factor $>3\,000\times$).   • Memory Hierarchy & Effective 12 MB L3 Residency: The baseline array ($38.15\text{ MB}$) massively exceeds the 12 MB L3 cache, forcing almost every non-leaf lookup out into high-latency main memory (DRAM penalty $\approx 60\text{--}90\text{ ns}$). Reducing the dataset to $n = 4\,410\,155$ ($16.82\text{ MB}$) allows 12 MB of cache to cover $>71\%$ of the entire working set. Because the top 10+ levels of the binary search tree are hit repeatedly across all queries, they remain permanently hot in the cache hierarchy, while remaining accesses hit cache lines with vastly higher probability.
  • TLB Stress & Pipeline Stalls: The footprint reduction from $38.15\text{ MB}$ to $16.82\text{ MB}$ cuts 4 KB virtual memory page table coverage from $\sim 9\,766$ pages down to $\sim 4\,305$ pages. This substantially alleviates Translation Lookaside Buffer (TLB) thrashing. Execution latency is governed almost entirely by cache miss stalls and memory access penalties rather than raw ALU branch or comparison operations.
T4. Query Sequence Crossover: Linear Search vs. Sort-Once + Lower-Bound

Experimental Setup & Strategies:

For a fixed random array of $n = 100\,000$ distinct values (32-bit unsigned integers shifted into usize), we compared two query-resolution strategies across $q$ membership queries:

  • Strategy 1 (Linear Search): Queries are executed directly on the unsorted array sequentially. Terminating early when the element is matched, or scanning up to $n$ elements if absent.
  • Strategy 2 (Sort-Once + Binary Search): The array is sorted exactly once using the randomised Dual-Pivot Quicksort from T2, followed by lower-bound binary search from T3 for every incoming query. The one-time sorting cost (both comparisons and wall-clock execution time) is strictly incorporated into Strategy 2.

Queries were pre-generated with a 50/50 uniform distribution of present and absent elements. To evaluate reproducibility, the entire benchmark was evaluated across three distinct PRNG seeds (42, 2026, 777).

Theoretical vs. Empirical Crossover Models:

  • Naive Theoretical Model: Assuming $Cost_1 = q \cdot n$ and $Cost_2 = n \log_2(n) + q \log_2(n)$:
    $$q_{\text{naive}} = \frac{n \log_2(n)}{n - \log_2(n)} \approx \log_2(100\,000) \approx \mathbf{16.6\text{ queries}}$$
  • Empirical Comparison-Count Crossover ($q_{\text{comp}}$): Because linear search aborts upon finding an element (averaging $\sim 0.75n$ comparisons on mixed inputs) and Dual-Pivot Quicksort requires $\sim 1.9 n \ln(n) \approx 2.0 \times 10^6$ comparisons:
    $$q_{\text{comp}} = \left\lceil \frac{C_{\text{sort}}}{\bar{C}_{\text{linear}} - \bar{C}_{\text{bin}}} \right\rceil \approx \frac{2.0 \times 10^6}{75\,000 - 17} \approx \mathbf{28\text{ queries}}$$
  • Empirical Wall-Clock Timing Crossover ($q_{\text{time}}$): Determined by total elapsed real-world duration:
    $$q_{\text{time}} = \left\lceil \frac{T_{\text{sort}}}{\bar{T}_{\text{linear}} - \bar{T}_{\text{bin}}} \right\rceil \approx \mathbf{202 \text{ to } 276\text{ queries}}$$

The answers:

  • Theoretical vs. Empirical Comparison Crossover: The naive theoretical model predicts crossover at $q \approx 16.6$ queries. However, our measurements demonstrate that sorting becomes worthwhile by comparison count only around $q_{\text{comp}} \approx 28$ queries. This discrepancy occurs because Dual-Pivot Quicksort requires $\approx 1.9 n \ln(n)$ comparisons (rather than the ideal $n \log_2 n$), while early termination in linear search cuts the average per-query comparison cost down from $n$ to $\sim 0.74n$.
  • Comparison Crossover vs. Timing Crossover Disparity: While Strategy 2 wins on comparison count at $q \approx 28$, it does not break even in real execution time until $q_{\text{time}} \approx 202\text{--}276$ queries (nearly an order of magnitude later).
  • Hardware & Implementation Divergence:
    • Hardware Prefetching in Linear Search: Linear search walks contiguous memory sequentially. The CPU hardware prefetcher predicts streaming cache lines flawlessly, avoiding memory stalls ($\sim 0.4\text{ ns}$ per comparison).
    • Memory Moving & Swapping Overhead: Dual-Pivot Quicksort executes hundreds of thousands of write swaps alongside comparisons, incurring heavy pipeline branch penalties and cache writes.
    • Memory Latency in Binary Search: Each step in lower_bound incurs unpredictable branches and scattered cache accesses. Consequently, a single comparison in Quicksort and Binary Search costs significantly more processor cycles than a streaming comparison in linear scan.
