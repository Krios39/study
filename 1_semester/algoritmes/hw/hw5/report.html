Distinguishing words from prefixes: The word-ending bit acts as a boolean flag. A node like ab serves as a routing prefix for aba and abb, but it is also a valid dictionary word itself. Setting its word-ending bit to 1 explicitly tells the algorithm that a valid word terminates at this exact node.

2. LCP Rule and Full Node Count

Full node count (N): 192,242

Why the previous word is enough for the LCP count: Because the dictionary is strictly lexicographically (alphabetically) sorted, adjacent words are guaranteed to share the maximum possible common prefix. Any word appearing before the immediate previous word will share the exact same or a shorter common prefix. Thus, comparing only with the immediately preceding word is sufficient to find the exact point where a new branch must be created.

2. Performance Analysis

Compare hashes at the same load (Weak vs Affine):

At the same load (e.g., 50%), the weak hash requires thousands of probes (1996.94), while the affine hash takes only ~1.5 probes. This happens because the maximum possible hash value for a 6-letter word using the weak function is extremely small (e.g., "zzzzzz" = 6 * 26 = 156). Therefore, 100% of the inserted words initially hash to the tiny range of slots 0–156, causing massive primary clustering. The affine hash, however, distributes the words pseudorandomly across all 8192 slots.

Compare loads for the same hash (4096 vs 7373):

For the affine hash, increasing the load from 50% to 90% significantly increases the mean absent probes from 2.44 to 56.48. As the table fills up, EMPTY slots become rare. When a collision occurs, linear probing forces the algorithm to step through increasingly long sequences of occupied slots before finding an empty one.

3. Primary Clustering & Absent vs Present Costs

Long runs of occupied slots (Primary Clustering):

In linear probing, when collisions occur, elements are placed in the next adjacent available slot. This forms a contiguous block (a "run") of occupied slots. Any new element whose hash maps anywhere within this block must step through the entire block to find an empty slot, adding to the end of the block and making it even longer. This snowball effect destroys O(1) performance.

Why absent queries cost more than successful ones:

A successful search (present) stops as soon as it finds the target word. On average, this takes traversing about half the length of the cluster. An unsuccessful search (absent) cannot stop until it encounters an EMPTY slot. Therefore, it must traverse the entire length of the cluster, explaining why absent probes are roughly double the present probes at 50% load, and scale even worse at 90% load.

4. The Memory, Accuracy, and Speed Trade-off

Memory vs. Speed: A smaller counter is not necessarily faster. Exact counting uses 4 KB of memory and operates at extremely high throughput (~53 M events/s) because it only involves a simple CPU integer increment instruction (+= 1). The Morris counter saves 3 KB of memory (reducing the footprint by 4x), but its throughput collapses entirely to ~1.2 M events/s. This massive slowdown occurs because updating a single Morris state requires branching (if C[v] < 255), random number generation, and expensive floating-point exponentiation for every single event in the stream.

Accuracy (Unbiased vs Exact): The saturating byte gives 100% exact answers for rare items (frequencies ≤ 255) but completely flatlines for popular items, resulting in a horrific MARE of ~0.86. The Morris counter sacrifices exactness (it relies on probabilities and introduces variance), meaning it is almost never "exact" in a single run. However, because it is an unbiased estimator, it correctly approximates the overall magnitude of heavily frequent items up to millions, maintaining a vastly superior MARE of around ~0.17 compared to the naive saturating byte.

4. Analysis and Hash Choice

Choice of Custom Hash: I implemented the FNV-1a (Fowler–Noll–Vo) 64-bit hash function. It is a highly respected non-cryptographic hash widely used in standard libraries for its simplicity and excellent avalanche characteristics. It requires only an XOR operation and a multiplication by a prime number per byte of data, making it extremely lightweight to implement from scratch without external dependencies.

Was the "good" hash good in practice? Yes. In practice, the FNV-1a non-cryptographic hash provided a false positive rate almost identical to the cryptographic SHA-256 (0.00808 vs 0.00824) and perfectly matched the idealized theoretical prediction of ~0.82%. The outputs of FNV-1a were uniformly distributed enough that hash correlation did not noticeably degrade the Bloom filter's accuracy. Furthermore, despite Rust's highly optimized sha2 crate, the raw simplicity of FNV-1a allowed it to achieve a massive performance advantage (~273k lookups/sec vs ~19k lookups/sec), proving that a well-designed non-cryptographic hash is strictly superior for Bloom filters where cryptographic resistance to malicious inputs is not required.

3. Cryptographic Analysis

Does doubling iterations roughly double time?
Yes. The timing data confirms this linear relationship: 200,000 iterations (1.83s) takes roughly twice as long as 100,000 iterations (1.06s). PBKDF2 applies the internal HMAC function sequentially in a loop, meaning the time complexity is strictly O(N) based on the iteration count.

The Role of the Salt:
The salt guarantees that two users with the exact same password will have entirely different derived verifiers (keys). This strictly prevents the use of precomputed dictionary tables ("rainbow tables") and forces an attacker who steals the database to crack each individual user's password separately, rather than attacking the database globally.

The Role of Work per Guess (Iterations):
Iterations enforce "key stretching". By making a single password check artificially computationally expensive, we dictate the terms of engagement for an offline attacker. A legitimate user only logs in occasionally, so a 1-second delay is imperceptible. But to an attacker testing millions of guesses, a 1-second cost per guess is devastating.

Why fast hashing is unsuitable here:
Fast algorithms like the basic Salted SHA-256 execute in fractions of a microsecond (e.g., ~0.000004s). If we used them for passwords, an attacker with modern GPUs or ASICs could evaluate billions of password candidates per second, trivially brute-forcing most user passwords offline in minutes. Fast hashing is for quick structure lookups (like Bloom filters or Hash tables); password hashing must be slow to defend against offline computational attacks.

2. Why equal fingerprints do not prove equal boards?

A Zobrist fingerprint is generated by XORing random 64-bit integers. Because it maps the entire universe of possible board states into a fixed 64-bit space, it acts as a hash function. Equal fingerprints do not mathematically prove that two boards are identical due to the possibility of hash collisions.

Even though 64-bit integers offer an immense space (1.8 × 1019 values), there is still a non-zero mathematical probability that two entirely different subsets of random numbers could XOR to the exact same resulting 64-bit value. Therefore, a fingerprint match means the boards are probabilistically almost certainly the same, but it does not constitute a rigid cryptographic or mathematical proof.

2. Coverage Conditions & Trace

  • Fixed step k: Full coverage is guaranteed if gcd(k, m) = 1.
  • Triangular probing: Full coverage is guaranteed if m is a power of 2.
  • Square probing: Guarantees finding a slot only if m is prime and load is ≤ 50%.

Trace for first 9 probes of i*i mod 9:
i=0 → 0, 1 → 1, 2 → 4, 3 → 0 (Repeated), 4 → 7 (NEW), 5 → 7, 6 → 0, 7 → 4, 8 → 1.

Can a new slot appear after a repeated slot? Yes. At i=4, slot 7 appears for the first time, even though i=3 already repeated slot 0.

The Infinite Loop Problem: If a hash maps to a specific probe sequence, and every reachable slot in that sequence is full, an unbounded while(true) loop will cycle over those occupied slots forever — even if the rest of the table is empty. A probe limit prevents this infinite loop. Hitting the limit means the reachable slots are exhausted, not necessarily that the entire table is full.

Analysis

Does it reduce probes for both hashes and loads? For the "Good" (Affine) hash, triangular probing successfully reduces the mean lookup probes compared to linear probing, particularly at 90% load (Absent probes dropped significantly from 56.48 to 12.00). This happens because triangular probing breaks primary clustering — a major issue in linear probing where blocks of occupied slots merge together.

Does it fix a poor hash? No. While triangular probing mitigates the catastrophic 4000-7000 probes seen in linear probing, it still suffers heavily from secondary clustering. The "Weak" hash maps hundreds of different words to the exact same starting slot. Because triangular probing is strictly deterministic, all these words follow the exact same triangular path, colliding with each other sequentially (resulting in 100 to 242+ probes). Changing the probe strategy cannot rescue a fundamentally poor hash distribution.

Why full coverage doesn't guarantee a short search? Even though triangular probing with m=8192 guarantees visiting every single slot eventually, finding that empty slot may still require hundreds or thousands of hops if the hash creates a secondary cluster. Full coverage guarantees correctness (we will eventually find a spot without infinite looping), but speed still relies entirely on the initial uniform distribution of the hash function.
