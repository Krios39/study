5. What Neighbour Order Can and Cannot Change

What changes: neighbour order decides which unvisited vertex is explored next, so it changes the discovery order, the parent pointers and therefore the path that gets reconstructed. For DFS the effect is dramatic: in all three variants alphabetical DFS commits to one branch and reaches t after 5 or 6 edges. With reverse order it found a 2-edge path in variants 1 and 2, but a 4-edge path in variant 3. DFS gives no guarantee about path length, it returns whichever path its first deep dive hits. For BFS, order only changes the tie-breaking between paths of equal length (for example B-A-G vs B-C-G in variant 2, A-B-F vs A-E-F in variant 3).

What does not change: the shortest-path distance is a property of the graph itself (the minimum number of edges over all s-t paths), not of the algorithm that explores it. Reordering neighbours does not add or remove any edge, so the set of possible paths, and the minimum of their lengths, stays the same. That is why BFS, which explores layer by layer (all vertices at distance 1, then distance 2, ...), finds a 2-edge path in both orders in every variant.

4. The Shared-Pattern Idea

Comparing every pair of words would need about 4448² / 2 ≈ 9.9 million comparisons. The helper avoids that: it replaces each position of a word by * in turn, so sport produces 5 patterns *port, s*ort, sp*rt, spo*t, spor*, and puts the word into the bucket of each pattern. Two words share a bucket exactly when they agree everywhere except the starred position, that is, when they differ in exactly one letter. For example the bucket sp*rt holds sport, spirt and spurt, and all three are pairwise neighbours. So the edges are all pairs inside each bucket: the work is 5 · 4448 bucket insertions plus the (small) number of pairs inside buckets, instead of millions of comparisons. Two different words cannot share two buckets (that would mean they agree on all five positions), so no edge is produced twice.

7. Why BFS Finds a Fewest-Edge Ladder

        

            BFS processes words in the order they were discovered (FIFO queue), so it finishes all words at distance k before it discovers any word at distance k + 1.
            By induction, every word is discovered for the first time from a parent one layer closer to the start, so its parent chain has exactly as many edges as its distance.
            The first time the target is discovered, it is in the lowest layer that contains it, and the parent chain gives a ladder with the minimum number of changes.
            In the explorer above this is visible directly: spice first appears in layer 3, so no 1- or 2-step ladder exists.
        

        

            Note on depth: the BFS tree from sport over its whole component has depth 27 (from shore: 26).
            This is the eccentricity of the source within the component, not the component's diameter.

6. Discovered vs Settled

        

            Discovered means the vertex has received some finite tentative distance: the cost of the best path found so far, using only edges from vertices that are already settled.
            It is an upper bound, not the answer. Settled means the vertex was popped from the priority queue with the smallest tentative distance.
            At that moment its distance is final: every other route to it would have to leave the settled set through some vertex whose distance is already at least as large,
            and since all edge costs are positive, continuing from there can only add cost.
        

        

            Why a discovered vertex must still accept improvements: when C was discovered, only S was settled, so the only known route was the direct edge of cost 5.
            The cheaper route through A and B was simply not explored yet. If C refused the update, it would keep the wrong distance 5 and the wrong parent S,
            and every vertex reached through it (here T, 5 + 1 = 6 instead of 4) would inherit the error.
        

        

            Why stopping at discovery fails: discovery happens along the first edge that reaches a vertex, and the first edge is often an expensive one.
            Here T is discovered right away through S-T with cost 10, while the cheap chain still has three vertices waiting in the queue.
            Only when T is popped are all vertices with smaller distance already settled, so only then can no cheaper path appear.

4. Priority Queue: New Entries Instead of Changing Old Ones

        

            When Dijkstra finds a cheaper way to a vertex that is already waiting in the queue, the old entry is not modified. Rust's BinaryHeap (like Python's heapq)
            has no decrease-key operation: changing an entry would mean searching the heap's internal array (O(n)) and repairing the heap order by hand, which breaks its encapsulation and is easy to get wrong.
            Instead, after every strict improvement a fresh entry with the new distance is pushed, and the old one simply stays in the heap. When an entry is popped, it is skipped as outdated
            if the vertex is already settled or if its stored distance is larger than the current best dist[v]. A vertex can therefore appear in the heap several times, but it is settled only once,
            with its smallest distance, which comes out first. The heap may temporarily hold more entries than there are vertices (at most one per improvement, i.e. O(E)),
            so the running time is O(E log E) = O(E log V), the same order as with decrease-key.
        


        
5. Steps vs Cost

        

            BFS minimises the number of edges and is blind to the terrain, so on map A it runs straight through the slow patch: 79 steps but cost 136.
            Dijkstra minimises the sum of edge costs: it accepts 36 more steps (115) to go around the patch below, and every one of them costs 1, so the total drops to 115 (−15%).
            On map B the walls already force a long detour, and the remaining freedom is used differently: BFS goes up right after the first opening and follows row 13, which crosses the cost-4 patch
            between the walls and later the cost-2 patch (145 steps, cost 220). Dijkstra goes two rows higher (row 11), above the cost-4 patch, and passes the cost-2 patch on its left and lower side:
            only 4 steps more, but cost 149 instead of 220 (−32%). The fewest-step route and the cheapest route coincide only when the terrain is uniform; as soon as some cells are expensive,
            a few extra cheap steps can be much better than a short expensive shortcut.
        

    





    Task T5: When does a hint towards the target help?
    


        
1. The Heuristic

        

            A* orders the queue by f(v) = g(v) + h(v) with the Manhattan distance h(r, c) = |r − rt| + |c − ct|.
        

        
    
            
  • Lower bound (admissible): one move changes either the row or the column by exactly 1, so it changes the Manhattan distance to the target by at most 1.
                Any path from v to the target therefore has at least h(v) edges. Every edge costs max(value[u], value[v]) ≥ 1, so the path costs at least h(v).
                Walls only remove edges, which can only make the true cost larger.
    • 
            
  • Consistency: for an edge u–v, h(u) ≤ h(v) + 1 (the distance changes by exactly 1 per move) and 1 ≤ cost(u, v),
                so h(u) ≤ cost(u, v) + h(v). With a consistent heuristic f never decreases along a path, so a vertex is final when it is settled, exactly as in Dijkstra.
    • 
            
  • Is 2h admissible? No. Counterexample on map A: vertex (30, 83), target (30, 84). Both cells have value 1, the true remaining cost is 1,
                but 2h = 2 > 1. The overestimate is not just theoretical: running A* with 2h returned cost 136 instead of 115 on map A Q1 and 157 instead of 128 on map B Q3,
                i.e. a wrong (non-optimal) route.
    • 
        

        

            Expectation for walls: Manhattan distance ignores walls, so it should help least where the optimal route has to move away from the target to reach an opening.
            On map B this is Q1 (row 30 → down to the opening at rows 46–50 → up to rows 9–13) and Q2 (start at the top, forced down to the first opening, then back up to the second one).
            On map A without walls, the queries whose optimal cost equals the Manhattan distance should be almost free.

4. What the Heuristic Knows and Ignores

        

            Manhattan distance knows only where the target is: it assumes an empty map where every step costs 1. It ignores walls and expensive terrain.
            When the optimal route really is a monotone staircase of cost-1 cells (map A Q2 and Q3, optimal cost 128 = 49 + 79 = h(source)), the estimate is exact,
            every vertex on the route has the same f, and A* settles only 129 vertices instead of ~5340.
            On map A Q1 the straight line crosses the cost-4 patch; the optimum (115) is 36 more than h(source) = 79, and A* has to settle every cell with f below 115 — a band around the patch (27% of Dijkstra).
        

        

            Map B Q1 is the worst case. h(source) is 79, the true cost 149: the walls force the route 16 rows down to the first opening and then 35 rows up to the second.
            Everything west of the first wall looks "close" to the heuristic (small h, small g), so A* settles almost the whole western region before it accepts the detour,
            and then also the band between the walls. Q2 is similar (start at the top, forced down to rows 46–50 and back up to rows 9–13).
            Map B Q3 is easier: the route goes from the bottom left to the top right, and both openings (rows 46–50 near the start row 54, rows 9–13 near the target row 5) lie roughly on the way, so the detours are short.

4. Why Expensive Edges Make the Route Cheaper

        

            Each new edge is individually more expensive than a one-letter step (21 or 29 vs 13), but it replaces several steps: a 2-letter change costs 21 instead of 2 · 13 = 26,
            a 3-letter change 29 instead of 3 · 13 = 39 (and that is only when the intermediate words exist at all). The constant +5 is paid once per edge instead of once per letter,
            so bundling changes is cheaper, and adding edges can only add options, never remove the old paths.
        

        

            Giving cost 13 to all original edges alone cannot change which paths are cheapest: every path then costs exactly 13 × (number of edges),
            so comparing costs is the same as comparing edge counts, and the cheapest paths are exactly the fewest-edge paths that BFS already finds. Multiplying all weights by the same positive constant
            rescales every path cost equally and preserves their order; only new edges with a different cost per letter changed can create a different optimum.

1. Wall Choice

        

            From T5, the query with the largest A*/Dijkstra ratio on map B is Q1 (0.641). Its settled region is the whole area west of the wall at column 29
            plus the band between the walls: Manhattan points straight east along row 30, but the route must go down to the opening at rows 46–50 and then up to the opening at rows 9–13.
        

        

            Choice: keep the wall at column 59 (opening rows 9–13) for all queries. All three targets lie east of column 59, so every route must pass through that opening as its last obstacle,
            and the relaxed distance tells every cell west of it how far it really is from the gap. The opening at the top is also the detour Manhattan misses most for Q1 and Q2
            (both reach column 59 from below). For comparison, keeping column 29 instead gave 5912 online settled vertices in total (Q2 not improved at all) against 4108 for column 59.
        

        

            Relaxed map: copy of map B with the wall at column 29 removed, the wall at column 59 kept with its original opening, every traversable cell cost 1.
            For each target, BFS runs backwards from the target on this map; the distance table is the heuristic for A* on the original weighted map B.
        


        
2. Why It Is Admissible and Consistent

        
    
            
  • Admissible: every path on map B is also a path on the relaxed map (removing a wall only adds cells and edges, it never removes any), and on the relaxed map it costs
                1 per edge, which is ≤ its real cost (real edge costs are ≥ 1). So the relaxed shortest distance h(v) is ≤ the cost of the cheapest real path from v.
    • 
            
  • Consistent: BFS distances satisfy h(u) ≤ 1 + h(v) for every relaxed edge u–v. Every edge of map B is a relaxed edge, and its real cost is ≥ 1,
                so h(u) ≤ cost(u, v) + h(v). This inequality was also checked by the program on every edge of map B for all three tables.

5. When Does Preprocessing Pay Off?

        

            For a single query it does not: Q1 needs 5345 BFS visits plus 1637 settled vertices, more than plain Dijkstra (4677). The saving per query against Manhattan A* is
            2996 − 1637 = 1359 settled vertices for Q1 (Q2: 1359, Q3: only 212), so the table repays its 5345 visits only from about the 4th query to the same target (Q3: ~25 queries).
            The table depends only on the target, so repeated queries from different sources to one destination (e.g. many units walking to the same base) reuse it for free;
            a new target needs a new backward BFS and a new table. And not every query improves equally: for Q3 the gain is small, because Manhattan already handles its detour quite well.
