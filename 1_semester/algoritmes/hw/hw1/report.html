T1. Asymptotic winner versus practical winner
$$T_A(n) = 0.3 * n * log_2(n)\text{ milliseconds}$$ $$T_B(n) = 5 * n \text{ milliseconds}$$

Some calculations:

$$0.3 \cdot n \cdot \log_2(n) = 5 \cdot n$$ $$0.3 \cdot \log_2(n) = 5\text{ (divide both part for n)}$$ $$\log_2(n) = \frac{5}{0.3} = \frac{50}{3}\ = 16\frac{2}{3}\text{ (divide both part for 0.3)}$$ $$n = 2^{16\frac{2}{3}} = 2^{16} \cdot \sqrt[3]{2^2} = 65\,536 \cdot \sqrt[3]{4} \approx \mathbf{104\,031.92} \text{ (found Intersection point)}$$

T2. Empirical Validation and Operation Counting

Basic operations:

  • Linear scan: subtraction of neighboring items array[i+1] - array[i] (runs once per step).
  • Naive inversion counter: comparison array[i] > array[j] (runs every time in inner loop).
  • Library sort: comparison of elements a < b.

Operation counts and formulas:

$$C_{\text{scan}}(n) = n - 1\text{ (loop runs from 0 to n - 2)}$$ $$C_{\text{inv}}(n) = \sum_{i=0}^{n-1} (n - 1 - i) = \frac{n(n - 1)}{2} = \frac{n^2 - n}{2}\text{ (sum of arithmetic progression)}$$

For library sort we cannot write exact formula because Rust uses pdqsort. It is adaptive, so number of comparisons changes depending on how elements already ordered, chosen pivots and internal optimizations. We only know it is $\Theta(n \log n)$.

3. Held-Out Prediction for Naive Inversions ($n = 32\,000$)

Calibration constant $c$ using $n = 8\,000$ and $n = 16\,000$:

$$c = \frac{3.233 + 3.143}{2} \approx 3.188\text{ ns per pair}$$ $$T_{\text{predicted}}(32\,000) = c \cdot (32\,000)^2 = 3.188 \cdot 1\,024\,000\,000 \approx \mathbf{3\,264\,512\,000}\text{ ns } (\approx 3.26\text{ s})$$

Actual measured median: $\mathbf{3\,383\,013\,200}\text{ ns } (\approx 3.38\text{ s})$

$$\text{Error} = \frac{|3\,383\,013\,200 - 3\,264\,512\,000|}{3\,383\,013\,200} \cdot 100\% = \frac{118\,501\,200}{3\,383\,013\,200} \cdot 100\% \approx \mathbf{3.50\%}$$

Conclusions (Decision on Growth Claims):

All theoretical growth claims are supported by empirical data. For linear scan, ratio $T(10n)/T(n)$ stabilizes around 9.9–10.3 on larger inputs, and normalisation $T(n)/n$ becomes flat at $\approx 4.6$ ns, confirming $\Theta(n)$. At $n = 100$, higher $T(n)/n = 6.0$ is caused by fixed timer overhead and cold instructions. For library sort, normalisation $T(n)/(n \log_2 n)$ becomes most stable around $18.5 - 19.5$ ns, while $T(n)/n$ keeps growing, fully confirming $\Theta(n \log n)$. For naive inversions, doubling ratio stays between 3.8 and 4.5, and $T(n)/n^2$ stays stable around $2.8 - 3.2$ ns. Calibrated model predicted $n = 32\,000$ runtime with only 3.5% error, confirming $\Theta(n^2)$. None of the predictions are contradicted.

T4. Insertion Sort Operation Counting & Sensitivity

Basic operations counted:

  • Comparisons: condition array[j - 1] <= key evaluated inside the inner loop (plus boundary check).
  • Shifts: assignment array[j] = array[j - 1] moving elements to the right.

Predictions before test:

Experiment A (Ordering, baseline: Random):
  • for sorted it would be fewer, because it doesnt need to shift something, it would be just traversal of the array (O(n))

  • for sorted-block it would be similar (slightly fewer), because blocks are randomly ordered, but elements within each block are already sorted and introduce zero internal inversions

  • zipf would be fewer cause less unical items you have then less shifts you need

The answers:

  • Predictions vs Reality: all predictions were correct. Insertion sort depends directly on number of inversions and how far each element travels to the left.
  • Experiment A (Ordering):
    • Sorted: best case $O(n)$, exactly $9\,999$ comparisons and 0 shifts because loop breaks immediately on previous element.
    • Reverse: worst case $O(n^2)$, exact maximum $\frac{n(n-1)}{2} = 49\,995\,000$ operations. Every element moves to index 0.
    • 100 Blocks: requires less shifts than random ($22.02\text{M}$ vs $24.94\text{M}$) because elements inside each 100-item block are already sorted and have 0 internal inversions.
  • Experiment B (Frequency): Zipf has fewer shifts than uniform ($23.73\text{M}$ vs $24.99\text{M}$). Because we have only $1\,585$ unique values and lots of duplicates, inner loop stops earlier on array[j-1] <= key without shifting element too deep.
  • Difference between A and B: in A we keep exact same items and change only their order, while in B we keep same domain $[1, 10\,000]$ and change frequency of duplicates.
