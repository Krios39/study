Task T1: Three exact-search methods

Method

  • Naive: for every start position compare left to right until the first mismatch.
  • KMP: the failure table fail[i] is the length of the longest proper border of P[0..i]. The text is read once; after a mismatch the pattern state falls back to fail[k−1], after a full match to fail[m−1], so overlapping matches are found.
  • Boyer–Moore–Horspool (the chosen variant): the window is compared right to left. Whatever happens, the window moves by shift[c] where c is the text letter under the last pattern position; shift[c] = m−1−i for the last occurrence i < m−1 of c in the pattern, and m if c does not occur there. There is no good-suffix rule.
  • Counting: one generic function compares two letters and increments a counter; the timed runs use a no-op counter, so the same code is measured. Table lookups and index tests are not counted. Preprocessing comparisons (KMP failure table) are counted separately; Horspool's table needs none.
  • Timing: median of 7 runs, matches only counted. Preprocessing time is the median of 7 runs of 10,000 preparations divided by 10,000.

Conclusion

  • Naive and KMP make almost the same number of comparisons (about 1.04 per letter): with 26 equally likely letters the first comparison already fails 25 times out of 26, so KMP's fallback is rarely needed.
  • Horspool makes far fewer comparisons, about n/m: most windows end in a letter that is not near the end of the pattern, so it jumps almost m letters. The longer the pattern, the fewer comparisons.
  • Fewer comparisons does not mean proportionally less time. For m = 5 Horspool makes 4.6× fewer comparisons than naive but is only about 1.5× faster. Each Horspool step does more work (a right-to-left loop, a table lookup and a variable jump), while the naive loop is a tight, well-predicted scan. Comparisons count the abstract work; time also depends on memory access and branch prediction.
Task T2: Make the data change the result

Generators (text size 1,000,000, patterns of length 5, 10, 20)

All random texts use splitmix64. The main seed is 2026; every random family was also run with seeds 2027 and 2028. Patterns taken from the text start at position 500,000.

  • Small alphabet: uniform letters over {a, b}, and as an intermediate case over DNA {a, c, g, t}; patterns from the text.
  • Unequal frequencies: 26 letters; each position is e with probability 0.5, otherwise one of the other 25 letters uniformly; patterns from the text.
  • Periodic: text an, pattern am (no randomness; 1,000,000 − m + 1 overlapping matches).
  • Nearly periodic with long partial matches: each position is b with probability 0.01, otherwise a. Two patterns: am−1b and the mirror b am−1.

Predictions (written before the runs)

  • Small alphabet: naive about 2 comparisons per letter (the first letter matches half the time), KMP not worse than naive. Horspool loses its long shifts (both letters occur near the end of the pattern), so it should be close to the others in comparisons and probably slower in time. DNA in between.
  • Unequal frequencies: naive and KMP a little worse than uniform (about 1.3) when the pattern starts with e; Horspool still best but with shorter shifts when the window often ends in e. The first and last letters of the pattern decide.
  • Periodic: naive and Horspool compare all m letters at every position, about m·n; KMP exactly one comparison per letter. KMP wins by far.
  • Nearly periodic: for a…ab naive about m·n, KMP at most 2n, Horspool about n (it checks the last letter first). For b a…a the roles swap: naive about n, Horspool about m·n.

Where each method is most competitive

  • Horspool: alphabets of four or more letters and longer patterns, especially when the pattern ends in a rare letter (uniform 26 letters, DNA, skewed with a rare last letter, a…ab in comparisons). Weakest when the window usually ends in a letter that is also near the end of the pattern: b a…a gave 16.7 comparisons per letter, its worst case m·n.
  • KMP: periodic text and many overlaps (an: 1.00 against 20.0, 18× faster), and it was the fastest in time on both nearly periodic patterns, also where Horspool made fewer comparisons. It never exceeded 2 comparisons per letter in any run, and on binary text its cost was the same for every pattern and seed.
  • Naive: it never won a test outright. Its closest results come when the first letter of the pattern is rare: b a…a (1.17 comparisons per letter against KMP's 1.00, 0.74 ms against 0.57 ms) and skewed seed 2028, where the pattern starts with the rare a (1.03 against 1.02, 0.81 ms against 0.71 ms), a near tie with KMP. There it beats Horspool by far: the first comparison almost always fails, so its simple loop does about one comparison per letter.
  • Comparisons versus time: branch prediction matters. Naive on skewed text costs 3.9 ms at 1.75 comparisons per letter but 0.8 ms at 1.03: when the first comparison succeeds at random half the time, the processor mispredicts often. On a…ab Horspool makes the fewest comparisons (1.00) but KMP (1.83) is twice as fast, because Horspool always shifts by 1 and pays the table lookup at every position.
  • Observed versus guaranteed: these inputs show typical behaviour for the chosen generators. The only general worst-case guarantee among the three is KMP's: at most 2n comparisons in the search (plus at most 2m for the failure table). Naive and Horspool are O(n·m) in the worst case, and the periodic and nearly periodic families reach that bound. Horspool's good average needs a large alphabet and is not a guarantee.

Interval search

  • Constructor (own): prefix doubling in the style of Manber and Myers. Suffixes are sorted by the pair (rank of the first k letters, rank of the next k letters), k = 1, 2, 4, …, until all ranks differ; each round is a sort, so O(n log² n). Suffixes are never copied; only rank arrays are kept. It is checked against sorting suffix slices on 2,000 random texts and on a5000.
  • Lower bound: the first rank whose suffix is not smaller than the pattern. Upper bound: the first rank whose first m letters are greater than the pattern. Both are binary searches over ranks; one comparison step compares the pattern with the start of a suffix letter by letter until the first difference, and every letter pair is counted. The answer is the rank interval [lo, hi); the count is hi − lo, the positions are SA[lo..hi).

Encoder and decoder

encode(text):                           // text ends with the unique, smallest marker $
    SA = suffix_array(text)
    return [ text[(SA[i] - 1) mod n] for i in 0..n ]

decode(L):
    copy[i]  = number of earlier positions j < i with L[j] = L[i]
    C[c]     = number of letters in L smaller than c      // first row of c in F
    row = 0                                             // row 0 starts with $
    out = "$"
    repeat n - 1 times:
        c   = L[row]                                    // the letter before the current one
        out = c + out
        row = C[c] + copy[row]                          // LF mapping: same copy of c in F
    return out

Interactive: rotation matrix, decoding links and backward search

Rows are all rotations of the text, sorted. F is the first column, L the last; L is the BWT. The lines link the k-th copy of a letter in L to the k-th copy in F: it is the same letter of the text. Green rows start with the pattern.
  • Repeated letters: the rows that start with a letter c are sorted by what follows c. The rows that end with c are sorted by the same continuation (it is at the front of those rows). So the k-th a in L is the k-th a in F; the copy number tells the copies apart. For example, step 2 reads the copy #8 of a in row 20 and jumps to C[a] + 8 = 1 + 8 = 9.
  • The end marker: it is unique and smallest, so the decoder knows the start row (row 0, the rotation beginning with $) without storing the index of the original row, and it ensures that all rotations are different, which is what links the BWT to the suffix array. Without it the transform is not reversible: BWT(banana) = BWT(ananab) = nnbaaa, so rotations of the same text cannot be told apart.

The BWT is only a permutation of the letters: it has exactly the same length and letter counts, so by itself it saves nothing. It helps compression because the grouped letters can then be coded cheaply by run-length or move-to-front coding followed by an entropy coder.

Bonus B1: BWT as a search index
  • Data: L = BWT = snnnnbbdbn$aanaaaaaaa. C[c] = number of letters smaller than c: $:0 a:1 b:10 d:13 n:14 s:20. occ(c, i) = copies of c in L[0..i) (counted directly; for a small example no sampled rank table is needed).
  • Backward search: read the pattern from right to left, starting with all rows [0, 21). With letter c: lo = C[c] + occ(c, lo), hi = C[c] + occ(c, hi). This is the LF mapping from T5 applied to a whole block of rows: the rows whose suffix starts with the current string and whose previous letter is c become the rows that start with c + string.

Loci of the final FM intervals in the suffix tree (diamonds) and their descendant leaves (framed).

  • Connection: a suffix-array interval is a set of consecutive ranks; in the suffix tree the same suffixes are exactly the leaves below one locus, because the leaves of any subtree are consecutive in lexicographic order. The interval for ana is the 5 leaves below node v4; for band it is the single leaf 12 below the point one letter into the edge danas$.
  • Backward search does not walk this path. It visits the loci of a, na, ana (v1, v10, v4), which lie in different parts of the tree, because it prepends letters. Only the final result, the set of suffixes starting with the pattern, is the same. The FM index here only answers counting and locating, not the other suffix-tree operations.
