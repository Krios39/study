# План замеров: overhead механизмов доверия в X-Road

Семинар: *Measuring the Overhead of Trust Mechanisms in the X-Road Data Exchange Layer*
Черновик от 17.09.2026. Источники и цифры — в `sources/literature_summary.md` и `sources/numbers.md`.

---

## 1. Зачем

В литературе нет ни одного замера, который раскладывает задержку X-Road по механизмам доверия. Есть сквозной RTT на одном ноутбуке (IJIS 2026, ≈32 ms с программным токеном), есть грубое сравнение «через Security Server против напрямую» на прикладном сервисе (Taklai 2020, шум больше эффекта) и есть предсказания роста накладных расходов при переходе на PQC и DPKI без базовой линии. Базовую линию и делаем.

**Вопросы:**

- RQ1. Сколько каждый механизм доверия добавляет к задержке и к размеру сообщения: TLS между Security Server, подпись, проверка подписи, проверка статуса сертификата, метка времени, запись в message log.
- RQ2. Как эти доли меняются при росте размера сообщения и параллельной нагрузки.
- RQ3. Насколько выводы зависят от среды: всё на одном хосте, всё на одном сервере, или реальная сеть между узлами.

RQ3 — то, из-за чего делаем несколько прогонов. Все опубликованные замеры сделаны на одной машине, и это их главное ограничение.

## 2. Что считаем механизмом доверия

По инвентаризации X-Road 7.6.2 (отчёт NIIS) в пути запроса стоят:

| Механизм | Где | В синхронном пути |
|---|---|---|
| TLS между Security Server (auth key, RSA-2048 или secp256r1) | SS ↔ SS | да |
| Подпись сообщения (sign key) | SS отправителя | да |
| Проверка подписи | SS получателя | да |
| Проверка статуса сертификата (OCSP, кеш) | SS, порт 5577 | нет, пока кеш свеж |
| Метка времени (TSA) | SS, пакетно раз в минуту | нет, если batch |
| Запись в message log + hash chain | SS обеих сторон | да (запись), архивация нет |
| Глобальная конфигурация | CS → SS | нет, фоновое обновление |

Отсюда две группы: то, что платится на каждом сообщении, и то, что вынесено в фон. Гипотеза: доминируют подпись, проверка и логирование, а OCSP и timestamping почти не видны, пока не сломать их конфигурацию. Это и надо показать числами.

## 3. Стенд

Топология: **1 Central Server + testca (CA, OCSP, TSA) + 4 Security Server + 2 информационные системы**.

- `cs` — Central Server, раздаёт глобальную конфигурацию.
- `ca` — тестовый CA с OCSP-респондером и TSA.
- `ss0` — management Security Server (регистрация членов).
- `ss1` — consumer.
- `ss2`, `ss3` — два provider, чтобы нагрузка шла к разным узлам и появился хоть какой-то параллелизм в сети.
- `is-provider` — эхо-сервис, отдаёт ответ заданного размера с околонулевым временем обработки. Это принципиально: у Taklai всё съела база, и эффект утонул.
- `is-baseline` — тот же эхо-сервис, доступный напрямую, без X-Road.

Версия X-Road — 7.7.x, образы с фиксацией по digest. Ориентир по компонентам: `niis/xroad-central-server`, `niis/xroad-security-server-sidecar`, `ghcr.io/nordic-institute/xrddev-testca`. Порты: админка 4000, SS ↔ SS обмен 5500, OCSP 5577, IS-интерфейсы 8080/8443. Точные теги и порты сверить перед сборкой.

Compose-файл пишем отдельно, после согласования плана.

## 4. Четыре варианта среды

Изначально план был простой: собирать и отлаживать стенд на ноутбуке, а данные снимать с сервера. При проработке выяснилось, что выбор среды — это не деталь исполнения, а часть RQ3, и что осмысленных вариантов четыре. Они дополняют друг друга, а не заменяют; если объём окажется велик, режем с конца списка.

Две оси, по которым они различаются: где стоят компоненты и какая сеть между Security Server.

| | **A. Ноут** | **B. Локалка** | **C. Облако UT HPC** | **D. Гибрид** |
|---|---|---|---|---|
| Где что | всё на одной машине | consumer и provider на разных ноутах | C1: 2–3 VM; C2: одна VM | consumer на ноуте, остальное в облаке |
| Сеть между SS | нет, петля в хосте | настоящая, ~0.3 мс | настоящая, ~0.2–0.5 мс (C1); нет (C2) | настоящий WAN, десятки мс |
| Железо | одно, твоё | разное у машин | одинаковое, описанное | смешанное |
| Воспроизводимость | средняя | низкая | высокая | низкая |
| Готовность | сразу | как появится вторая машина | после выдачи VM | после открытия портов |

### A. Ноутбук, всё локально

Windows + Docker Desktop (WSL2), 64 ГБ RAM. Все 8 контейнеров на одном хосте, сети между узлами фактически нет. Это воспроизведение условий IJIS 2026, то есть точка, с которой наши числа сравнимы с опубликованными.

Задача: разложение задержки по механизмам в чистом виде, без сетевого шума.

Подводные: WSL2 по умолчанию забирает до половины RAM хоста и меняет это на ходу — зафиксировать в `.wslconfig`; контейнерам выставить те же лимиты, что на VM (2 ядра, 4 ГБ на Security Server), иначе среды несравнимы; генератор нагрузки на 16–32 клиентах начнёт конкурировать за ядра — ограничить и проверить контрольным прогоном, что упирается не он.

### B. Два-три ноутбука в локальной сети

Consumer и provider Security Server на физически разных машинах, вспомогательные компоненты на третьей или рядом с consumer. Требования: машины сопоставимого класса, проводной коммутатор, а не Wi-Fi, Docker на каждой, около 50 ГБ свободного диска там, где стоит Security Server.

Задача: проверить, что выводы из A не следствие петли внутри хоста. Плюс отладка всего стенда, пока идёт согласование с облаком.

Подводные: железо разное, поэтому часть асимметрии между узлами объясняется машинами, а не сетью; чужими руками такой прогон не повторить; задержка здесь того же порядка, что внутри дата-центра, то есть настоящая сеть появляется, а другой класс задержки — нет. Если машины сильно различаются, слабую отдаём под management Security Server и Central Server — они в измеряемом пути не участвуют.

### C. Облако UT HPC

Основная среда для публикуемых чисел: железо одинаковое, описанное, без фоновой активности, прогон воспроизводим чужими руками. Доступ — письмом в support@hpc.ut.ee. Docker разрешён, но дефолтную сеть `docker0` надо увести с 172.17.0.0/16; снаружи по умолчанию открыты только 22, 80, 443 и ICMP, остальное по запросу.

**C1, 2–3 VM (предпочтительно).** Consumer и provider на разных машинах, измеряемый участок существует. Раскладка и требования — в разделе 8.3.

**C2, одна VM (fallback).** Всё на одном инстансе, портов наружу не нужно. Сети между Security Server нет, поэтому RQ3 закрывается только эмуляцией `tc netem` (1, 5, 20, 50 мс, потери 0 и 0.1%) — это более слабый ответ, и подаётся он именно так.

Подводные: сроки выдачи VM и открытия портов вне нашего контроля. Поэтому запрос уходит в первый день, а среда B существует как страховка.

### D. Гибрид: consumer на ноутбуке, остальное в облаке

> Статус: обсуждается с Артёмом, опционально. На сроки и на остальной план не влияет.

Единственный вариант с настоящим WAN, то есть с RTT на порядок выше остальных.

- В облаке: `cs`, `ca`, `ss0`, `ss2`, `ss3`, `is-provider`.
- На ноутбуке: `ss1` (consumer) и генератор нагрузки.

VPN не нужен: инициатор соединения всегда consumer. Его Security Server сам ходит на Central Server за конфигурацией, на CA за OCSP и меткой времени и на Security Server провайдера по 5500. Входящие соединения к ноутбуку не требуются, NAT не мешает. Обратный вариант (провайдер на ноутбуке) требует проброса портов, его не делаем.

Что нужно: открыть на облачной стороне 80, 5500, 5577 и порты тестового CA и TSA.

**План Б, если наружу не откроют: WireGuard** между ноутбуком и VM. Согласовать проще (наружу торчит только UDP-порт туннеля), NAT снимается совсем. Минус: туннель добавляет свою задержку и своё шифрование поверх TLS X-Road, попадая прямо в измеряемую величину. Тогда обязателен контрольный прогон «через туннель против напрямую» на одной паре облачных узлов: разность даёт цену туннеля.

Подводные: домашний канал нестабилен, разброс может оказаться сопоставим с эффектом — ровно то, что случилось у Taklai. Поэтому D идёт последним и подаётся как проверка внешней валидности, а не как основной результат. Отдельный смысл сценария: сравнить настоящий WAN с эмуляцией `netem` из C. Если совпадает, значит для таких замеров достаточно эмуляции, и это само по себе полезный вывод.

### Порядок сокращения

Если объём великоват, первым выбывает D, вторым B. Минимальный осмысленный набор — A плюс C.

## 5. Что варьируем

| Фактор | Значения |
|---|---|
| Размер полезной нагрузки | 1 KB, 10 KB, 100 KB, 1 MB |
| Параллельные клиенты | 1, 2, 4, 8, 16, 32 |
| Конфигурация доверия | см. раздел 6 |
| Ключи | RSA-2048 (дефолт) и secp256r1 |
| Протокол | REST; SOAP — если останется время |
| Среда | A, B, C |

Полный перебор не нужен. Основная сетка: размер × конфигурация доверия при 1 клиенте (чистая задержка), затем конкурентность × конфигурация при 10 KB (поведение под нагрузкой).

## 6. Как разделить вклад механизмов

Выключить подпись в X-Road нельзя, поэтому работаем разностями между конфигурациями:

1. **Baseline-0**: прямой HTTP от клиента к `is-baseline`, без X-Road. Нижняя граница.
2. **Baseline-1**: HTTPS с mTLS между двумя простыми прокси (nginx с теми же сертификатами). Отделяет цену TLS от цены X-Road.
3. **X-Road полный**: всё включено, значения по умолчанию.
4. **X-Road без TSA**: `acceptable-timestamp-failure-period` = 0 при выключенной службе меток. По результатам Mironova 2017 Security Server в такой конфигурации продолжает обрабатывать запросы, не завися от TSA. Разность с (3) даёт цену timestamping.
5. **X-Road с синхронным timestamping**: `timeStampingIntervalSeconds` в минимум. По блогу NIIS синхронный режим добавляет четыре операции timestamping к сквозной обработке — проверяем, сколько это на самом деле.
6. **X-Road с истёкшим OCSP-кешем**: `ocspFreshnessSeconds` в минимум, чтобы каждый запрос упирался в обращение к респондеру. Разность с (3) даёт цену OCSP в худшем случае.
7. **X-Road с ключами secp256r1** вместо RSA-2048.

Разности (3)−(2) и (2)−(1) дают цену X-Road поверх mTLS и цену самого mTLS. Разности (5)−(3), (6)−(3), (3)−(4) дают цены timestamping и OCSP в явном виде.

Дополнительно к разностям — прямое разложение изнутри: включить operational monitoring на Security Server и снимать по-запросные записи (таймстемпы прохождения запроса и размеры сообщений). Точные имена полей и сервис запроса данных надо сверить по документации X-Road перед началом: это даст разбиение без арифметики между прогонами.

## 7. Метрики и инструменты

- Задержка: p50, p90, p99, максимум. Среднее приводим только ради сравнимости с IJIS и Taklai.
- Пропускная способность: запросов в секунду при насыщении.
- Размер на проводе: сравнение размера запроса клиента и того, что реально уходит между Security Server (tcpdump или счётчики интерфейса). Отдельно — прирост от подписи и hash chain.
- Ресурсы: CPU и память контейнеров (`docker stats` или cAdvisor + Prometheus).
- Побочные запросы: сколько обращений к OCSP и TSA пришлось на N сообщений.
- Рост message log: байты на сообщение.

Нагрузка — k6 или JMeter. У k6 из коробки перцентили и сценарии по числу виртуальных пользователей; JMeter удобнее, если понадобится SOAP. Выбрать один и не менять между сценариями.

**Дисциплина измерений**, чтобы не повторить ошибку Taklai:

- 50 запросов прогрева, 1000 измеряемых на конфигурацию (как в IJIS), 3 независимых повтора в разное время;
- порядок конфигураций рандомизировать, а не гнать блоками;
- сначала контрольный прогон: два раза подряд одна и та же конфигурация. Если разница между повторами сопоставима с ожидаемым эффектом, стенд не готов, нагрузку и число контейнеров надо снижать;
- образы фиксировать по sha256, версии записывать в результаты;
- сырые данные (по-запросные, а не агрегаты) сохранять в CSV и коммитить.

## 8. Требования к ресурсам

### 8.1 Официальный минимум на компонент

Из руководств по установке X-Road (IG-SS, IG-CS):

| Компонент | CPU | RAM | Диск |
|---|---|---|---|
| Security Server | 2 ядра x86-64, желательно с AES-NI | 4 ГБ (с add-on'ами мониторинга — тоже 4 ГБ, но это уже впритык) | 3 ГБ |
| Central Server | 2 ядра | 2 ГБ | 3 ГБ |

Это минимум для работы, а не для нагрузочного теста. Для замеров берём с запасом: 2 vCPU и 4 ГБ на Security Server, и отдельно считаем диск под message log (раздел 8.4).

ОС по документации — Ubuntu Server 22.04 или 24.04 LTS. В облаке UT HPC есть образ `ubuntu24.04`, он и подходит.

### 8.2 Ноутбук (64 ГБ)

Памяти хватает с запасом: вся топология (4 SS + CS + CA + 2 IS + генератор) укладывается примерно в 24–28 ГБ. Важнее другое:

- **Выставить каждому контейнеру одинаковые лимиты** (`cpus`, `mem_limit`: 2 ядра и 4 ГБ на Security Server). Без этого сравнение ноутбука и сервера бессмысленно: на ноутбуке контейнеры разъедятся по свободной памяти, на VM — нет.
- **Зафиксировать WSL2**: по умолчанию он забирает до половины RAM хоста и подстраивается на ходу. В `.wslconfig` задать фиксированные значения (например 32 ГБ и 8 CPU), чтобы прогоны были воспроизводимы.
- Генератор нагрузки на том же хосте при 16–32 клиентах начнёт конкурировать за ядра. Ограничить его отдельно и в контрольном прогоне убедиться, что упирается не он.

Диск: с чисткой между прогонами (раздел 8.4) достаточно держать свободными около 50 ГБ.

### 8.3 Вариант с несколькими VM в облаке UT HPC

Смысл: сеть настоящая, но стабильная — в отличие от домашнего канала в гибриде. Раскладка на три VM (предпочтительно):

| VM | Что размещаем | vCPU | RAM | Диск |
|---|---|---|---|---|
| **vm-core** | Central Server, testca (CA + OCSP + TSA), management SS (`ss0`) | 4 | 8 ГБ | 40 ГБ |
| **vm-consumer** | `ss1` (consumer) + генератор нагрузки | 4 | 8 ГБ | 60 ГБ |
| **vm-provider** | `ss2`, `ss3` (providers) + эхо-сервис | 6 | 12 ГБ | 60 ГБ |

Если дадут только две VM: `vm-core` объединяем с `vm-consumer` (6 vCPU, 12 ГБ, 80 ГБ), провайдеры остаются отдельно. Если совсем одну — это вариант C2: 8 vCPU, 32 ГБ, 60 ГБ, портов наружу не нужно. Главное требование к любой раскладке — **consumer и provider Security Server на разных машинах**, иначе измеряемого сетевого участка просто нет.

Что запрашивать у support@hpc.ut.ee:

- 2–3 инстанса на образе `ubuntu24.04`, флейворы поколения g4 или g5;
- диски как в таблице (на провайдере больше всего — там растёт message log);
- сетевая связность между инстансами внутри проекта без ограничений по портам;
- снаружи открыть на vm-core и vm-provider: **TCP 5500** (обмен между Security Server), **TCP 5577** (OCSP), **TCP 80 и 443** (раздача глобальной конфигурации, OCSP, timestamping), **TCP 4001** (регистрация сертификатов на Central Server), порт тестового TSA. По умолчанию открыты только 22, 80, 443 и ICMP, остальное — по запросу, поэтому порты лучше перечислить сразу все;
- предупредить, что будет Docker, и не использовать дефолтную сеть `docker0` на 172.17.0.0/16 (об этом прямо сказано в их документации).

Админку Security Server (4000) и интерфейсы IS (8080/8443) наружу не открываем — ходим через SSH-туннель.

### 8.4 Диск: сколько съест message log

Это главный неочевидный расход. По умолчанию `message-body-logging = true`, то есть **тела запроса и ответа целиком пишутся в базу message log на обоих Security Server**, а раз в 6 часов уезжают в архивные ASiC-контейнеры (`archive-interval` = каждые 6 часов, `archive-max-filesize` = 32 МиБ, `archive-path` = `/var/lib/xroad`, `keep-records-for` = 30 дней).

Грубая оценка на один обмен и один Security Server: 2 × размер полезной нагрузки (запрос + ответ) плюс примерно 4 КБ на подпись, hash chain и метаданные. Умножаем на два, потому что логируют обе стороны, и ещё примерно на 1.3 за индексы и WAL PostgreSQL.

| Размер полезной нагрузки | 1000 запросов, обе стороны |
|---|---|
| 1 КБ | ≈ 16 МБ |
| 10 КБ | ≈ 62 МБ |
| 100 КБ | ≈ 0.5 ГБ |
| 1 МБ | ≈ 5.3 ГБ |

Без чистки вся кампания (5 конфигураций × 3 повтора × 4 размера, плюс прогоны на конкурентность) набирает десятки гигабайт, причём почти всё — за счёт мегабайтных сообщений. Поэтому два решения, оба обязательны:

1. **Чистка между конфигурациями**: останавливать стенд, чистить таблицы message log и архивы, поднимать заново. Тогда пик диска определяется самым тяжёлым прогоном, а не суммой.
2. **На 1 МБ делать 200 запросов вместо 1000**: на таком размере разброс меньше, тысяча повторов не нужна. Прогон весит около 1 ГБ.
3. Дополнительно поставить `keep-records-for` в сутки, чтобы ничего не копилось само.

С этим пик под данные — единицы гигабайт, и 60 ГБ на машину хватает с запасом (из них 15–20 уходит на ОС и образы). Скрипт очистки — часть шага 3, а не «потом».

Отдельно: образы. Ориентир 1.5–2 ГБ на образ Security Server и Central Server, плюс слои — 10–15 ГБ на машину, где они тянутся. Проверить `docker images` после первой сборки.

### 8.5 Сроки доступа

## 9. Угрозы валидности

- Всё в Docker на одном хосте — сети нет, доля криптографии завышена. Отсюда среды B и C1 с настоящей сетью и `netem` в C.
- Тестовый CA и TSA стоят рядом, а в проде это внешние службы с собственной задержкой. Значит, наши числа по OCSP и timestamping — оптимистичные, это надо писать прямо.
- Конфигурации 4–6 из раздела 6 намеренно отведены от дефолтов, чтобы сделать механизм наблюдаемым; их числа — верхняя граница стоимости механизма, а нормальный режим — это конфигурация 3. Отдельный вопрос к Артёму: ссылаться ли только на задокументированные дефолты или упоминать и продовые значения эстонской инсталляции 2017 года (6 и 8 часов против 10 и 20 минут), которые известны из одной магистерской работы.
- Эхо-сервис вместо реального сервиса завышает относительную долю механизмов доверия. Это осознанный выбор: нас интересует именно она, но в тексте нужна оговорка и, для калибровки, один прогон с искусственной задержкой сервиса в 50 ms.
- Windows + WSL2 добавляет свой оверхед на файловую систему и сеть, и это ещё одна причина иметь среды B и C.

## 12. Открытые вопросы

1. Точные имена полей operational monitoring и способ их выгрузки — проверить по документации до шага 3.
2. Объём по подписям: оставляем оба слоя (RSA и ECDSA в системе плюс примитивы ML-DSA и Falcon для прогноза) или режем прогнозную часть.
3. REST плюс одна контрольная точка на SOAP при 10 КБ — или только REST.
4. Есть ли у Артёма одна-две машины в локальной сети для среды B.
5. Как быстро UT HPC обычно выдаёт VM и открывает нестандартные порты. План считает это самым долгим пунктом; если это быстро, среда B становится необязательной.
6. Дефолтные интервалы или ещё и продовые значения 2017 года (раздел 9).
7. Показывать ли результаты кому-то в NIIS или RIA и есть ли контакты — с локальным тестовым CA наши числа заведомо оптимистичны.
8. Делаем ли гибрид D. Если да, основной путь — открытые 5500/5577, запасной — WireGuard с контрольным прогоном на цену туннеля (раздел 4D).
