# Сертификаты в X-Road — с нуля

## 1. Ключ и подпись

Пара ключей — два числа, связанных математикой:

```
   приватный ключ  ──► ставит подпись под данными        (хранится в секрете)
   публичный ключ  ──► проверяет, что подпись поставлена
                       именно парным приватным            (раздаётся всем)
```

Подпись — это не «зашифровать». Данные остаются открытыми, к ним прикладывается короткий блок, который сходится только с этим публичным ключом и только для этих данных. Изменил байт — подпись не сходится.

Проблема: публичный ключ — просто число. Получив число, ты не знаешь, чьё оно.

## 2. Сертификат = публичный ключ + имя + печать того, кому верят

```
 ┌────────────────────────────────────────┐
 │ СЕРТИФИКАТ                             │
 │  subject:  CN=ss1, serialNumber=DEV/SS1/MEMBER │  ← чьё
 │  publicKey: 30 82 01 0a …              │  ← сам ключ
 │  keyUsage: TLS  /  подпись             │  ← для чего разрешён
 │  notAfter: 2046-…                      │  ← до какого срока
 │  issuer:   Test CA                     │  ← кто выдал
 │  подпись Test CA ═══════════════════   │  ← печать выдавшего
 └────────────────────────────────────────┘
```

Аналогия — паспорт: фото (публичный ключ), ФИО (subject), печать государства (подпись CA). Ты не веришь человеку «на слово», ты веришь паспорту, потому что веришь тому, кто его выдал. Государство здесь — **CA** (certification authority). В Эстонии для X-Road это SK ID Solutions; на стенде — контейнер `ca`, который ставит печать всем подряд.

Значит, чтобы проверить чужую подпись, надо: взять серт → убедиться, что печать на нём от CA, которому ты доверяешь → взять из серта публичный ключ → проверить подпись.

## 3. Как получить сертификат: CSR

Ключи ты делаешь **сам, у себя**. Приватный никому не показываешь — ни CA, ни CS. Наружу отправляешь анкету:

```
   у тебя (SS)                                   CA
   ────────────                                  ──
   1. сгенерить пару ключей
      (приватный остаётся в SS)
   2. CSR = { публичный ключ, «я ss1»,
              подписано приватным }  ──────────►  3. проверить анкету
                                                     (тестовый CA ничего не проверяет,
                                                      настоящий — проверяет документы)
                                                  4. серт = анкета + печать CA
   5. import cert            ◄───────────────────────
```

CSR (certificate signing request) — «вот мой публичный ключ, вот кто я, поставьте печать». Подпись под CSR своим же приватным доказывает, что ключ действительно твой.

Поэтому три шага в UI: **Add key** (шаг 1–2, скачивается CSR) → отдать в testca (3–4) → **Import cert** (5). SS сопоставит серт с ключом по публичной части и положит рядом.

## 4. Почему X-Road хочет два сертификата на сервер

Два разных вопроса, на которые серт отвечает:

| Вопрос | Кто отвечает | Серт |
|---|---|---|
| «С кем я сейчас говорю по сети?» | **сервер** (машина, ss1) | **auth** |
| «Кто отвечает за содержимое этого сообщения?» | **организация** (член SS1-CODE) | **sign** |

Аналогия: **auth** — пропуск курьера, по нему охрана впускает в здание. **sign** — подпись директора на документе, который курьер принёс. Курьер завтра может быть другой, здание — другое, а подпись под документом должна оставаться подписью организации, и её должно быть можно проверить через пять лет, когда документ достанут из архива.

Отсюда всё остальное:

- auth привязан к серверу → CN = имя хоста, и CS должен знать «сервер SS1 живёт по адресу ss1 с вот таким сертом» → **регистрация на CS**.
- sign привязан к члену → CN = код члена. Если на одном SS живут подсистемы трёх разных организаций — три sign-ключа. CS этот серт не регистрирует: он проверяется получателем по цепочке до CA, как любая подпись.
- Сообщение с подписью кладётся в **message log** обеих сторон. Это юридическое доказательство «организация SS1-CODE запросила X у организации SS2-CODE». Именно поэтому подпись — организации, а не машины.

## 5. Что происходит, когда ss1 шлёт запрос ss2

```
 ss1 (consumer)                                        ss2 (provider)
 ──────────────                                        ──────────────
 a. собрать сообщение
 b. подписать sign-ключом члена SS1-CODE,
    приложить sign-серт члена SS1-CODE
 c. открыть TLS к ss2:5500
    ── предъявить auth-серт ss1 ─────────────────────► d. это серт сервера SS1?
    ◄── получить auth-серт ss2 ─────────────────────      (сверить с тем, что в gconf)
 e. это серт сервера SS2? (gconf)                        печать CA на нём? не отозван (OCSP)?
 f. отправить сообщение ─────────────────────────────► g. печать CA на sign-серте?
                                                          не отозван (OCSP)?
                                                          серт принадлежит члену SS1-CODE? (gconf)
                                                          подпись сходится с содержимым?
                                                       h. член SS1-CODE / подсистема CLIENT
                                                          имеет право на echo? (ACL в gconf)
                                                       i. записать в message log
                                                       j. вызвать is-provider
                                                       k. ответ подписать sign-ключом члена SS2-CODE
 l. проверить ответ так же, как ss2 проверял   ◄──────
    запрос (печать, OCSP, подпись); в лог
```

TLS (c–e) — это «пропуск курьера», защищает канал и говорит, с какой машиной ты связан. Подпись (b, g, k, l) — «подпись директора», защищает содержимое и говорит, какая организация за него отвечает. Одно другое не заменяет: TLS не оставляет следов после закрытия соединения, а подпись живёт в логе.

## 6. Отзыв: OCSP

Паспорт можно аннулировать до истечения срока (ключ утёк). Список аннулированных ведёт CA. **OCSP** — сервис «вот серийник серта, он ещё действителен?». Ответ подписан ключом OCSP-респондера (третий серт из `ca`, `ocsp.pem`, поэтому его тоже загружаем на CS).

Спрашивать при каждом сообщении дорого, поэтому:

```
   ss1 раз в N минут: «мои auth и sign ещё живы?» ──► ca:8888 ──► подписанный ответ, кладётся в кеш
   ss2, получив от ss1 сообщение: берёт OCSP-ответ на серты ss1
        — из своего кеша, либо
        — у самого ss1 по порту 5577 (ss1 раздаёт готовые ответы на свои серты)
   Ответ старше ocspFreshnessSeconds → считается протухшим → сообщение отклоняется
```

Это и есть конфигурация 6 плана: сделать `ocspFreshnessSeconds` крошечным, чтобы кеш всегда протухал и OCSP попадал в синхронный путь.

## 7. Метка времени: TSA

Через пять лет серт члена SS1-CODE истёк. Как доказать, что подпись в логе была поставлена, **пока** серт был жив? Нотариус со штампом даты — **TSA** (time-stamping authority). SS раз в минуту берёт хеши накопившихся записей message log, отправляет в `ca:8899`, получает подписанный «я видел этот хеш в 12:34:56» (подпись ключом TSA, `tsa.pem`, поэтому и он на CS).

Пакетно и в фоне — поэтому в нормальном режиме в задержке запроса его нет. Конфигурация 5 плана (синхронный timestamping) вытаскивает его в путь; конфигурация 4 (TSA выключен) проверяет, сколько это стоит в обратную сторону.

## 8. Ключ CS и якорь: откуда берётся самое первое доверие

Всё выше опирается на «gconf говорит, что…». gconf — телефонная книга сети, её раздаёт CS. Но кто сказал, что книга настоящая?

```
   CS: пара ключей в своём softToken (1.3 в гайде)
        └─ подписывает каждую версию gconf

   ЯКОРЬ (anchor.xml) = { адрес cs, хеш публичного ключа CS }
        └─ передаётся на каждый SS РУКАМИ (wizard, шаг 1)

   SS: скачал gconf → проверил подпись ключом, чей хеш в якоре → верит содержимому
        → в содержимом лежит серт Test CA → теперь верит и ему
        → в содержимом лежат auth-серты всех серверов → знает, с кем говорит
```

Курица и яйцо разрывается тем, что якорь ты приносишь лично. В проде — администратор получает файл от RIA и сверяет хеш по телефону. Ключ CS не от CA — он корень сам по себе, ровно как корневой серт браузера.

## 9. Где лежат приватные ключи: токен и PIN

Приватные ключи SS лежат в **токене** — на стенде это `softToken-0`, файл на диске, зашифрованный PIN'ом. В проде на sign-ключ ставят HSM (железка, из которой ключ вообще нельзя вытащить), auth обычно остаётся в софт-токене.

```
   PIN ──► токен разблокирован ──► signer может ставить подписи
   контейнер перезапустился → токен заблокирован → ничего не подписывается
   sidecar: XROAD_TOKEN_PIN → xroad-autologin вводит PIN сам при старте
```

Поэтому PIN в wizard'е и в compose обязан совпадать. «TokenNotActive» в логах — это оно: зайти в Keys and certificates → Log in.

## 10. Все сертификаты стенда, поимённо

| Сколько | Что | Кто выдал | Где живёт | Куда загружаем |
|---|---|---|---|---|
| 1 | корневой серт Test CA | сам себе | `ca:/home/ca/certs/ca.pem` | CS → Trust services |
| 1 | серт OCSP-респондера | Test CA | `ocsp.pem` | CS → в CA → OCSP responders |
| 1 | серт TSA | Test CA | `tsa.pem` | CS → Timestamping services |
| 4 | auth-серты (ss0…ss3) | Test CA, `type=auth` | токен каждого SS | Import на свой SS, Register → CS |
| 4 | sign-серты (члены SS0-CODE…SS3-CODE) | Test CA, `type=sign` | токен своего SS | Import на свой SS |
| 2 | ключи CS для подписи gconf (internal + external) | — (корень) | токен CS | никуда; хеш уходит в якорь |
| 5 | внутренние TLS-серты (admin UI :4000, IS :8443) | сам себе | каждый SS и CS | никуда, «Not secure» в браузере — это они |

Первые три копируешь с `docker cp`, четыре+четыре создаёшь через Add key → testca → Import, остальное создаётся само.

## 11. Шпаргалка аналогий

| X-Road | Аналогия |
|---|---|
| приватный ключ | печать |
| публичный ключ | оттиск печати, по которому её узнают |
| сертификат | паспорт: оттиск + имя + печать государства |
| CA | паспортный стол |
| CSR | анкета на паспорт |
| auth-серт | пропуск курьера / замок на двери |
| sign-серт | подпись директора на документе |
| OCSP | «проверьте, не аннулирован ли паспорт» |
| TSA | нотариус со штампом даты |
| gconf | телефонная книга сети, подписанная издателем |
| якорь | «издатель книги вот этот, узнавать по такой печати», передано лично |
| токен + PIN | сейф с печатями и код от него |
| message log | архив подписанных документов |
