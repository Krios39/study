# Стенд на трёх машинах (среда B)

Три Linux-ноутбука в офисе, соединённые своим свитчем. Тот же стенд и тот же bench, что на одной машине; отличаются раскладка контейнеров и сеть.

```
        университетская сеть ── VPN ── доступ снаружи (только к l2)
                   │ (Wi-Fi или второй порт)
               [l2 10.10.0.2]  ss1 (consumer) + k6/curl, отсюда запускается bench
                   │
  ── свитч, изолированная подсеть 10.10.0.0/24, только для стенда ──
       │                                              │
 [l1 10.10.0.1]                                 [l3 10.10.0.3]
 cs, ca, ss0, ss3 (provider B), is-provider-b   ss2 (provider A), is-provider
```

- **Свитч соединён с розеткой кафедры** (так подключил руководитель, 03.10): машины получают на проводе адрес университета по DHCP и доступны через VPN напрямую; трафик между машинами свитч пересылает внутри себя. `setup.sh` добавляет 10.10.0.N вторым адресом к существующему подключению, не заменяя его. l2 — на eduroam, на проводе только 10.10.0.2.
- **Сеть контейнеров — ipvlan L2** на проводном интерфейсе к свитчу (`compose.yml`): у каждого контейнера свой адрес, без NAT и проброса портов, но MAC у всех один — как у машины (свитч соединён с розеткой кафедры, новые MAC в сети университета не нужны); на одном адресе может быть только один SS (порты 5500/5577 фиксированы протоколом). Имена контейнеров на других машинах — `extra_hosts`; временные контейнеры bench (k6, curl) получают те же имена через `--add-host`.
- Хост не достаёт до своих ipvlan-контейнеров — bench работает через `docker exec`, UI — туннелем через другую машину: `ssh -L 4000:10.10.0.10:4000 l2` → https://localhost:4000 (CS).
- У ss3 свой эхо-сервис на l1 (`is-provider-b`), чтобы оба провайдера отвечали из локального IS.
- `direct` (baseline-0) теперь идёт k6 (l2) → is-provider (l3) через свитч — это путь клиент → IS по сети, а не внутри одной машины.

## Удалённый доступ (на месте, первым делом)

Ноутбуки стоят в офисе, работа с ними — из дома. На месте нужно только это, остальное (`setup.sh` без `--access`) — потом по ssh:

```bash
sudo bash setup.sh l2 <интерфейс к свитчу> --access [--tailscale]
```

ssh-сервер, открытые ключи с https://github.com/Krios39.keys (или `--keys=файл`) в `authorized_keys`, адрес 10.10.0.N на интерфейсе к свитчу, сон и крышка выключены. В конце — отчёт: адреса во внешней сети, маршрут наружу и что помешает подключиться после перезагрузки без человека рядом (Wi-Fi-подключение только для одного пользователя или с паролем «у пользователя» — до входа в систему не поднимется; шифрованный диск ждёт пароль у экрана).

Пути снаружи, по порядку (Tailscale — только если ни один из путей выше не работает или адрес меняется после перезагрузки):
1. **IPv6 через eduroam**: у eduroam публичный IPv6 университета (2001:bb8:…), постоянный адрес обычно переживает перезагрузку — `ssh -6 user@<адрес>` из любой сети с IPv6 (eduroam в общежитии), если университет не режет входящие. Отчёт печатает эти адреса.
2. **Учебный VPN → проводная сеть кафедры**: у l2 нужен второй порт (USB-Ethernet), встроенный — в свитч. Адрес по DHCP может смениться — спросить у Артёма/IT закреплённый адрес или имя. Через eduroam по IPv4 почти наверняка нет (частные адреса, клиенты изолированы).
3. **`--tailscale`** — исходящее соединение, работает за любым NAT, адрес не меняется; с разрешения руководителя.

Проверять с телефона в режиме модема, не из сети университета, включая `sudo reboot` и повторный вход на тот же адрес. С l2 на l1/l3 — `ssh -A` (ключ с твоего ноутбука проходит дальше).

Docker по умолчанию берёт сети 172.17–172.31.x — те же, что у учебного VPN (172.18.64.0/23) и eduroam (172.31.208.0/21): ответы на ssh ушли бы в docker-мост. `setup.sh` переносит сети docker в 10.200–10.201.x (`/etc/docker/daemon.json`).

## Установка

На каждой машине (адрес из `ip -br link` — интерфейс, воткнутый в свитч):

```bash
curl -fsSL https://raw.githubusercontent.com/Krios39/study/master/1_semester/distributed_systems_seminar/stand/multihost/setup.sh -o setup.sh
sudo bash setup.sh l1 enp0s31f6
```

`setup.sh`: пакеты под apt/dnf/pacman/zypper (git, docker + compose ≥ 2.24, chrony, ssh, node на l2), репозиторий в `/opt/study` (путь одинаковый на всех машинах — compose монтирует файлы стенда по абсолютному пути), `10.10.0.N/24` на интерфейсе (NetworkManager или systemd-networkd), `l1/l2/l3` в `/etc/hosts`, сон и крышка выключены, автообновления выключены, `.env` стенда (роль, профиль compose, интерфейс, диапазон адресов временных контейнеров; логин/пароль/PIN спросит — **одинаковые на всех трёх**), образы скачаны заранее. Повторный запуск безопасен.

Потом на l2, от своего пользователя:

```bash
bash /opt/study/1_semester/distributed_systems_seminar/stand/multihost/link.sh user@l1 user@l3
```

ssh-ключ l2 → l1/l3, `~/.ssh/config` с ControlMaster (bench делает сотни docker-вызовов на l1/l3), docker context `l1`/`l3`.

## Запуск

Всё с l2, из `/opt/study/1_semester/distributed_systems_seminar/stand`, теми же командами:

```bash
node bench/up.js --fresh     # compose на всех трёх (через ssh), init через hurl на l1 — ключи генерируются заново
node bench/check.js          # + docker на l1/l3, расхождение часов, ping по свитчу
node bench/night.js 2        # в tmux: tmux new -s night
```

`STAND_HOST` в `.env` включает многомашинный режим в `bench/lib.js`: контейнеры другой машины — `docker --context <host>`, compose — `ssh <host> docker compose …` в каталоге стенда (со своим `.env` той машины), hurl — на l1 (там volume с сертификатами testca), docker stats — по процессу на машину.

## Не проверено

Написано и проверено на одной машине (compose-раскладка через `docker compose config`, пакетная часть `setup.sh` в контейнерах Debian/Fedora/Arch/openSUSE/Mint); на трёх машинах ещё не запускалось. Первые вероятные места: имя интерфейса и NetworkManager, ipvlan на конкретной сетевой карте, ssh-доступ l2 → l1/l3, расхождение часов.
