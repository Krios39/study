## 1. A Decentralised Public Key Infrastructure for X-Road

**Библиография.** M. Bakhtina, K. L. Leung, R. Matulevičius, A. Awad (University of Tartu), P. Švenda (Masaryk University). *ARES 2023*, Benevento. DOI: [10.1145/3600160.3605092](https://doi.org/10.1145/3600160.3605092). Код PoC: gitlab.cs.ut.ee/ssi-xroad.

**Вопрос.** Как установить доверие между информационными системами X-Road через децентрализованную PKI (DPKI), а не через PKIX с централизованными CA?

**Метод.** Design science research (DSRM, Peffers). Статья закрывает шаги «демонстрация» и «оценка» для архитектуры, предложенной ранее (SAC 2023, отчёт NIIS «Rebooting Trust Management in X-Road»).

**Как устроен X-Road по статье.**
- Central Server распространяет глобальную конфигурацию: реестр членов, доверенные CA и TSA.
- Security Server отвечает за ключи, защищённый канал, подпись сообщений, timestamping и логирование.
- У Security Server два типа ключей: auth (TLS между SS) и sign (подпись сообщений).
- Статус сертификатов проверяется по **OCSP без nonce**. Это позволяет кешировать и заранее создавать ответы, что снижает нагрузку на OCSP-сервис, но открывает replay-атаки с отозванным сертификатом. Окно такой атаки ограничено интервалом обновления (по умолчанию **20 минут**).

**PoC.**
- DID-метод Sovrin на Hyperledger Indy (VON Network, 4 валидатора).
- Верифицируемые учётные данные (VC) — AnonCreds; поддерживают selective disclosure, predicates и revocation registry на ledger.
- SSI-агент — Aries Cloud Agent Python (ACA-Py). Он заменяет компоненты Signer и Proxy в Security Server, канал — DIDComm.
- Central Server и облегчённый Security Server написаны на Spring Boot.
- Онбординг: Present Proof → endorsement транзакции регистрации DID → запись в ledger.
- Перед каждым обменом **обе стороны** запрашивают друг у друга verifiable presentation, то есть атрибутный контроль доступа идёт на каждый запрос.
- Протокол non-repudiable message exchange пришлось реализовать самим: ACA-Py не даёт API для подписи.

**Результаты.**
- Цели G1 (децентрализация) и G2 (гранулярный доступ) достигнуты, G3 (автоматический онбординг) — условно.
- Качественная оценка по безопасности, надёжности и контролю:
  - меньше риск DoS и SPoF: revocation list распределён по узлам ledger;
  - replay-атаки закрыты свежими non-revocation proofs;
  - у члена больше контроля над приватностью.
- Остаются зависимости от внешних issuer'ов и SSI-агентов. Проблема масштабирования проверки статуса отзыва сохраняется, её только смягчает ledger.

**Ограничения.** Решение привязано к экосистеме Indy/Aries. Предполагается, что у каждого члена есть свой SSI-агент. Governance вне рамок работы. **Производительность не измерялась.**

**Для темы.** Статья называет конкретный механизм доверия и его компромисс: OCSP без nonce ради нагрузки и доступности ценой окна replay-атак. Кроме того, PoC добавляет proof request на *каждый* запрос, то есть заметный overhead, который никто не измерил. Это кандидат на сравнение: PKIX/OCSP против DPKI/VP.

## 2. Migration of X-Road to Post-Quantum Cryptography

**Библиография.** Dr. Mariia Bakhtina (University of Tartu). Консультанты: R. Matulevičius (UT), P. Kivimäki (NIIS). NIIS Publication series, 13.01.2026, 67 с. ISBN 978-9916-9853-4-2, ISSN 2733-3345.

**Цель.** Понять, какие угрозы квантовые вычисления создают для X-Road и как адаптировать систему. RQ1–RQ4: угрозы от квантовых вычислений (QC), угрозы самой PQC, затронутые активы, меры защиты.

**Метод.**
- Криптографическая инвентаризация X-Road 7.6.2: документация, исходники и IBM CBOMkit.
- Систематический литобзор по Kitchenham: 204 статьи, после отбора 21.
- Моделирование угроз и оценка рисков с экспертами NIIS (R = EP · I).

**Инвентаризация (самое полезное для семинара).** Всего 27 криптоактивов: 9 для данных в передаче, 12 для данных в хранении, 6 для конфигурации.

| Механизм | Криптография |
|---|---|
| TLS SS↔SS (auth key) | RSA-2048 (по умолчанию) или secp256r1; ECDHE/DHE + AES-256-CBC-SHA384/256 |
| Подпись сообщений (sign key) | RSA-2048 или secp256r1 (допускаются 2k/3k/4k), SHA-256; soft token или HSM |
| OCSP | порт 5577, хеши сертификатов SHA-1 |
| Timestamping | внешний TSA, ≥ RSA-2048; хеш записи лога ≥ SHA-256 |
| TLS SS↔IS | RSA; 8 наборов ECDHE/DHE + AES-128/256 GCM/CBC |
| UI/API | TLS, RSA-2048, порт 4000 |
| Message log | AES-128-CTR, ключ через HKDF-SHA-512; hash chain / Merkle tree; архив ASiC-E + XAdES |
| Бэкапы и архивы | GPG RSA-4096 |
| Глобальная конфигурация | подпись rsa-sha512, хеш SHA-512 |

**Результаты.**
- 10 угроз: T1–T6 от QC (включая Harvest Now, Decrypt Later) и PQC.T1–T4 для самой PQC.
- 6 бизнес-активов, 32 риска. Высокий приоритет: подделка подписи сообщения, HNDL для тела сообщения в логе, подделка подписи лога и архива.
- 11 мер (C1–C11):
  - PQ-подписи (Dilithium, FALCON, SPHINCS+) и PQ KEM (Kyber, HQC);
  - на переходный период — гибридные (composite) подписи и альтернативные поля в X.509;
  - AES-192/256, удвоение длины хеша, отказ от долгого хранения данных.
- Стратегия — гибридная (dual-stack) миграция, начинать с данных, которые должны долго оставаться конфиденциальными.
- HSM и TPM несовместимы с PQC, их придётся заменить. Возможна перегрузка CA, против неё предлагается ACME.
- При гибридной подписи Security Server создаёт и проверяет **две** подписи.

**Числа (все из чужих работ, своих замеров нет).**
- Ключ ML-KEM **1 568 байт против 64 байт** у X25519 (ссылка на Cloudflare). Отчёт связывает это с фрагментацией и дополнительными round-trips. 1 568 байт — это публичный ключ Kyber1024 (уровень NIST 5, см. источник 5), а не уровень AES-128, как сказано в отчёте.
- AES-128 против квантового противника ≈ 106 бит стойкости.
- Про латентность, пропускную способность и размер подписей в X-Road — только качественные утверждения.

**Ограничения.** Нет прототипа, замеров и оценки стоимости. Доступность вне рамок. Вероятности угроз — экспертные. В таблицах рисков есть внутренние несостыковки: разные списки «high»-рисков в Табл. 5 и Табл. 11.

**Для темы.** Это готовая карта того, **что именно** измерять: TLS-handshake между SS, подпись и проверка сообщения, OCSP, timestamping, message log, подпись глобальной конфигурации. Отчёт прямо предсказывает рост overhead при переходе на PQC, но **базового уровня (baseline) для классического X-Road в нём нет** — это пробел, который закрывает тема семинара.

## 3. Securing Organisational Digital Identity: A Full-Lifecycle Approach to Distributed Key Management

**Библиография.** M. Bakhtina, J. Kvapil, P. Švenda (Masaryk University), R. Matulevičius (University of Tartu). *International Journal of Information Security* 25:131 (2026), 21 с. DOI: [10.1007/s10207-026-01291-5](https://doi.org/10.1007/s10207-026-01291-5). Расширенная версия доклада на CAiSE 2024. Код: github.com/crocs-muni/xroad-threshold-signatures.

**Вопрос.** Как защитить существующую цифровую идентичность организации (ODI) механизмами управления ключами, чтобы прийти к zero trust? Проблема: ключ организации контролирует один Security Server. Это SPoF и риск злоупотреблений со стороны своих сотрудников (insider threat).

**Метод.**
- Design science. Обзор механизмов управления ключами по фазам NIST SP 800-57 (pre-operational, operational, post-operational).
- Артефакт — **DKMS** на пороговых подписях (K-of-N), в двух вариантах:
  - с trusted dealer: RSA по Shoup;
  - с распределённой генерацией ключа (DKG): ECDSA по GG18.
- Таксономия подписантов: автоматические, люди, полуавтоматические.

**PoC на X-Road 7.7.0.**
- Платформа пороговой подписи подключена к Security Server через **PKCS#11**, поэтому проверяющую сторону менять не нужно.
- Сценарий: больница ↔ Health board, доли ключа у IS, SS и сотрудников, порог 3-of-5.

**Результаты: RTT полного обмена Client→Provider**, среднее по 1000 запросам. Стенд — один ноутбук (Ryzen 7 PRO 7840U), всё в Docker, без сетевых задержек.

| Токен / группа | RSA | ECDSA |
|---|---|---|
| SoftToken (встроенный) | 32 ms (±5) | 32 ms (±5) |
| SoftHSM 2.6.1 | 36 ms (±4) | 30 ms (±5) |
| YubiKey 5C NFC | 174 ms (±8) | 100 ms (±5) |
| TPM NTC 7.2.3.1 | 267 ms (±11) | 190 ms (±6) |
| 2-of-2 | 191 ms (±35) | 501 ms (±50) |
| 3-of-5 | 272 ms (±36) | 677 ms (±48) |
| 11-of-15 | 705 ms (±80) | 3081 ms (±345) |

- RSA 3-of-5 по задержке сопоставим с самым медленным аппаратным токеном. Авторы считают такой штраф приемлемой ценой за zero trust.
- ECDSA-пороговые подписи сильно медленнее: у GG18 10 раундов подписи. Протокол DKLS с 3 раундами должен улучшить результат.
- Размер передаваемых данных:
  - RSA-подпись — около 1.5 kB на участника за раунд;
  - ECDSA-подпись: от 100 B до 3.5 kB (2-of-2), от 150 B до 7 kB (3-of-5), от 760 B до 35 kB (11-of-15);
  - ECDSA DKG — до 105 kB.

**Ограничения.**
- Локальный стенд, поэтому числа — нижняя граница.
- Замерен только сквозной RTT; отдельно OCSP, timestamping и проверка подписи не выделены.
- При K<N теряется non-repudiation.
- Задержка от участия человека (human-in-the-loop) не измерена.
- У RSA-варианта dealer остаётся SPoF.
- Постквантовые пороговые подписи и post-operational фазы в X-Road не оценены.

**Для темы.** **Главный количественный источник.** Даёт baseline подписи в X-Road 7.7.0 (SoftToken ≈ 32 ms RTT), методику замера (RTT по 1000 запросам, xrd-dev-stack в Docker) и показывает, как overhead растёт с усилением модели доверия. Методику стоит воспроизвести и расширить: добавить сеть и разложить RTT на TLS, подпись, OCSP и timestamping.

## 4. Architecture of Secure MPC as a Service with No Single Point of Trust

**Библиография.** Anton Zakatov, магистерская диссертация (Software Engineering, 30 ECTS), University of Tartu, 2025. Руководители: Kert Tali, Raimundas Matulevičius. Контекст: проект JOCONDE (Eurostat + Cybernetica AS).

**Вопрос.** Как добиться отсутствия единой точки доверия (SPoT) в сервисе MPC-as-a-Service, чтобы никто, включая провайдера, не мог нарушить конфиденциальность данных клиента?

**Метод.**
- Design science. Архитектура по Viewpoints & Perspectives (Rozanski & Woods), с акцентом на security.
- Attack trees: сначала для абстрактного «минимального MPC-фреймворка» (требования взяты у Sharemind MPC, Roseman Labs, Partisia), затем для системы JOCONDE.
- Решения оформлены как ADR.
- Оценка — 3 экспертных интервью.

**Архитектурные решения (ADR-1…8).**
1. Не менее 3 независимых Computing Parties.
2. Прямая связь Client ↔ Computing Party, без reverse proxy: прокси был бы SPoT.
3. Федерация Service Nodes, открытый и аудируемый код.
4. TEE на базе виртуальных машин + MPC, remote attestation, mTLS, TEE разных вендоров.
5. Древовидная топология узлов, служебные артефакты распространяет Service Broker.
6. Иерархия CA с корнем у System Operator, но корневой CA **только распространяет** сертификаты. Само доверие устанавливается **вне системы**: стороны сверяют fingerprint цепочки сертификатов по out-of-band каналу.
7. MPC-проверки качества данных до основного вычисления.
8. Целостность: публичные digest образов ПО, подписанный Addendum с хешем спецификации задачи.

**Результаты.** Эксперты подтвердили полноту угроз и достаточность мер. Главный компромисс автор формулирует прямо: *stronger trust guarantees at the expense of operational simplicity*.

**Числа.** Замеров нет, прототипа нет. Overhead описан качественно: out-of-band верификация названа «negligible», настройка доверия — «one-time procedure».

**Ограничения.** Работа теоретическая; предполагается корректная реализация ПО; решения заточены под официальную статистику; всего 3 эксперта. Доступность и supply chain отложены на будущее. Замеры производительности — следующая фаза JOCONDE.

**Для темы.** Концептуальная рамка: отказ от единой точки доверия переносит стоимость в процедуры и архитектурную сложность, и эту стоимость признают, но не измеряют. X-Road в работе **не упоминается**. Параллели (Central Server как корень доверия против out-of-band верификации, Security Servers против Service Nodes, PKI и mTLS) придётся проводить самому.

## 5. Integrating post-quantum cryptography to UXP

**Библиография.** Nikita Snetkov, Jelizaveta Vakarjuk (Cybernetica AS). Cybernetica Research Report D-2-499, версия 1.1, 10.01.2023, 15 с. UXP (Unified eXchange Platform) — коммерческая версия X-Road от Cybernetica.

**Цель.** Обзор доступных PQ-примитивов: где и как встроить их в UXP, какие будут трудности, что рекомендовать.

**Метод.** Обзор стандартизации (NIST, позиции BSI и ANSSI) и сравнение схем по опубликованным бенчмаркам OQS. Собственных экспериментов нет.

**Где в UXP нужна PQC (то же, что потом в источнике 2):**
- TLS между Security Server и внешними клиентами, плюс их сертификаты;
- подпись сообщений между Security Servers;
- подпись глобальной конфигурации.

**Сравнение схем (Table 2).** Все схемы на уровне NIST 5. Бенчмарк OQS, Intel Xeon Platinum 8259CL @ 2.50 GHz.

| Схема | Размеры, байт | Операций в секунду |
|---|---|---|
| Kyber1024 (KEM) | pk 1 568, sk 3 168, ct 1 568 | gen 36 949, encaps 32 358, decaps 41 786 |
| FrodoKEM-1344-SHAKE | pk 21 520, sk 43 088, ct 21 632 | gen 205, encaps 190, decaps 193 |
| Classic McEliece-8192128 | pk 1 357 824, sk 14 120, ct 240 | gen 1.47, encaps 14 102, decaps 6 723 |
| Dilithium5 | pk 2 592, sk 4 864, sig 4 595 | gen 9 991, sign 5 224, ver 10 612 |
| Falcon-1024 | pk 1 793, sk 13 953, sig 1 280 | gen 39, sign 1 403, ver 8 672 |
| SPHINCS+-256f | pk 64, sk 128, sig 49 856 | gen 226, sign 10.66, ver 226 |
| SPHINCS+-256s | pk 64, sk 128, sig 29 792 | gen 13.82, sign 1.13, ver 439 |

**Гибридный режим.**
- Ключи: конкатенация ECDH и Kyber, общий секрет = ss_DH ‖ ss_PQ (по draft-stebila-tls-hybrid-design).
- Подписи: четыре способа комбинирования по Bindel et al. — concatenation, weak nesting, strong nesting, dual message combiner.
- Сертификаты: альтернативные ключи и подписи в X.509 (редакция 2019) через subjectAltPublicKeyInfo, altSignatureAlgorithm, altSignatureValue. Сертификат от этого растёт.
- Для подписи сообщений в UXP предлагается конкатенация. Отчёт прямо говорит, что сообщения станут больше, а скорость подписи и проверки на решётках остаётся высокой.

**Рекомендации.**
- TLS: Kyber1024 в гибриде с эллиптическими кривыми; аутентификация — Dilithium5 в гибриде.
- Подпись сообщений: протестировать Dilithium и Falcon в гибриде. У Falcon меньше подпись и быстрее проверка, у Dilithium быстрее подпись и проще безопасная реализация.
- Глобальная конфигурация: stateful hash-based подписи (LMS/XMSS, подписывает одна сторона) или Falcon в гибриде (важнее скорость проверки).
- Инструменты: OQS (liboqs, OQS-OpenSSL-1.1.1), тестировать гибридный TLS 1.3 на Security Servers.

**Ограничения.** Написан до финальных стандартов NIST (FIPS 203/204/205 вышли в августе 2024), поэтому старые имена и параметры. Все числа — сторонние бенчмарки примитивов, не замеры UXP.

**Для темы.** Даёт порядок величин для того, что источник 2 описывает только словами: подпись Dilithium5 в 4 595 байт против 256 байт у RSA-2048, и скорость операций. Это и есть первый источник цифры 1 568 байт. Для семинара полезно как ориентир, что сравнивать после baseline.

## 6. High-Performance Qualified Digital Signatures for X-Road

**Библиография.** A. Ansper, A. Buldas, M. Freudenthal, J. Willemson (Cybernetica AS, ELIKO). *NordSec 2013*, LNCS 8208, pp. 123–138, Springer. https://link.springer.com/chapter/10.1007/978-3-642-41488-6_9

**Контекст.** X-Road 5-го поколения. Подписи сообщений делались программными ключами Security Server и не считались квалифицированными по эстонскому Закону о цифровой подписи. Для этого нужны аппаратные ключи, OCSP и timestamp, а дешёвые смарт-карты слишком медленные.

**Решения (именно отсюда архитектура нынешнего X-Road):**
- **Кеширование OCSP у отправителя.** Не запрос на каждую подпись, а ответ, действующий какое-то время («a couple of hours»). Число OCSP-запросов зависит от числа сертификатов, а не сообщений. Снимает SPoF, перегрузку OCSP-сервиса и задержку.
- **Timestamping у получателя и с отложенной очередью.** Штамп можно поставить в любой момент, пока действует OCSP-ответ. Немедленно или в очередь — вопрос политики: доступность против риска не доказать подпись позже.
- **Пакетная подпись и пакетный timestamp** на дереве Меркла (Pavlovski–Boyd): одна операция RSA на пакет, у каждого сообщения — свой hash chain до корня. Рассмотрены и отвергнуты batch RSA по Fiat и простые hash lists (последние применены в Азербайджане). Дана XSD-схема hash chain.
- Переход на XAdES и ASiC, общий с национальной PKI.

**Числа (все оценочные или контекстные, замеров нет).**
- Нагрузка: более 240 млн запросов в год (2011), до 1 млн в день. Пик 5.04.2013 — 4 194 сообщения за 5 минут, около 14 сообщений в секунду (Digital Prescription Center).
- Смарт-карта SafeNet Smart Card 400: одна подпись RSA-1024 за 0.45 с, RSA-2048 за 1.23 с.
- Keccak-256: 101.3 такта на байт (64-байтный вход, AMD Athlon 2400 МГц) → ≈ 370 000 хеширований в секунду.
- Отсюда теоретическая пропускная способность пакетного подписывания при одной подписи в секунду: 32 · 370 000 ≈ **11.84 МБ/с**.
- Контекст: 1 193 050 активных ID-карт (апрель 2013), около 112 млн подписей ID-картами за 11 лет; более 100 организаций и 600 реестров в X-Road.

**Ограничения.** Прототипа и замеров нет. Авторы сами пишут, что учтено только хеширование, а реальный бенчмарк — будущая работа.

**Для темы.** Первоисточник того, **почему** механизмы доверия X-Road устроены асинхронно: кеш OCSP, отложенный пакетный timestamping, пакетная подпись. Это прямо сформулированный компромисс между стоимостью доверия и доступностью. Отсюда же конкретная гипотеза для измерений: сравнить синхронный и пакетный timestamping. Все числа — 2011–2013 годов и оценочные; обещанного бенчмарка в открытой литературе мы пока не нашли.

## 7. XATF: A Carrier-Binding Verification Profile with Typed Failure Attribution for AI-Agent Evidence over X-Road

**Библиография.** Anton Sokolov (Tyche Institute, Таллин) — один автор, университетской аффилиации нет. В колонтитуле: «accepted for publication in IEEE Access, author's version», DOI 10.1109/ACCESS.2026.3732535, рукопись от 13.08.2026. Тут же строкой ниже «Digital Object Identifier Not assigned» — противоречие. Артефакты на Zenodo (10.5281/zenodo.20613101).

**Вопрос.** Как привязать доказательства о действиях AI-агента к конкретному обмену через X-Road, не превращая X-Road в верификатор агентов. X-Road остаётся носителем (PKI carrier) и свидетелем аудита, а отдельный пакет AEP (Agent Evidence Package) несёт identity, delegation, policy, runtime, freshness, revocation. Правило приёмки: accept := carrier ∧ binding ∧ evidence.

**Метод.** Есть реализация и эксперименты: лаборатория из двух Security Server в Docker (образы xrddev, Central Server, Test CA, пиннинг по sha256), реальный обмен с переносом хеша AEP, корпус подписанных пакетов (SHA-256 над canonical JSON, RSA-4096, ML-DSA-65 по FIPS 204, timestamp по RFC 3161), строгий профиль из 18 негативных кейсов, два независимых верификатора (Python и Node) для проверки на согласованность.

**Результаты.**
- Реконсиляция сквозного обмена: request ID, хеш payload и хеш AEP сходятся со строками message log на обеих сторонах.
- 18/18 совпадений вердикта и метки отказа у двух независимых верификаторов.
- Baseline «только подписи» принимает 11 из 18 строго негативных кейсов, включая случай, где подписи валидны, а привязка к носителю не совпадает.
- 5 из 5 негативных кейсов уровня верификатора дают HTTP 200: транспорт X-Road их не ловит, это уже offline-проверка.

**Числа (замеренные, 50 прогревов + 1000 измерений).**
- Offline-верификация: медиана **18.296 ms** (IQR 9.386) на accept-path, 18.316 ms на reject-path. Железо в тексте не указано, разброс большой.
- Размер запроса через X-Road: **289 B** (только хеш), **352 B** (URI + хеш), **23 360 B** (весь AEP в base64) — разница на два порядка.
- Размер пакета AEP: в среднем 17 587 B.
- Это оверхед **дополнительного слоя**, а не самого X-Road. Задержка обмена через Security Server, стоимость OCSP, timestamping и подписи здесь не измерялись.

**Достоверность — читать с оговорками.** В плюс: X-Road описан корректно и предметно (Security Server, Central Server, глобальная конфигурация, OCSP, timestamping, таблица `messagelog.logrecord`, заголовок `x-road-request-hash`), ссылки — настоящие RFC, FIPS и документация docs.x-road.global, есть реальная оценка с негативными контролями и публично выложенные артефакты, автор сам сообщает о двух найденных дефектах. В минус: один автор, собственный «институт» вместо университета; ключевая предшествующая работа (EATF, AEP) — самопубликация того же автора, что он честно помечает как «not independent validation»; терминология (XATF, AEP, OVERT receipt) за пределами этих работ не существует; в тексте признаётся, что материал подавался в несколько мест (принят на GAISS 2026, отозван из Journal of Cybersecurity); в благодарностях указано, что текст писался с помощью языковой модели. Не мусор, но и не независимо подтверждённая работа.

**Ограничения (по самому тексту).** Dev-образы, игрушечный сервис-поставщик, синтетические доказательства; message log — лабораторная БД; из модели угроз исключены компрометация ключей и хостов, а также ошибки самих верификаторов; не покрыты ротация сертификатов, отказ OCSP и TSA, устаревшая глобальная конфигурация, расхождение часов. Автор прямо пишет, что это не заявка на production-производительность.

**Для темы.** Baseline по самому X-Road отсюда взять нельзя. Полезно другим: это пример стоимости *надстройки* над X-Road (289 / 352 / 23 360 байт и ~18 ms проверки) и хороший образец методики стенда — два Security Server в Docker с фиксированными образами, экспорт message log, воспроизводимый пакет артефактов. Цитировать с явной пометкой о статусе публикации.

## 10. X-tee teenuste jõudlustestimine Eesti äriregistri näitel

**Библиография.** Erik Taklai. Дипломная работа, Tallinna Tehnikaülikool, 2020, 44 с. Руководители: Kaido Kikkas (PhD), Tambet Artma (BSc). Файл: `Taklai_2020_X-tee_teenuste_joudlustestimine.pdf`, [источник](https://digikogu.taltech.ee/et/Download/3e6d35ea-6f33-4af8-be4f-3be143d310ac).

**Что делалось.** Нагрузочное тестирование сервисов Эстонского бизнес-регистра в X-Road версии 6. Разобраны пять самых используемых сервисов и пять самых медленных, подробный кейс — `detailandmed_v3`.

**Стенд.** SoapUI (выбран вместо JMeter из-за работы с WSDL). Тестовая среда со сниженными ресурсами, три сервера по одному ядру Intel Xeon 2.66 ГГц: Security Server (12 ГБ RAM), adapter-сервер (11.5 ГБ), БД (5.5 ГБ), сеть 1 Гбит/с. Нагрузка 10, 20 и 30 одновременных потоков по 600 секунд. Сравнивались три пути: через Security Server, напрямую в adapter (XML) и напрямую в adapter (JSON).

**Числа (среднее время ответа, запрос по регистрационному коду).**

| Путь | 10 потоков | 20 потоков | 30 потоков |
|---|---|---|---|
| Через Security Server | 1 078 ms | 1 728 ms | 2 601 ms |
| Adapter напрямую, XML | 1 022 ms | 1 823 ms | 2 745 ms |
| Adapter напрямую, JSON | 711 ms | 1 461 ms | 2 358 ms |

- Разница «через Security Server минус напрямую» при 10 потоках по пяти наборам входных данных (Табл. 4 и рис. 2): **56, 258, 122, 206 и 319 ms** (1078/1022, 2097/1839, 2522/2400, 2474/2268, 3015/2696). Вывод автора: для пользователя незаметно.
- При 20 и 30 потоках путь через Security Server оказался **быстрее** прямого вызова adapter. Это признак шума стенда, а не ускорения: доверять этим цифрам как измерению overhead нельзя.
- Формат ответа влияет сильнее маршрута: JSON быстрее XML на 300–1100 ms.
- Автор заключает, что время ответа определяется в основном эффективностью запросов к БД, а разница из-за Security Server для пользователя незаметна.

**Для темы.** Ближайшая по смыслу работа: прямое сравнение «через Security Server против напрямую» на реальном сервисе. Но это end-to-end замер прикладного сервиса, где доминирует БД, а не разложение по механизмам доверия. Разброс между прогонами сопоставим с самим измеряемым эффектом. Годится как мотивировка («такие замеры делались только грубо») и как список ошибок, которых стоит избежать: слабый одноядерный стенд, нагрузка, при которой шум превышает эффект, отсутствие изоляции подписи, OCSP и timestamping.

## 11. X-tee platvormi kriitiliste kesksete teenuste testimine

**Библиография.** Liis Mironova. Магистерская работа, Tallinna Tehnikaülikool, факультет ИТ, 2017, 82 с. Файл: `Mironova_2017_X-tee_kesksete_teenuste_testimine.pdf`, [источник](https://digikogu.taltech.ee/et/Download/e1864c2c-4189-4807-a5a7-073ed55d3e2e).

**Что делалось.** Проверка трёх критичных центральных сервисов X-Road версии 6 — глобальной конфигурации, службы статуса сертификатов (OCSP) и службы меток времени — на то, сохраняется ли работоспособность платформы при их отказе. Тестирование ручное, по сценариям.

**Значения в эстонском проде (2017), а не по умолчанию.** Это самое ценное в работе:
- глобальная конфигурация действует **6 часов** (в тестах уменьшали до 10 минут — это значение по умолчанию);
- `ocspFreshnessSeconds` — **8 часов** (28 800 с), в тестах 600 с;
- `acceptable-timestamp-failure-period` — **4 часа** (14 400 с), оно же значение по умолчанию.

По SLA максимальный простой центральных сервисов — 6 часов: пока он не превышен, члены X-Road ничего не замечают, потому что кеш глобальной конфигурации ещё действует. Восстановление минимального набора компонентов центрального сервера занимало около часа; автор пишет, что если 6 часов окажется мало, придётся продлевать срок действия конфигурации.

**Дополнительные тесты по timestamping (по запросу заказчика):**
- при `acceptable-timestamp-failure-period` = 0 и выключенной службе меток Security Server продолжает обрабатывать запросы, то есть обработка вообще перестаёт зависеть от TSA, а целостность обеспечивается лишь частично;
- при значении INT_MAX запросы проходят, только если служба меток сконфигурирована в самом Security Server; иначе обработка падает.

**Что ещё полезного.** Названы сами параметры, которые задают окна отказоустойчивости, и поведение системы при отказе:
- `confExpireIntervalSeconds` — срок действия глобальной конфигурации, `update-interval` — как часто Security Server её скачивает (в проде обновление примерно раз в минуту). Без действующей конфигурации Security Server изолирован и обмен невозможен.
- `ocspFreshnessSeconds` — сколько живёт кешированный OCSP-ответ. Пока он свеж, всё работает; после истечения Security Server не может отправлять сообщения.
- `timeStampingIntervalSeconds` — частота простановки меток, должна быть меньше `ocspFreshnessSeconds`; `acceptable-timestamp-failure-period` — допустимое время отказа TSA. Timestamping асинхронный, поэтому на обмен сразу не влияет, но при долгом отказе теряется доказательство целостности.
- Тест рассинхронизации времени (NTP) провести не удалось: платформа виртуализации не даёт отключить синхронизацию.

**Для темы.** Замеров производительности нет, но это прямое подтверждение того, какие механизмы стоят в синхронном пути, а какие в фоне, и как это конфигурируется. Практическая ценность двойная: имена параметров, которыми на стенде включают и выключают механизмы доверия (`ocspFreshnessSeconds`, `timeStampingIntervalSeconds`, `acceptable-timestamp-failure-period`, `confExpireIntervalSeconds`), и готовый приём — ставить `acceptable-timestamp-failure-period` = 0, чтобы получить конфигурацию без зависимости от TSA и сравнить её с обычной.

## Сквозные выводы для обзора

1. **Механизмы доверия в X-Road** хорошо описаны: TLS с auth-ключами между SS, подпись сообщений, OCSP (без nonce, кеш около 20 мин), timestamping, message log с hash chain, подписанная глобальная конфигурация (источники 1, 2, 5).
2. **Их асинхронное устройство — осознанный компромисс 2013 года** (источник 6): кеш OCSP, отложенный пакетный timestamping и пакетная подпись введены именно ради производительности и доступности. Обещанного тогда бенчмарка в открытых источниках нет.
3. **Альтернативы усиливают доверие**: DPKI/VC (1), пороговые подписи (3), PQC и гибридные подписи (2, 5), отсутствие SPoT (4). Все авторы признают, что это стоит производительности или операционной сложности.
4. **Замеры самого X-Road есть только в одном источнике (3)**, и там только сквозной RTT на локальном стенде. В источниках 5 и 6 — бенчмарки примитивов и оценки, в источнике 7 — стоимость надстройки над X-Road, а не его собственных механизмов. Нет:
   - разложения задержки по отдельным механизмам (TLS-handshake, подпись и проверка, OCSP, TSA, запись в message log);
   - замеров под нагрузкой и с реальной сетью;
   - baseline классического X-Road, с которым сравнивать PQC (2) и DPKI (1).
5. **Пробел для семинара.** Нужно систематически измерить вклад каждого механизма доверия в латентность, пропускную способность и размер сообщений X-Road, включая синхронный и пакетный timestamping. Это baseline для оценки миграций из работ 1–3 и 5 и первая реальная проверка оценок из работы 6. Методика и стенд (xrd-dev-stack, RTT по 1000 запросам) есть в источнике 3.
6. **Авторские кластеры.** Источники 1–3 — одна группа (Bakhtina, Matulevičius; UT + Masaryk + NIIS), источник 4 — тоже UT (Matulevičius). Источники 5 и 6 — Cybernetica (разработчик X-Road и UXP), то есть тоже не независимые. Источник 7 — самостоятельная исследовательская экосистема одного автора. Стоит добавить официальную архитектурную документацию NIIS и независимые исследования производительности OCSP и TLS.
7. **Что делать с источниками 8 и 9.** Это работы про e-government, а не про системы. Их место — один абзац мотивировки (масштаб развёртывания и то, что каждое сообщение проходит подпись, проверку и логирование дважды), а не раздел с измерениями. Источник 9 лучше заменить первоисточниками.
8. **Единственное прямое сравнение «через Security Server против напрямую» — источник 10**, и оно слабое: одноядерный стенд, шум между прогонами больше измеряемого эффекта (при 20 и 30 потоках путь через Security Server «быстрее» прямого), доминирует время БД. Это усиливает мотивировку темы, а не закрывает её.
