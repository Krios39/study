## 1. Замерено на самом X-Road

### 1.1 RTT полного обмена Client → Provider, X-Road 7.7.0 — **И**

[Securing Organisational Digital Identity (IJIS 2026), Table 3](./Securing%20Organisational%20Digital%20Identity%20A%20Full-Lifecycle%20Approach%20to.pdf)

Стенд: один ноутбук AMD Ryzen 7 PRO 7840U, 4×8 ГБ LPDDR5, всё в Docker (`xrd-dev-stack`), сети между узлами фактически нет. Среднее ± σ по 1000 запросам. У Provider всегда SoftToken. Генерация ключей в замер не входит.

| Токен или группа на стороне Client | RSA | ECDSA |
|---|---|---|
| SoftToken (встроенный в X-Road 7.7.0) | 32 ms (±5) | 32 ms (±5) |
| SoftHSM 2.6.1 | 36 ms (±4) | 30 ms (±5) |
| YubiKey 5C NFC | 174 ms (±8) | 100 ms (±5) |
| TPM NTC 7.2.3.1 | 267 ms (±11) | 190 ms (±6) |
| Пороговая подпись 2-of-2 | 191 ms (±35) | 501 ms (±50) |
| Пороговая подпись 3-of-5 | 272 ms (±36) | 677 ms (±48) |
| Пороговая подпись 11-of-15 | 705 ms (±80) | 3081 ms (±345) |

Производные утверждения авторов: RSA 11-of-15 примерно в 2.6 раза медленнее 3-of-5; ECDSA 3-of-5 более чем в 2.4 раза медленнее RSA 3-of-5; на 11-of-15 ECDSA более чем в 4 раза медленнее RSA.

**Это единственная в папке точка отсчёта для «сколько стоит подпись в X-Road»: ≈32 ms сквозного RTT с программным токеном.**

### 1.3 Через Security Server против прямого вызова, X-Road 6 — **И**, но шумно

[Taklai 2020, Tabel 4–6](./Taklai_2020_X-tee_teenuste_joudlustestimine.pdf)

Стенд: SoapUI, тестовая среда Бизнес-регистра, три сервера по 1 ядру Intel Xeon 2.66 ГГц (Security Server 12 ГБ RAM, adapter 11.5 ГБ, БД 5.5 ГБ), сеть 1 Гбит/с, по 600 с на прогон. Сервис `detailandmed_v3`, запрос по регистрационному коду.

| Путь | 10 потоков (min/avg/max) | 20 потоков | 30 потоков |
|---|---|---|---|
| Через Security Server | 596 / **1078** / 4297 ms | 759 / **1728** / 6015 ms | 957 / **2601** / 13773 ms |
| Adapter напрямую, XML | 510 / **1022** / 2325 ms | 578 / **1823** / 3216 ms | 1050 / **2745** / 5122 ms |
| Adapter напрямую, JSON | 329 / **711** / 1318 ms | 392 / **1461** / 2434 ms | 330 / **2358** / 3339 ms |

Пропускная способность при 10 потоках: 172 268 / 169 239 / 116 353 байт/с соответственно.

Разница «через Security Server минус напрямую» при 10 потоках по пяти наборам входных данных: **56, 258, 122, 206, 319 ms** (пары средних 1078/1022, 2097/1839, 2522/2400, 2474/2268, 3015/2696).

Рост при удвоении нагрузки (10 → 20 потоков): +650 ms (60%) через Security Server, +801 ms (78%) напрямую, +750 ms (105%) для JSON. Далее 20 → 30: +873 ms (50%), +922 ms (50%), +897 ms (61%).

**Осторожно:** при 20 и 30 потоках путь через Security Server оказался быстрее прямого. Это значит, что разброс стенда превышает измеряемый эффект, и брать эти 56–319 ms как «оверхед Security Server» нельзя.

### 1.4 Стоимость надстройки поверх X-Road — **И**, но не про механизмы X-Road

[XATF (Sokolov, 2026)](./XATF_A_Carrier-Binding_Verification_Profile_with_Typed_Failure_Attribution_for_AI-Agent_Evidence_over_X-Road.pdf). Статус публикации спорный, см. раздел 7 в `literature_summary.md`.

- Offline-верификация пакета доказательств: медиана **18.296 ms** (IQR 9.386) на accept-path, **18.316 ms** (IQR 9.296) на reject-path; 50 прогревов + 1000 измерений. Железо не указано.
- Размер запроса через X-Road: **289 B** (только хеш), **352 B** (URI + хеш), **23 360 B** (весь пакет в base64).
- Размер пакета AEP: в среднем **17 587 B** (от 16 779 до 17 971).
- Baseline «только проверка подписей» принимает **11 из 18** строго негативных кейсов; два независимых верификатора совпали 18/18.
- Задержка самого обмена через Security Server, OCSP, timestamping и подпись здесь **не измерялись**.

## 2. Параметры конфигурации — **П**

### 2.1 Значения по умолчанию

[P. Kivimäki, *Resisting Failure*, блог NIIS, 20.11.2020](https://www.niis.org/blog/2020/11/20/resisting-failure) (цитируется как [20] в [ARES 2023](./A%20Decentralised%20Public%20Key%20Infrastructure%20for%20X-Road.pdf))

| Параметр | Значение |
|---|---|
| Обновление глобальной конфигурации на Security Server | каждые 60 с |
| Срок действия глобальной конфигурации | 10 мин (Central Server может лежать до 9 мин) |
| Интервал получения OCSP-ответов | 20 мин; при сбое попытка раз в минуту |
| Пакетный timestamping | раз в минуту |
| Допустимый простой TSA | 4 ч; при сбое попытка раз в минуту |
| Синхронный timestamping | добавляет 4 операции timestamping к сквозному времени обработки |

### 2.2 Значения в эстонском проде, 2017

[Mironova 2017](./Mironova_2017_X-tee_kesksete_teenuste_testimine.pdf)

| Параметр | Прод | В тестах работы |
|---|---|---|
| Срок действия глобальной конфигурации | **6 часов** | 10 мин (значение по умолчанию) |
| `ocspFreshnessSeconds` | **8 часов** (28 800 с) | 600 с |
| `acceptable-timestamp-failure-period` | **4 часа** (14 400 с), оно же по умолчанию | 600 с |
| Максимальный простой центральных сервисов по SLA | 6 часов | — |
| Восстановление минимального набора компонентов Central Server | ≈ 1 час | — |

Поведение при отказе TSA: при `acceptable-timestamp-failure-period` = 0 и выключенной службе меток Security Server продолжает обрабатывать запросы (целостность обеспечивается лишь частично); при INT_MAX запросы проходят, только если служба меток сконфигурирована в самом Security Server.

### 2.3 Криптография X-Road 7.6.2 (что именно стоит в каждом механизме)

[Migration of X-Road to PQC (NIIS, 2026)](./REPORT_Migration_of_X-Road_to_Post-Quantum_Cryptography.FINAL.pdf) — инвентаризация 27 криптоактивов: 9 для данных в передаче, 12 для данных в хранении, 6 для конфигурации. Таблица по механизмам — в разделе 2 файла `literature_summary.md`.

Ключевое для расчётов: sign key RSA-2048 (по умолчанию) или secp256r1, хеш SHA-256; auth key для TLS между Security Server такой же; глобальная конфигурация rsa-sha512; message log AES-128-CTR + hash chain.

## 3. Бенчмарки криптопримитивов — **Б**

[Integrating post-quantum cryptography to UXP (Cybernetica, 2023), Table 2](./PQC_UXP_report_8c97d91552.pdf)

Уровень стойкости NIST 5, Intel Xeon Platinum 8259CL @ 2.50 ГГц, замеры Open Quantum Safe.

| Схема | Размеры, байт | Операций в секунду |
|---|---|---|
| Kyber1024 (KEM) | pk 1 568, sk 3 168, ct 1 568 | gen 36 949, encaps 32 358, decaps 41 786 |
| FrodoKEM-1344-SHAKE | pk 21 520, sk 43 088, ct 21 632 | gen 205, encaps 190, decaps 193 |
| Classic McEliece-8192128 | pk 1 357 824, sk 14 120, ct 240 | gen 1.47, encaps 14 102, decaps 6 723 |
| Dilithium5 | pk 2 592, sk 4 864, sig 4 595 | gen 9 991, sign 5 224, ver 10 612 |
| Falcon-1024 | pk 1 793, sk 13 953, sig 1 280 | gen 39, sign 1 403, ver 8 672 |
| SPHINCS+-256f | pk 64, sk 128, sig 49 856 | gen 226, sign 10.66, ver 226 |
| SPHINCS+-256s | pk 64, sk 128, sig 29 792 | gen 13.82, sign 1.13, ver 439 |

Для сравнения с нынешним X-Road: подпись RSA-2048 — 256 байт, secp256r1 — около 64–72 байт в DER. Это не из файлов, это арифметика по длине ключа; если пойдёт в текст, сослаться на RFC.

Цифры из [отчёта NIIS](./REPORT_Migration_of_X-Road_to_Post-Quantum_Cryptography.FINAL.pdf), все взяты из чужих работ:
- ключ ML-KEM **1 568 байт** против **64 байт** у X25519 (ссылка на Cloudflare) — это pk Kyber1024, то есть уровень 5, а не AES-128, как написано в отчёте;
- AES-128 против квантового противника ≈ 106 бит стойкости;
- для взлома ECC нужно примерно в 10 раз больше квантовой памяти, чем для RSA.

## 6. Чего в цифрах нет

- Разложения задержки X-Road по механизмам: TLS-handshake между Security Server, подпись, проверка подписи, проверка OCSP, timestamping, запись в message log. Нигде.
- Ни одного замера с реальной сетью между Security Server: у IJIS всё в Docker на одном ноутбуке, у Taklai доминирует время БД.
- Размера сообщения X-Road по частям (SOAP/REST-конверт, подпись, hash chain, заголовки) — только размеры примитивов отдельно.
- Пропускной способности Security Server в сообщениях в секунду на известном железе. Ближайшее — оценка 14 сообщений/с как пик всей системы в 2013 году.
- Сравнения синхронного и пакетного timestamping по задержке. Механизм описан (источники 6, 11 и блог NIIS), цифр нет.
- Baseline классического X-Road, с которым можно сравнивать PQC, DPKI и пороговые подписи.
