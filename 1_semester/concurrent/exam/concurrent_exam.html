Терминология

  • Concurrent — общий термин, охватывает parallel и distributed (терминология не 100% единая). Несколько действий "в процессе" одновременно, но не обязательно в один момент времени: может достигаться через time slices (разделение времени). Выглядит одновременно, но на деле нет. Пример: X на Linux запускает несколько приложений на одноядерном процессоре.
  • Parallel — несколько процессов выполняются действительно одновременно. Нужна аппаратная поддержка (multi-core). При правильном программировании — ускорение.
  • Distributed computing — несколько компьютеров, общаются сообщениями (message passing); компьютеры и процессы работают параллельно. В курсе: одна общая задача на нескольких машинах. Client-server веб (servlets + JavaScript) — формально тоже distributed, но не фокус курса. Архитектуры: peer-to-peer, client-server и др.
  • Иерархия: concurrent ⊃ parallel, distributed ("You will find different views on this!").
  • Distributed менее tightly coupled ⇒ можно собрать больше ресурсов, но программировать сложнее.
  • Параллелизм в реальном мире — "больше того же самого" (стройка, конвейеры), а не специализация труда.

Законы ускорения

Amdahl's law — теоретическое ускорение при распараллеливании части кода, p = доля параллелизуемого кода:

  • при бесконечном числе процессов: speedup = 1 / (1 − p)
  • с N процессами: speedup = 1 / ((1 − p) + p/N)
  • накладные расходы (overheads) не учитываются.
  • Ускорение ограничено последовательной частью: speedup ≤ 1/(1−p). Если половина кода последовательна — время сокращается максимум на 50% (speedup ≤ 2).

Таблица (speedup):

N \ p 0.5 0.9 0.95 0.99
10 1.82 5.26 6.89 9.17
100 1.98 9.17 16.80 50.25
1 000 1.99 9.91 19.62 90.99
100 000 1.99 9.99 19.99 99.90
  • Хорошая новость: последовательная часть часто мала и уменьшается с ростом задачи — инициализация/I/O константны или линейны, а сам алгоритм (параллелизуемая часть) может быть полиномиальным или хуже.

Gustafson's law (Gustafson–Barsis) — последовательная часть считается константой: speedup = s + p·N (s — последовательная доля, p — параллельная).

  • Почти линейный рост. Смысл: не "ту же задачу быстрее", а больше данных за то же время ⇒ параллелизация делает задачи scalable.

Speedup:

  • speedup in latency = time_old / time_new (в 2 раза быстрее ⇒ speedup 2).
  • speedup in throughput — относится к числу CPU-инструкций.
  • Обычно ограничен числом процессоров, но бывают (редко) super-linear speedup.

Flynn's taxonomy

Single Data Multiple Data
Single Instruction SISD SIMD
Multiple Instruction MISD MIMD
  • SISD — один поток инструкций, один поток данных за такт. Старые ПК.
  • SIMD — все процессорные элементы выполняют одну и ту же инструкцию за такт над разными данными. Для регулярных задач. GPU, vector machines (суперкомпьютеры 1980-х, Cray X-MP 1982), signal processing (часто на FPGA).
  • MISD — несколько потоков инструкций над одним потоком данных. Редко на практике. Pipelining можно считать MISD: инструкция разбита на фазы, на каждом такте выполняются разные фазы нескольких команд.
  • MIMD — каждый процессор свой поток инструкций и свои данные. Большинство современных компьютеров: кластеры, grid, multi-core ПК.

Модели памяти в MIMD

  • Shared memory — все процессоры имеют прямой доступ к общей физической памяти. Типично для multi-core. Обычно тип SMP (Symmetric Multi-Processor): единое адресное пространство, равный доступ, равная скорость (кроме кэшей — но ими управляют автоматически).
    • UMA (uniform memory access) — одинаковая стоимость доступа ко всей памяти.
    • NUMA — стоимость доступа разная (но доступ всё ещё прямой). Стало распространено с AMD Opteron и Intel Nehalem.
    • PRAM (Parallel Random Access Machine) — "идеальный" shared memory компьютер (UMA) в теории.
  • Distributed memory — процесс "видит" только локальную память; чужая — через коммуникацию с другими процессами. Кластеры.
  • Distributed shared memory — и то и другое.
  • Hybrid — кластер с multi-core CPU в каждом узле. Очень распространено.

Pros/cons:

  • Shared memory проще в обращении, но может вызывать race conditions.
  • Distributed memory заставляет тщательнее проектировать алгоритм.
  • Distributed memory даёт ёмкости, недостижимые иначе.

SMP — по сути то же, что shared memory system; иногда только системы без кэшей. Asymmetric multiprocessing почти устарел (раньше: один процессор для ОС, другой для приложений).

Massively parallel — строго не определено (как и "supercomputer"); GPU, большие кластеры; иногда только кластеры со специальной interconnect (не ethernet).

Программный уровень

  • ОС: у процессов своя память ⇒ несколько процессов образуют distributed memory систему (на слайде опечатка "shared"; по смыслу — процессы изолированы).
  • Threads share memory ⇒ несколько потоков = shared memory система.
  • "Concurrent programming languages" как таковых нет — есть языки, подходящие для определённых видов concurrent программирования. Иногда библиотеки делают язык параллельным (OpenMP, MPI).
  • Языки курса: Java, Python, C++.

Summary слайдов

  • Concurrency — одновременное выполнение программ; parallel и distributed — подтипы.
  • MIMD — типичная модель сегодня; SIMD — в GPU.
  • Shared vs distributed memory — важнейшее различие.

Карточки (22)
Q: Concurrent vs parallel: в чём разница?
  • Concurrent — несколько действий "в процессе" одновременно, но не обязательно в один момент: может быть через time slices на одном ядре (кажется одновременным).
  • Parallel — действительно одновременно, нужна аппаратная поддержка (multi-core); может дать ускорение.
Q: Что такое distributed computing и какая техника в нём главная?

Несколько компьютеров, которые общаются сообщениями; компьютеры и процессы работают параллельно. Главная техника — message passing. В курсе — одна общая задача на нескольких машинах.

Q: Как соотносятся concurrent, parallel, distributed?

Concurrent — общий термин; parallel и distributed — его подтипы (терминология не вполне единая).

Q: Плюсы и минусы distributed по сравнению с parallel?
  • Менее tightly coupled ⇒ можно собрать больше ресурсов.
  • Но требует больше работы программиста, чтобы эти ресурсы использовать.
Q: Формулы Amdahl's law (без N и с N процессами)?
  • speedup = 1 / (1 − p) (бесконечно много процессов)
  • speedup = 1 / ((1 − p) + p/N)

p — доля параллелизуемого кода, N — число процессов. Overheads не учитываются.

Q: 50% кода последовательно. Каков максимальный speedup по Amdahl?

1/(1−0.5) = 2 — время можно сократить максимум на 50%, сколько бы процессоров ни было.

Q: p = 0.9, N = 10. Speedup по Amdahl?

1 / (0.1 + 0.9/10) = 1/0.19 ≈ 5.26. Верхний предел при N→∞ — 10.

Q: Почему Amdahl's law на практике не так пессимистичен?

Последовательная часть (инициализация, I/O) часто мала и константна/линейна по размеру задачи, а параллельная (сам алгоритм) — полиномиальна или хуже ⇒ с ростом задачи доля последовательной части уменьшается.

Q: Gustafson's law: формула и смысл. Отличие от Amdahl?

speedup = s + p·N — последовательная часть считается константой ⇒ почти линейный рост.

  • Amdahl: фиксированная задача — насколько быстрее.
  • Gustafson: фиксированное время — сколько больше данных обработаем ⇒ параллелизация делает задачи scalable.
Q: Speedup in latency vs speedup in throughput? Бывает ли super-linear speedup?
  • Latency: time_old / time_new.
  • Throughput: относится к числу CPU-инструкций (за время).
  • Super-linear speedup (больше числа процессоров) — бывает, но редко.
Q: Назовите 4 класса Flynn's taxonomy.

SISD, SIMD, MISD, MIMD — Single/Multiple Instruction stream × Single/Multiple Data stream.

Q: Что такое SIMD и где применяется?

Все процессорные элементы выполняют одну и ту же инструкцию за такт над разными элементами данных. Для регулярных задач. GPU, vector machines (Cray X-MP, 1980-е), signal processing (FPGA).

Q: Что такое MISD и какой пример можно привести?

Несколько потоков инструкций над одним потоком данных. Редко на практике. Pipelining можно считать MISD: инструкции разбиты на фазы, за такт выполняются разные фазы нескольких команд.

Q: Какая модель Flynn типична для современных компьютеров?

MIMD — кластеры, grid, multi-core ПК (каждый процессор — свой поток инструкций и свои данные). GPU — SIMD.

Q: Shared memory vs distributed memory (в MIMD)?
  • Shared: все процессоры имеют прямой доступ к общей физической памяти (multi-core). Проще, но возможны race conditions.
  • Distributed: процесс видит только свою память, остальное — через коммуникацию (кластеры). Требует более тщательного дизайна алгоритма, но даёт ёмкость, недостижимую иначе.
  • Также distributed shared memory и hybrid (кластер из multi-core узлов).
Q: UMA vs NUMA?
  • UMA — одинаковая стоимость доступа ко всей памяти.
  • NUMA — стоимость доступа разная (но доступ прямой). Распространилось с AMD Opteron / Intel Nehalem.
Q: Что такое SMP?

Symmetric Multi-Processor: единое адресное пространство, равный доступ, равная скорость — по сути shared memory система (кэши — исключение, но управляются автоматически). Asymmetric multiprocessing почти устарел.

Q: Что такое PRAM?

Parallel Random Access Machine — "идеальный" shared memory компьютер (UMA) в теоретических работах.

Q: Что такое hybrid system?

Система с shared и distributed памятью одновременно, напр. кластер, где в каждом узле multi-core CPU. Очень распространено.

Q: Processes vs threads с точки зрения памяти?
  • У процессов ОС своя память (изолированы).
  • Threads делят память процесса ⇒ несколько потоков образуют shared memory систему.
Q: Существуют ли "concurrent programming languages"?

По слайдам — строго говоря нет: есть языки, более или менее подходящие для определённых видов concurrent программирования. Иногда параллельным язык делают библиотеки (OpenMP, MPI).

Q: Что значит "massively parallel"?

Строго не определено (как и supercomputer); меняется со временем. GPU, большие кластеры/grid; иногда только кластеры со специальной interconnect (не ethernet).

Идея

  • Алгоритм — "конечная последовательность строгих инструкций" ⇒ мышление об алгоритмах обычно последовательное.
  • Чтобы использовать параллельные компьютеры, алгоритм должен быть параллельным; иногда это легко, часто — нет. Реализация на конкретном языке — следующий шаг.
  • Различать: problem (найти простые 2..n) → algorithm (Sieve of Eratosthenes, другие) → implementation (serial, parallel...). Реализации отличаются структурами данных, управляющими конструкциями.

Пример: Sieve of Eratosthenes

Последовательный псевдокод:

A[2..n] = true
for i = 2,3,... not exceeding n:
    if A[i]:
        for j = i², i²+i, i²+2i, ... ≤ n: A[j] = false
return all i with A[i] true
  • Даже "let A be an array ... initially all set to true" неявно последовательно — это про реализацию?
  • C-реализация: malloc, проверка NULL, цикл инициализации, внешний цикл до sqrt(N), внутренний — помечает кратные.

Что можно распараллелить:

  • malloc/инициализацию/проверку NULL — трудно.
  • Инициализацию списка нулями — можно (вопрос, стоит ли).
  • Пометка кратных: "каждое число параллельно" — проблема: следующее число для вычёркивания известно только после вычёркивания предыдущим (зависимость).
  • Альтернатива — разбить данные на chunks; вычёркивание одного и того же числа параллельно в каждом chunk; нужна коммуникация, чтобы найти следующее число.
  • Общая стратегия: один процесс делает 2..sqrt(N), остальные — оставшиеся числа ⇒ меньше коммуникации.

Shared memory вариант:

Thread 0: if A[i] true → Broadcast i to other threads; cross out multiples
Thread > 0: in its block, cross out all multiples of i
  • Один массив; thread 0 делает 2..sqrt(n) и рассылает (broadcast) каждое простое; в конце в массиве остаются только простые.
  • Для части 2..sqrt(n) ускорения нет; для остального — зависит от числа процессоров ("немного как в Amdahl's law").

Distributed memory вариант:

  • Единой структуры данных нет.
  • Каждый процесс сам делает часть 2..sqrt(n) (массив A) и вычёркивает в своём сегменте B = (L, H]; затем отправляет B процессу 0, который объединяет.
  • Дублирование 2..sqrt(n) кажется неэффективным, но всё идёт параллельно и экономит коммуникацию.
  • Разбиение sqrt(n)+1..n: равные chunks хороши, если процессы равной мощности; блоками или interleaving chunks; обработать случай, когда деление "не ровное".

Foster's Methodology (Ian Foster, 1995)

Четыре шага: Partitioning → Communication → Agglomeration → Mapping (PCAM). Полезные шаги, но не механический рецепт.

1. Partitioning

  • Domain decomposition — разбить данные на много мелких одинаковых кусков; найти самый большой/часто используемый объект данных, разбить его, каждому куску — primitive task. Пример: трансформация 3D-объекта по пикселю. Идеально для data parallelism.
  • Functional decomposition — разбить функции на отдельные задачи, применяемые к части или всем данным. Пример: обработка аудио тремя разными операциями на разном железе над одними данными. Для functional parallelism.
  • Критерии:
    • задач хотя бы на порядок больше, чем процессоров (гибкость);
    • избегать избыточных вычислений и хранения;
    • primitive tasks примерно одного размера (иначе дисбаланс);
    • число задач — возрастающая функция размера задачи (рост задачи ⇒ больше задач, а не крупнее);
    • рассмотреть несколько альтернативных разбиений (и domain, и functional).

2. Communication

  • Какая коммуникация нужна? Local (несколько задач) или global (все)? Есть ли паттерн (сетка: клетка общается с соседями)?
  • Критерии: все задачи делают примерно одинаковое число коммуникаций; каждая общается с малым числом соседей; коммуникации могут идти concurrently; задачи могут вычислять concurrently.

3. Agglomeration

  • До этого: много задач и (в distributed) много коммуникаций, без привязки к системе.
  • Объединяем 2+ задачи в более крупные ⇒ меньше задач, больше размер, лучше производительность, проще код. Tradeoff.
  • Критерии: уменьшить коммуникацию за счёт locality; дублирование вычислений/данных должно окупаться и не ломать scalability; задачи с похожей стоимостью вычислений/коммуникации; число задач всё ещё растёт с размером задачи; достаточно concurrency для текущих и будущих машин; меньше задач нельзя без дисбаланса; разумная цена модификации существующего последовательного кода.

4. Mapping

  • Назначение задач процессорам; может быть не нужно, если делается автоматически.
  • Цель — минимизировать время выполнения ⇒ максимизировать загрузку процессоров; часто общающиеся задачи — с низкой стоимостью коммуникации; load balancing алгоритмы.
  • Критерии: рассмотрены варианты one task per processor и multiple tasks per processor; static и dynamic распределение; при centralized load balancing — менеджер не bottleneck; при dynamic — оценены издержки стратегий.

Прочее

  • Embarrassingly parallel — легко распараллеливаемые задачи: независимые поиски (биоинформатика, BLAST), фракталы (Mandelbrot — каждый пиксель независим).
  • Проблемы concurrent программ: starvation, race conditions, deadlocks (подробно — в лекциях по языкам).
  • Все ли задачи решаются быстрее параллельно? Зависит от определения. Вероятно, все алгоритмы распараллеливаемы, но не все хорошо. Класс NC — задачи, решаемые за полилогарифмическое время на параллельном компьютере с полиномиальным числом процессоров. Вопрос P = NC открыт.

Parallel modelling (process calculi)

  • CCS (Calculus of Communicating Systems), Robin Milner. Конкурент — CSP (Hoare). Моделирует компоненты, их наблюдаемое поведение и взаимодействие.
  • Пример: спецификация A := a.b.A (бесконечно a, затем b). Компоненты B := a.B, C := b.C; (B | C) — a и b в неопределённом порядке (не соответствует спецификации).
  • С обменом сообщениями (без shared memory): B' := c.d.b.B', C' := c.a.d.C', A' := (B' | C')\{c,d} — синхронизация по c, затем a, затем по d, затем b. Можно формально доказать A == A'. \{c,d} — restriction (скрытие каналов).
  • CSP — вдохновил Go; реализации pyCSP, js-csp, CSP for Java. Именованные каналы: query!i (отправка) и query?i (приём) по каналу query. Есть операторы parallel, choice, restriction. Есть и CCS с value passing.
  • Диаграммы (Foster): базовые действия задачи — read/write local memory, send message, receive message, create new tasks (suspending until they terminate), terminate. Всё ad hoc, стандарта нет.

Summary

  • Большинство алгоритмов сформулированы последовательно.
  • Foster: partitioning, communication, agglomeration, mapping.
  • Можно ли полезно распараллелить все алгоритмы — открытый вопрос.

Карточки (21)
Q: Problem vs algorithm vs implementation — в чём разница (на примере простых чисел)?
  • Problem: найти все простые от 2 до n.
  • Algorithm: Sieve of Eratosthenes (или другие).
  • Implementation: serial / parallel — отличаются структурами данных и управляющими конструкциями.
Q: Почему нельзя наивно распараллелить решето, вычёркивая кратные каждого числа в отдельном потоке?

Следующее число, кратные которого нужно вычёркивать, известно только после вычёркивания кратных предыдущего — зависимость между шагами.

Q: Какую стратегию распараллеливания решета предлагают для shared memory?

Один массив. Thread 0 обрабатывает 2..sqrt(n) и broadcast'ит каждое найденное простое остальным; потоки > 0 вычёркивают кратные в своём блоке. Для части 2..sqrt(n) ускорения нет (как в Amdahl's law).

Q: Как решето делается в distributed memory? Почему дублирование не страшно?

Каждый процесс сам вычисляет простые 2..sqrt(n) (массив A) и вычёркивает кратные в своём сегменте B = (L, H]; затем шлёт B процессу 0, который объединяет. Дублирование идёт параллельно и экономит коммуникацию.

Q: Как можно делить числа sqrt(n)+1..n между процессами?

Равные chunks (если процессоры одинаково мощные); блоками или interleaving; нужно обработать случай, когда деление не ровное.

Q: Назовите 4 шага Foster's methodology.

Partitioning, Communication, Agglomeration, Mapping (PCAM). Полезные шаги, но не механический рецепт.

Q: Domain decomposition vs functional decomposition?
  • Domain: делим данные на много мелких одинаковых кусков (самый большой/частый объект данных), каждому — primitive task. ⇒ data parallelism (пример: обработка 3D-объекта по пикселю).
  • Functional: делим функции на отдельные задачи, применяемые к данным. ⇒ functional parallelism (пример: три разные операции над аудиосигналом на разном железе).
Q: Критерии хорошего partitioning?
  • Задач хотя бы на порядок больше, чем процессоров.
  • Нет избыточных вычислений/хранения.
  • Primitive tasks примерно одного размера.
  • Число задач растёт с размером задачи (а не размер задач).
  • Рассмотрено несколько альтернатив (domain и functional).
Q: Какие вопросы задаются на шаге Communication и каковы критерии?

Какая коммуникация нужна; local или global; есть ли паттерн (сетка/соседи). Критерии: сбалансированное число коммуникаций у задач; общение с малым числом соседей; коммуникации и вычисления могут идти concurrently.

Q: Что делается на шаге Agglomeration и зачем?

Объединяем 2+ задачи в более крупные ⇒ меньше задач, меньше коммуникации (больше locality), проще код, лучше производительность. Это tradeoff: должно оставаться достаточно concurrency и масштабируемость с размером задачи.

Q: Что такое Mapping и его цель?

Назначение задач процессорам (может делаться автоматически). Цель — минимизировать время, т.е. максимизировать загрузку процессоров; часто общающиеся задачи — с дешёвой коммуникацией; load balancing.

Q: Критерии mapping?
  • Рассмотрены one task per processor и multiple tasks per processor.
  • Рассмотрены static и dynamic распределение.
  • Centralized load balancing — менеджер не bottleneck.
  • Dynamic — оценены издержки стратегий.
Q: В каком шаге Foster код начинает учитывать конкретную машину?

Partitioning и communication — машинно-независимы; в agglomeration задачи укрупняются под производительность реальной системы, mapping назначает их процессорам.

Q: Что такое embarrassingly parallel? Примеры.

Задачи, которые легко распараллелить (независимые части). Независимые поиски (биоинформатика, BLAST), фракталы (Mandelbrot — каждый пиксель независимо).

Q: Какие проблемы concurrent программ упоминаются как то, чего надо избегать?

Starvation, race conditions, deadlocks.

Q: Все ли задачи можно эффективно распараллелить? Что такое NC?

Вероятно, все алгоритмы распараллеливаемы, но не все хорошо. NC — задачи, решаемые за полилогарифмическое время на параллельном компьютере с полиномиальным числом процессоров. P = NC? — открытый вопрос.

Q: Что такое CCS и CSP?

Process calculi для моделирования параллельных/распределённых систем: компоненты, их наблюдаемое поведение и взаимодействие.

  • CCS — Calculus of Communicating Systems (Robin Milner).
  • CSP — Communicating Sequential Processes (Hoare); вдохновил Go; реализации pyCSP, js-csp, CSP for Java.
Q: CCS: A := a.b.A; B := a.B; C := b.C. Реализует ли (B | C) спецификацию A?

Нет: (B | C) выполняет a и b в неопределённом порядке, а A требует строго a, b, a, b...

Q: Как в CCS заставить B и C чередовать a и b (без shared memory)?

Синхронизация через каналы: B' := c.d.b.B', C' := c.a.d.C', A' := (B' | C')\{c,d}. Синхронизируются на c → a → на d → b → заново. \{c,d} скрывает (restriction) каналы. Формально можно доказать A == A'.

Q: Что означают query!i и query?i в CSP?

Отправка (!) и приём (?) значения i по именованному каналу query — процессы A = query!i и B = query?i обмениваются i.

Q: Какие 4 базовых действия задачи в модели Foster (диаграммы)?

Помимо чтения/записи локальной памяти: send message, receive message, create new tasks (suspend до их завершения), terminate. Диаграммы ad hoc — стандарта нет.

Лекция 04: Concurrency in Java — Basics, processes, threads, object monitors, memory model

Выжимка

Слайды: session4.pdf; код: code\session4lecturecode\lecture4\src\concurrent4\ (Thread1–4, CounterMain, TestList, BusyWaitingApp/Producer/Consumer)

Модель

  • Java поддерживает concurrency с самого начала. Модель shared memory: Java-процесс запускает несколько потоков, которые разделяют память процесса (но не других процессов).

Process vs Thread

  • Process — запущенная программа (одна программа может быть запущена несколько раз). Имеет свою память и ресурсы, процессы изолированы, управляет ОС. В multi-tasking ОС планирует процессы по ядрам и time slices (pre-emptive multi-tasking).
  • Thread — поток внутри процесса. Разделяют память (heap), но у каждого свой program counter, stack, local variables. Пример пользы: текстовый редактор не блокируется во время подготовки к печати.
  • Java использует потоки ОС (с Java 1.2; до этого — "green threads").
  • Обычная программа: поток main (Thread.currentThread().getName() → main), но ps -eLf показывает много потоков — их создаёт JVM.

Создание потоков

// 1) extends Thread, override run()
class MyThread extends Thread {
    @Override public void run() { System.out.println("thread in run"); }
}
Thread t = new MyThread();
t.start();   // НЕ run()!
t.join();    // main ждёт завершения t

// 2) implements Runnable — можно ещё наследовать свой класс
Thread t = new Thread(new MyRunnable()); t.start();

// 3) anonymous class (join невозможен — нет ссылки)
new Thread() { public void run() { ... } }.start();

// 4) lambda (Java 8)
Runnable r = () -> { ... };
new Thread(r).start();
new Thread(() -> doWork()).start();
  • start() делает поток готовым к запуску; когда реально выполнится run() — решает ОС (на ПК обычно сразу на свободном ядре). Вызов run() напрямую выполнит код в текущем потоке — нового потока не будет.
  • join() — вызывающий поток переходит в waiting до завершения другого потока.
  • Thread.sleep(ms) бросает checked InterruptedException — надо ловить или пробрасывать.

Thread states (диаграмма Baeldung)

  • New → start() → Runnable (внутри: Ready to Run ⇄ Running — scheduled/suspended) → exit → Terminated.
  • Timed Waiting: sleep(time), wait(timeout), join(timeout), parkNanos, parkUntil → назад по истечении времени или notify()/notifyAll().
  • Waiting: wait(), join(), park() → назад по notify()/notifyAll() (или завершению потока для join).
  • Blocked: ожидание object monitor (вход в synchronized) → назад, когда monitor lock получен.

Non-determinism

  • Thread3: main и поток печатают по 4 строки с sleep(100) — порядок разный от запуска к запуску. Non-determinism — важный "побочный эффект" concurrency, сильно усложняет программирование.

Race condition и synchronized

CounterMain: 4 потока × 10 000 ++count на общем Counter ⇒ результат например 37014 вместо 40000.

  • ++count не атомарен: read–modify–write, т.е. newvar = count + 1; count = newvar; — выполнения потоков "перекрываются", инкременты теряются (lost update).
  • Race condition — результат программы зависит от порядка выполнения инструкций (расписания), который мы не контролируем.
  • (Общие термины, кратко) Atomic операция — выполняется целиком, другие потоки не видят промежуточного состояния. Critical section — участок кода с доступом к общим данным, который одновременно должен выполнять только один поток. Mutual exclusion — гарантия этого (synchronized, Lock).
public synchronized void incrementCount() { ++count; }   // 40000
// или блок с явным monitor object:
public void incrementCount() { synchronized (this) { ++count; } }
  • synchronized: только один поток на monitor object может выполнять блок. Synchronized-метод неявно использует this (для static — объект класса).
  • Поток, не получивший monitor, переходит в состояние Blocked.
  • synchronized имеет небольшой overhead, но при сомнениях лучше использовать — проблемы бывают совсем неочевидны.
  • Code reordering (слайд 21): a=2, flg=false; Thread1: a = 1; flg = true; Thread2: if (flg) println(a); — может напечатать a = 2: компилятор/CPU могут переставить записи, а без синхронизации нет гарантии видимости.
  • Замечание (код): в CounterMain getCount() не synchronized — работает, т.к. читается после join() (join даёт видимость).

Explicit locking

private Lock myLock = new ReentrantLock();
public void methodToSynchronize() {
    myLock.lock();
    try { /* work */ } finally { myLock.unlock(); }   // на слайде без try/finally; finally — хорошая практика
}
  • Преимущества: настройка fairness policy (new ReentrantLock(true)), tryLock (с таймаутом — лекция 06). Но synchronized используется намного чаще.

Thread safety коллекций

  • Стандартные коллекции (ArrayList, HashMap...) не thread-safe — могут прийти в несогласованное состояние. Исключения: старые Vector и Hashtable.
  • TestList: 2 потока добавляют по 100 элементов в общий ArrayList ⇒ "всякие неожиданные результаты" (размер < 200, null-элементы, ArrayIndexOutOfBoundsException). Причина: при переполнении внутреннего массива создаётся новый, содержимое копируется, затем добавляется элемент — операция не атомарна.
  • Решения:
    • synchronized wrapper: List<String> safeList = Collections.synchronizedList(new ArrayList<>());
    • thread-safe коллекции из java.util.concurrent (разные реализации со своими плюсами; напр. ConcurrentHashMap, CopyOnWriteArrayList). Wrapper обычно менее эффективен.

Busy waiting, wait/notify

  • Busy waiting тратит CPU без пользы. BusyWaitingApp: Consumer крутит while (producer.isBusy()) print(...) пока Producer генерирует UUID; isBusy — volatile (иначе Consumer мог бы не увидеть изменение).
  • Избегать циклов ожидания другого потока. wait() переводит поток в Waiting, будится notify() / notifyAll() — гораздо экономнее.
  • sleep() похож, но не освобождает lock; wait() освобождает monitor.
  • (Уточнение API) wait/notify вызываются только внутри synchronized на том же объекте, иначе IllegalMonitorStateException; wait() принято вызывать в цикле while (!condition) wait(); (spurious wakeups).
synchronized (lock) { while (!ready) lock.wait(); /* use */ }
synchronized (lock) { ready = true; lock.notifyAll(); }

Java Memory Model

  • Память процесса общая для процесса, но у потоков есть свои области — память доступа и visibility переменных — не одно и то же.
  • Stack (у каждого потока): информация о выполняемом коде и локальные примитивные переменные; ссылки на объекты — тоже локальны.
  • Heap: все объекты, включая примитивные поля объектов. Любой поток, имеющий ссылку, может обратиться к объекту. Программа не управляет heap/stack.
  • Hardware: данные могут быть в регистрах, кэшах, RAM ⇒ проблема: переменная обновлена в кэше одного CPU, а другой поток на другом CPU читает старое значение из RAM.
  • volatile — переменная всегда читается/пишется из/в RAM ⇒ согласованность (visibility). Не даёт mutual exclusion (volatile int count; count++ — всё ещё race).
  • synchronized — и visibility, и mutual exclusion.
  • Atomic variables (AtomicInteger и др., java.util.concurrent.atomic) — visibility + атомарные операции (incrementAndGet(), compareAndSet()).
  • (Уточнение, не на слайдах) формально это описывается отношением happens-before: unlock монитора → последующий lock того же монитора; запись volatile → последующее чтение; start() → действия потока; действия потока → успешный join().

Обмен данными между потоками

  • Передать данные через конструктор (примитивы передаются по значению).
  • Метод, возвращающий результат, вызываемый стартером после завершения потока:
public class Foo implements Runnable {
    private volatile int value;
    public void run() { value = 2; }
    public int getValue() { return value; }
}
Foo foo = new Foo(); Thread th = new Thread(foo);
th.start(); th.join(); int v = foo.getValue();
  • Элегантнее — futures/promises (лекции 05–06).

Conclusion

  • Потоки: Thread или Runnable. Race conditions контролируются синхронизацией. В многопоточных программах — thread-safe классы. Memory model может давать несогласованность — помогает volatile.

  • sleep(100): Timed Waiting.
Q: main и поток печатают "main 1..4" и "thread in run 1..4" с sleep(100) между строками. Каков вывод?

Non-deterministic: строки каждого потока идут по порядку, но их чередование меняется от запуска к запуску. Это важный "побочный эффект" concurrency.

Q: 4 потока по 10 000 раз делают ++count на общем счётчике без синхронизации. Что напечатается?

Обычно меньше 40000 (напр. 37014): ++count не атомарен (read → +1 → write, т.е. newvar = count+1; count = newvar;), выполнения перекрываются, инкременты теряются. Race condition.

Q: Определение race condition (по слайдам).

Результат программы зависит от порядка (расписания) выполнения инструкций, который мы не контролируем.

Q: Что такое atomic операция и critical section?
  • Atomic — выполняется целиком, другие потоки не видят промежуточного состояния.
  • Critical section — код с доступом к общим данным, который одновременно может выполнять только один поток (mutual exclusion).
Q: Как исправить счётчик? Два варианта с synchronized. 
public synchronized void incrementCount() { ++count; }
// или
public void incrementCount() { synchronized (this) { ++count; } }

Ещё вариант — AtomicInteger.incrementAndGet().

Q: Что гарантирует synchronized? Какой monitor у synchronized-метода?

Только один поток на monitor object выполняет блок + видимость изменений. У instance-метода monitor — this (у static — объект класса). Не получивший monitor поток — Blocked.

Q: Два потока вызывают synchronized-методы m1() и m2() одного объекта. Могут ли они выполняться одновременно? А на разных объектах?

На одном объекте — нет (общий monitor this). На разных объектах — да (разные мониторы).

Q: Стоит ли использовать synchronized, если не уверен, что он нужен?

По слайдам — да: overhead небольшой, а проблемы бывают совсем неочевидны (напр. code reordering).

Q: a=2, flg=false. T1: a = 1; flg = true; T2: if (flg) println(a);. Что может напечатать T2?

Ничего, 1 или даже 2 — без синхронизации записи могут быть переупорядочены (code reordering) и/или не видны другому потоку. Решение: synchronized или volatile flg.

Q: ReentrantLock: как использовать и чем лучше synchronized? 
Lock lock = new ReentrantLock();
lock.lock();
try { ... } finally { lock.unlock(); }

Преимущества: настраиваемая fairness policy (new ReentrantLock(true)), tryLock с таймаутом. Но synchronized используется гораздо чаще.

Q: Что не так с myLock.lock(); doWork(); myLock.unlock();?

Если doWork() бросит исключение, unlock() не выполнится и lock останется захваченным навсегда. Нужно try { ... } finally { unlock(); }.

Q: Являются ли стандартные коллекции thread-safe?

Нет (ArrayList, HashMap и т.д.). Исключения — старые Vector и Hashtable.

Q: Два потока добавляют по 100 чисел в общий ArrayList. Будет ли в конце 200 элементов?

Не обязательно: возможны меньший размер, null-элементы, ArrayIndexOutOfBoundsException. add не атомарен — при переполнении создаётся новый массив, копируется содержимое, потом добавляется элемент.

Q: Как сделать список безопасным для многопоточности?
  • Collections.synchronizedList(new ArrayList<>()) — synchronized wrapper (обычно менее эффективен).
  • Thread-safe коллекции из java.util.concurrent (напр. CopyOnWriteArrayList, ConcurrentHashMap).
Q: Что такое busy waiting и почему это плохо? Альтернатива?

Цикл, крутящийся в ожидании другого потока (while (producer.isBusy()) {...}) — тратит CPU без пользы. Альтернатива: wait() (поток в состоянии Waiting) + notify()/notifyAll() из другого потока.

Q: sleep() vs wait()?
  • sleep() — пауза, не освобождает lock; метод Thread.
  • wait() — освобождает monitor и ждёт notify(); метод Object, вызывается только внутри synchronized на том же объекте (иначе IllegalMonitorStateException).
Q: Почему wait() принято вызывать в цикле while, а не в if?

После пробуждения условие может быть снова ложным (другой поток успел изменить состояние, notifyAll разбудил нескольких, spurious wakeup) ⇒ нужно перепроверить: while (!cond) wait();.

Q: Java memory model: что лежит в stack, что в heap?
  • Stack (свой у каждого потока): информация о выполняемом коде, локальные примитивы, локальные ссылки.
  • Heap: все объекты, включая их примитивные поля. Любой поток со ссылкой может обращаться к объекту.
Q: Почему в shared memory системе может возникнуть проблема видимости?

Переменная может жить в регистре/кэше одного CPU: поток обновил её в кэше, а поток на другом CPU читает старое значение из RAM. Доступ к памяти ≠ видимость переменной.

Q: Что гарантирует volatile и чего не гарантирует?
  • Гарантирует visibility: всегда читается/пишется из/в основную память.
  • Не даёт mutual exclusion / атомарности: volatile int c; c++; — всё ещё race condition.
Q: volatile vs synchronized vs atomic variables?
  • volatile — только visibility.
  • synchronized — visibility + mutual exclusion.
  • Atomic (AtomicInteger...) — visibility + атомарные операции (incrementAndGet, compareAndSet) без блокировок.
Q: Зачем private volatile boolean isBusy в Producer (BusyWaitingApp)?

Consumer в цикле читает isBusy, Producer в другом потоке ставит его в false. Без volatile Consumer может никогда не увидеть изменение (значение закэшировано) и крутиться вечно.

Q: Что такое happens-before (кратко)?

Отношение Java Memory Model: если A happens-before B, то эффекты A видны в B. Примеры: unlock монитора → последующий lock того же монитора; запись volatile → её последующее чтение; start() → действия нового потока; все действия потока → успешный join() на нём.

Q: Как передать данные в поток и получить результат (по слайдам)?
  • Вход — через конструктор (примитивы по значению).
  • Результат — поле + getter, который вызывается после join():
Foo foo = new Foo(); Thread t = new Thread(foo);
t.start(); t.join(); int v = foo.getValue();

Элегантнее — futures/promises.

Q: В CounterMain getCount() не synchronized, а incrementCount() — synchronized. Корректен ли итог?

Да: getCount() вызывается в main после join() всех потоков, а join гарантирует видимость их изменений. Если бы читали во время работы потоков — значение могло бы быть устаревшим.

Q: Что такое "green threads" и с какой версии Java использует потоки ОС?

Green threads — потоки, реализованные самой JVM (до Java 1.2). С Java 1.2 используются потоки ОС.

ExecutorService (Java 1.5, java.util.concurrent)

  • Держит pool of threads и автоматически распределяет задачи по ним.
  • Создаётся через фабрику Executors:
ExecutorService e1 = Executors.newSingleThreadExecutor();   // 1 worker thread, unbounded queue
ExecutorService e2 = Executors.newFixedThreadPool(10);      // фикс. число потоков, shared unbounded queue
ExecutorService e3 = Executors.newScheduledThreadPool(10);  // запуск с задержкой / периодически
// также newCachedThreadPool() и др.
  • Обязательно shutdown() — иначе потенциальная утечка памяти (и JVM может не завершиться).
    • shutdown() — новые задачи не принимаются, уже отправленные доделываются.
    • shutdownNow() — немедленно (прерывает; обычно нежелательно).
  • Задачи — Runnable или Callable.
    • Runnable — тот же интерфейс, что для Thread ⇒ один объект можно запустить как Thread или отдать executor'у. execute(Runnable) — без результата (submit(Runnable) тоже возможен — Future<?> с null).
    • Callable — V call() throws Exception; возвращает результат и может бросать checked exceptions; нельзя напрямую передать в Thread.
public class ExecutorAndCallable implements Callable<String> {
    public String call() throws Exception {
        Thread.sleep(1000);
        return Thread.currentThread().getName();   // напр. "pool-1-thread-1"
    }
}
ExecutorService executor = Executors.newFixedThreadPool(10);
Future<String> future = executor.submit(new ExecutorAndCallable());
System.out.println(new Date() + "::" + future.get());   // get() блокирует до результата
executor.shutdown();
  • Future<V> — тип совпадает с Callable.
  • get() блокирующий ⇒ варианты:
    • таймаут: future.get(200, TimeUnit.MILLISECONDS) (бросит TimeoutException);
    • проверка isDone();
    • отмена cancel(boolean mayInterruptIfRunning).
    • Исключение из call() приходит как ExecutionException при get().
  • invokeAll(Collection<Callable>) — запускает все, возвращает List<Future>; invokeAny(...) — возвращает результат одной успешно завершившейся задачи (остальные отменяются).
  • ExecutorAndRunnable: main печатает дату сразу, имя потока пула — примерно через 1 с; shutdown() не убивает выполняющуюся задачу.

Fork/Join Framework (Java 1.7)

  • Встроенный divide and conquer: fork (divide) и join (conquer) делает фреймворк, но как делить — говорим мы, и до "идеальной" точки (THRESHOLD).
  • ForkJoinPool — ядро. Потоков обычно = числу ядер. Принимает задачи типа ForkJoinTask<V>.
  • Work-stealing:
    • у каждого потока своя double-ended queue (deque); работает над задачами своей очереди;
    • при fork новые задачи кладутся в head своей очереди;
    • если работы нет — крадёт с tail чужой очереди (или берёт из общей (general) очереди пула);
    • такая схема push/steal оптимизирует locality и минимизирует lock contention.
  • Пишут обычно:
    • RecursiveAction — void compute(), ничего не возвращает;
    • RecursiveTask — V compute() возвращает результат.
    • Напрямую ForkJoinTask реализуют редко.
  • compute() либо считает сам (маленькая задача), либо делит.
  • join() ждёт результат подзадачи — это существенно; но он не должен блокировать поток: поток, выполняющий join, остаётся доступен для другой работы.
  • THRESHOLD определяет, сколько будет задач. Фреймворк "старается", но тонкие улучшения балансировки — на программисте (см. класс Applyer в доках RecursiveAction).

RecursiveTask (CustomRecursiveTask):

class CustomRecursiveTask extends RecursiveTask<Integer> {
    private int[] arr; static final int THRESHOLD = 20;
    protected Integer compute() {
        if (arr.length > THRESHOLD)
            return ForkJoinTask.invokeAll(createSubtasks())   // 2 половины через Arrays.copyOfRange
                    .stream().mapToInt(ForkJoinTask::join).sum();
        else
            return Arrays.stream(arr).filter(a -> a > 10 && a < 27).map(a -> a * 10).sum();
    }
}

RecursiveAction (SortTask — merge sort из доков Oracle):

protected void compute() {
    if (hi - lo < THRESHOLD) sortSequentially(lo, hi);   // Arrays.sort
    else {
        int mid = (lo + hi) >>> 1;
        invokeAll(new SortTask(array, lo, mid), new SortTask(array, mid, hi));
        merge(lo, mid, hi);        // <- merge после invokeAll (invokeAll ждёт обе подзадачи)
    }
}
// запуск:
ForkJoinPool pool = ForkJoinPool.commonPool();
pool.execute(action); action.join();      // или pool.invoke(task)
  • "Где merge?" — сразу после invokeAll в той же compute(), на каждом уровне рекурсии.
  • "Почему main — плохой пример?" — массив из 7 элементов < THRESHOLD = 1000 ⇒ просто последовательный Arrays.sort, никакого параллелизма (накладные расходы без пользы).
  • Подзадачи SortTask работают над разными диапазонами одного массива — нет гонок; CustomRecursiveTask копирует половины (проще, но лишняя память).

Bounded Buffer (producer–consumer)

  • Типичная ситуация producer/consumer: cat test.txt | grep "test" — обычно два потока с разной, непостоянной скоростью ⇒ нужен буфер, но не бесконечно растущий.
  • Bounded buffer — буфер с максимальным размером: полный ⇒ producer останавливается, пустой ⇒ consumer останавливается; в промежутке оба заняты.
  • В Java (по слайдам) нет стандартной реализации; вариант — массив + два указателя (start/end, кольцевой буфер) или двусвязный список.
  • Обязан быть thread-safe: минимум 2 потока читают и пишут, может быть несколько producers/consumers.
  • (Уточнение) На практике готовое поведение bounded buffer даёт BlockingQueue (ArrayBlockingQueue(capacity): put() блокирует при полной, take() — при пустой).

Классическая реализация на мониторе:

class BoundedBuffer<T> {
    private final Object[] buf; private int head, tail, count;
    BoundedBuffer(int n) { buf = new Object[n]; }
    public synchronized void put(T x) throws InterruptedException {
        while (count == buf.length) wait();          // full → producer ждёт
        buf[tail] = x; tail = (tail + 1) % buf.length; count++;
        notifyAll();
    }
    public synchronized T take() throws InterruptedException {
        while (count == 0) wait();                   // empty → consumer ждёт
        T x = (T) buf[head]; head = (head + 1) % buf.length; count--;
        notifyAll();
        return x;
    }
}

Semaphores and Mutexes

  • Semaphores и mutexes — конструкции уровня ОС; могут синхронизировать процессы (не только потоки).
  • В Java есть класс Semaphore: инициализируется числом permits; потоки делают acquire(); работает для до x потоков, остальные ждут, пока кто-то сделает release(). Как lock, но пускает больше одного потока в critical section (пример: connection pool).
Semaphore sem = new Semaphore(3);
sem.acquire();
try { useConnection(); } finally { sem.release(); }
  • Mutex (mutual exclusion, "mutex semaphore") — отдельного класса в Java нет; Semaphore(1) делает то же.
  • Lock vs mutex: в Java разницы по сути нет; в C можно иметь system-wide mutex, разделяемый между процессами.
  • (Уточнение) отличие Semaphore от Lock: у семафора нет "владельца" — release может сделать другой поток; ReentrantLock отпускает только владелец и допускает повторный захват тем же потоком.

Summary

  • ExecutorService упрощает выполнение задач. Fork/join ещё и балансирует нагрузку. Mutexes и semaphores — в основном конструкции уровня ОС.

Placeholder для результата асинхронной задачи (тип = тип Callable). get() — блокирует до результата; get(timeout, unit); isDone(); cancel(boolean mayInterruptIfRunning).

Блокирует вызывающий поток до завершения задачи (возможно, надолго). Варианты: get(200, TimeUnit.MILLISECONDS) (TimeoutException), проверять isDone(), отменять cancel(...).

Примерно через 1 с: дата + ::pool-1-thread-1 — задача выполнялась в потоке пула, main ждал в get().

Q: invokeAll vs invokeAny?

Оба принимают коллекцию Callable.

  • invokeAll — выполняет все, возвращает List<Future>.
  • invokeAny — возвращает результат одной успешно завершившейся задачи.
Q: Как сообщается исключение, брошенное внутри call()?

При future.get() оно приходит обёрнутым в ExecutionException (поэтому main в примере throws ExecutionException).

Q: Что такое fork/join framework, с какой версии Java?

Java 1.7. Встроенный divide and conquer: fork (разделить) и join (собрать) выполняет фреймворк, но как делить и до какого порога — задаёт программист.

Q: Сколько потоков у ForkJoinPool и какие задачи он принимает?

Обычно = числу ядер. Принимает ForkJoinTask<V>; на практике — RecursiveAction или RecursiveTask<V>.

Q: Объясните work-stealing.

У каждого потока своя double-ended queue. Поток берёт задачи из своей очереди; при fork новые задачи кладутся в head своей очереди; если своя пуста — крадёт с tail чужой очереди (или из общей очереди пула). Оптимизирует locality и минимизирует lock contention.

Q: RecursiveAction vs RecursiveTask?

Оба переопределяют compute().

  • RecursiveAction — void compute(), без результата (напр. сортировка на месте).
  • RecursiveTask — V compute(), возвращает результат (напр. сумма).
Q: Типичная структура compute()? 
if (size <= THRESHOLD) return computeDirectly();
else { split into subtasks; invokeAll(...) / fork(); combine results via join(); }
Q: В SortTask: где происходит merge?

Сразу после invokeAll(left, right) в той же compute(): invokeAll ждёт обе половины, затем merge(lo, mid, hi). Так на каждом уровне рекурсии.

Q: Почему main в SortTask (массив из 7 элементов, THRESHOLD = 1000) — "не хороший пример"?

7 < 1000 ⇒ сразу sortSequentially (Arrays.sort) — никакого параллелизма, только накладные расходы пула.

Q: Что определяет THRESHOLD и как его выбирать?

Порог, ниже которого задача считается последовательно ⇒ определяет число задач. Слишком мал — огромный overhead на создание задач; слишком велик — мало параллелизма/плохой баланс.

Q: Блокирует ли join() в fork/join поток?

Задача ждёт результат (это необходимо), но join не должен блокировать поток — поток остаётся доступным для другой работы (может выполнять другие задачи, пока ждёт).

Q: Решает ли fork/join всю балансировку нагрузки автоматически?

Нет — фреймворк "старается", но тонкие улучшения (умное деление, как в классе Applyer из доков RecursiveAction) — задача программиста.

Q: Что такое bounded buffer и зачем?

Буфер с максимальным размером между producer и consumer (как cat file | grep x): скорости разные и непостоянны, буфер сглаживает, но не растёт бесконечно. Полный ⇒ producer ждёт; пустой ⇒ consumer ждёт.

Q: Как реализовать bounded buffer и какое требование обязательно?

Массив + два указателя (start/end, кольцевой буфер) или двусвязный список. Обязательно thread-safe (минимум 2 потока, возможно несколько producers/consumers): synchronized + while(full) wait() / while(empty) wait() + notifyAll(). Готовый вариант — ArrayBlockingQueue (put/take).

Q: В bounded buffer используют notify() вместо notifyAll() при нескольких producers и consumers. Чем опасно?

notify будит один произвольный поток — может разбудить "не того" (producer'а, когда буфер полон), тот снова уснёт, а нужный поток не проснётся ⇒ все могут застрять. notifyAll + while-проверка безопаснее.

Q: Что такое Semaphore в Java?

Инициализируется числом permits. acquire() — занять (если нет — ждать), release() — вернуть. Пускает до x потоков одновременно в critical section (пример: connection pool).

Q: Есть ли класс Mutex в Java? Lock vs mutex?

Нет: mutex (mutual exclusion) = Semaphore(1). В Java разницы между lock и mutex по сути нет; в C mutex может быть system-wide, разделяемым между процессами.

Q: Semaphore vs lock — в чём отличие?
  • Semaphore допускает больше одного потока; у него нет владельца (release может сделать другой поток).
  • Lock — ровно один владелец; ReentrantLock отпускает только захвативший поток.
Q: На каком уровне изначально существуют semaphores и mutexes?

На уровне ОС — для синхронизации процессов. В Java-потоках менее актуальны, но существуют.

Сложности concurrency

  • Non-deterministic выполнение — обычное дело.
  • Отладка может менять результат программы — "Heisenbug".

Deadlock

  • Deadlock — поток никогда не завершается (заблокирован навсегда). На практике трудно отличить от очень долгого потока. Обычно возникает при взаимодействии двух и более потоков.
  • (Уточнение, не на слайдах) Классические условия Коффмана — deadlock возможен только если одновременно: (1) mutual exclusion, (2) hold and wait (держит ресурс и ждёт другой), (3) no preemption (ресурс нельзя отнять), (4) circular wait (цикл ожидания). Сломать любое ⇒ deadlock невозможен; единый порядок захвата ломает circular wait.

Классический пример ("crossed" locks):

final String r1 = "deadlock", r2 = "example";
Thread t1 = new Thread() { public void run() {
    synchronized (r2) { System.out.println("Thread 1: Locked r2");
        try { Thread.sleep(100); } catch (InterruptedException e) {}
        synchronized (r1) { System.out.println("Thread 1: Locked r1"); } } } };
Thread t2 = new Thread() { public void run() {
    synchronized (r1) { System.out.println("Thread 2: Locked r1");
        try { Thread.sleep(100); } catch (InterruptedException e) {}
        synchronized (r2) { System.out.println("Thread 2: Locked r2"); } } } };
t1.start(); t2.start();
  • Обычно печатается "Thread 1: Locked r2", "Thread 2: Locked r1" (в любом порядке) и программа виснет.
  • Гарантирован ли deadlock? Нет — если один поток успеет захватить оба монитора до старта второго, всё завершится. sleep(100) делает deadlock практически неизбежным, но не гарантирует.
  • Если поменять порядок захвата так, чтобы оба брали в одном порядке (r1, потом r2) — deadlock невозможен.
  • (Уточнение) синхронизация на строковых литералах — плохая практика: литералы interned, тот же объект может использоваться где угодно.

Рекомендации:

  • Избегать nested synchronization (реальные случаи редки); лучше вообще избегать нескольких синхронизаций в одном потоке.
  • Если нужно — потоки должны брать одни и те же locks в одном порядке.
  • Не делать долгих задач в synchronized-методах, которым синхронизация не нужна.
  • Timeouts: join(timeout); Lock.tryLock(time, unit); для synchronized таймаута нет. Но просто игнорировать проблему может вызвать другие.

Deadlock через synchronized-методы (DeadlockMethod) — обычно не прямо из кода, но можно сконструировать (довольно искусственно):

class A { synchronized void methodA(B b) { b.last(); }  synchronized void last() {...} }
class B { synchronized void methodB(A a) { a.last(); }  synchronized void last() {...} }
// main thread: a.methodA(b)  — держит монитор a, ждёт монитор b (для b.last())
// new thread : b.methodB(a)  — держит монитор b, ждёт монитор a (для a.last())
  • Возможен deadlock (не гарантирован — зависит от тайминга).

Диагностика: jstack, Java Mission Control (JMC), VisualVM, jcmd, jconsole (GUI и CLI); на Linux kill -3 <pid> печатает thread dump; сторонние/коммерческие инструменты. Ищем потоки, заблокированные (BLOCKED) длительное время.

Livelock

  • Livelock — поток никогда не завершается, хотя не заблокирован (активно работает, но без прогресса). Как и deadlock — от неправильного взаимодействия потоков.
  • LivelockWithLocks: два ReentrantLock(true) (fair). T1: берёт lock1, спит 50 мс, lock2.tryLock(); не удалось ⇒ отпускает lock1 и повторяет. T2 симметрично (lock2, затем lock1). Оба "вежливо" уступают и повторяют синхронно ⇒ бесконечно печатают "cannot acquire ..., releasing ...".
    • (Замечание к коду) результат lock1.tryLock(50, ms) игнорируется — если захват не удался, последующий unlock() бросит IllegalMonitorStateException.
    • Лечение (общее): случайная задержка (random backoff) перед повтором, единый порядок захвата.
  • Гораздо чаще на практике: ресурс повторно пытаются получить / ошибочное действие повторяется бесконечно (повторная отправка сообщения как единственный вариант, сбой доступа к диску). Это проблема error handling — бывает и в однопоточных программах.
  • Обнаружение: те же инструменты, что для deadlock; искать потоки, постоянно активные в одних и тех же строках кода. Часто очень сложно.

Другие проблемы

  • Race conditions — решение: синхронизация или atomic objects.
  • Thread-safe объекты не решают всё — check-then-act:
List<String> list = Collections.synchronizedList(new ArrayList<>());
if (!list.contains("foo")) {   // каждый вызов атомарен, но связка — нет:
    list.add("foo");           // два потока могут оба пройти проверку ⇒ дубликат
}
// исправление: synchronized (list) { if (!list.contains("foo")) list.add("foo"); }
  • Несколько synchronized-методов синхронизируются на одном объекте (this) — часто нежелательно (независимые операции блокируют друг друга; лучше отдельные lock-объекты).
  • Inconsistent object states — использовать volatile, если переменную используют несколько потоков.
  • Не менять объект, на котором синхронизируешься:
synchronized (foo) { foo = new Foo(); }   // другие потоки синхронизируются уже на другом объекте ⇒ нет взаимного исключения

Functional elements

  • Функциональное программирование: всё — чистые математические функции, выход зависит только от входа; нет состояния и side effects. Чисто функциональные: Haskell; Scala — Java-derived с функциональными элементами (не чисто).
  • В Java функции — first-class citizens (lambda, method references Person::getAge). Отсутствие shared mutable state делает concurrency проще.

Streams (Stream API)

  • Stream — обёртка вокруг источника данных; не хранит и не изменяет данные, а делает их доступными для функциональных операций. Не I/O-элемент (но можно с файлами).
  • Создание:
listOfNumbers.stream();
Arrays.stream(arr);
Stream.<String>builder().add("a").add("b").build();
IntStream.range(1, 3);          // 1,2
LongStream.rangeClosed(1, 3);   // 1,2,3
new Random().doubles(3);
Stream.iterate(2, i -> i * 2);  // бесконечный stream
// также через Supplier<> (Stream.generate)
  • Вычисление lazy — делается только нужная работа (без terminal operation ничего не выполняется).
  • По умолчанию stream не параллельный; list.parallelStream() (или .parallel()) — параллельный (печать Thread.currentThread().getName() покажет main и ForkJoinPool.commonPool-worker-N).

Операции:

  • forEach() — применить функцию к каждому элементу (terminal); в parallel — случайный порядок, для порядка — forEachOrdered().
  • map() — новый stream, функция к каждому элементу.
  • filter() — оставляет элементы, для которых predicate (boolean) истинен.
  • collect() — обратно в List и т.п. (collect(Collectors.toList())).
  • flatMap() — убирает "слой" (Stream<List<String>> → Stream<String>); функция может вернуть несколько значений.
  • peek() — как forEach, но не terminal (для отладки).
  • Агрегаты: sum(), average(), min(), max(), count().
  • skip(), limit(); allMatch, anyMatch, noneMatch.
  • reduce() — аккумуляция: integers.stream().reduce(0, (a, b) -> a + b). Map + reduce дали имя парадигме MapReduce (но это немного другое).
  • sorted() — сортировка по comparator — не lazy (stateful, нужно увидеть всё).

Примеры:

double avg = roster.parallelStream().filter(p -> p.getGender() == Person.Sex.MALE)
        .mapToInt(Person::getAge).average().getAsDouble();
long n = roster.stream().filter(e -> e.getSalary() > 200000).count();
boolean all = roster.stream().map(p -> p.getName()).allMatch(s -> s.startsWith("A"));
IntStream nv = IntStream.of(1,2,3,4).flatMap(v -> Arrays.asList(v*v, v*v*v, v+1).stream().mapToInt(Integer::intValue));
// nv: 1,1,2, 4,8,3, 9,27,4, 16,64,5
  • (Замечание к коду Streams.java) roster пуст ⇒ average() даёт пустой OptionalDouble, getAsDouble() бросит NoSuchElementException.
  • Parallel streams используют fork/join framework (common pool). Деление данных — Spliterator (итератор по chunk'у stream). Обычно явно не нужен.
  • (Уточнение) лямбды в parallel stream не должны изменять общее состояние (напр. list.add в forEach на ArrayList — race); результат reduce корректен только с ассоциативной операцией и нейтральным identity.

Futures, Promises, Delays, Deferreds

  • По сути одно и то же (точный смысл зависит от языка): объект — placeholder для результата, который ещё не готов. Используются в concurrency, сетевых операциях и т.д.
  • В Java (и Scala) различие:
    • Future (Java 5) — read-only ссылка на ещё не вычисленное значение; читается, когда готово (executor.submit(callable)).
    • CompletableFuture (Java 8) — по сути Java-Promise: можно завершить вручную и строить цепочки; сложный, но мощный.
// как обычный Future, завершаемый вручную (promise)
CompletableFuture<String> cf = new CompletableFuture<>();
Executors.newCachedThreadPool().submit(() -> { Thread.sleep(500); cf.complete("Hello"); return null; });
cf.get();   // "Hello"

// асинхронное выполнение
CompletableFuture<String> f = CompletableFuture.supplyAsync(() -> "Hello");   // Supplier, common pool

// callback по завершению
f.thenApply(s -> s + " World");            // возвращает новый CompletableFuture с результатом
// thenAccept(Consumer) / thenRun(Runnable) — не возвращают значение (CompletableFuture<Void>)

// chaining: результат передаётся в следующий async-вызов (как flatMap)
CompletableFuture.supplyAsync(() -> "Hello")
    .thenCompose(s -> CompletableFuture.supplyAsync(() -> s + " World"));

// combine двух независимых
CompletableFuture.supplyAsync(() -> "Hello")
    .thenCombine(CompletableFuture.supplyAsync(() -> " World"), (s1, s2) -> s1 + s2);
// thenAcceptBoth — то же без результата

// много параллельных
CompletableFuture<Void> all = CompletableFuture.allOf(f1, f2, f3);
all.get();   // ждёт всех (результаты брать из f1..f3, напр. join())
  • thenApply vs thenCompose: thenApply(fn: T→U) ⇒ CF<U>; если fn возвращает CF, получим CF<CF<U>>; thenCompose(fn: T→CF) "сплющивает" в CF<U>.
  • Обработка ошибок:
    • handle((result, ex) -> ...) — получает результат или исключение, может вернуть новый результат;
    • whenComplete((result, ex) -> ...) — получает то же, но ничего не возвращает (напр. печать);
    • exceptionally(ex -> ...) — выполняется только при исключении.

Карточки (36)
Q: Что такое Heisenbug?

Ошибка, которая исчезает или меняется при отладке — отладка меняет тайминг, а значит и поведение concurrent программы.

Q: Определение deadlock (по слайдам).

Поток никогда не завершается (заблокирован навсегда). Обычно возникает при взаимодействии двух и более потоков; на практике трудно отличить от очень долгого потока.

Q: Четыре необходимых условия deadlock (Coffman)?
  1. Mutual exclusion.
  2. Hold and wait — держит ресурс и ждёт другой.
  3. No preemption — ресурс нельзя отобрать.
  4. Circular wait — цикл ожидания.

Сломай любое — deadlock невозможен (не на слайдах, но стандартно).

Q: T1: synchronized(r2){ sleep(100); synchronized(r1){...} }, T2: synchronized(r1){ sleep(100); synchronized(r2){...} }. Что произойдёт? Гарантирован ли deadlock?

Почти всегда: T1 держит r2 и ждёт r1, T2 держит r1 и ждёт r2 ⇒ deadlock, программа висит после "Thread 1: Locked r2" / "Thread 2: Locked r1". Не гарантирован: если один поток захватит оба монитора до того, как второй возьмёт первый — всё завершится. sleep лишь делает deadlock очень вероятным.

Q: Как исправить crossed-locks deadlock?

Захватывать locks в одном и том же порядке во всех потоках (оба: r1, затем r2) — тогда deadlock невозможен. Или избегать вложенной синхронизации.

Q: Рекомендации по избежанию deadlock (по слайдам)?
  • Избегать nested synchronization; лучше — нескольких синхронизаций в одном потоке.
  • Одинаковый порядок захвата locks.
  • Не делать долгих задач в synchronized-методах, которым синхронизация не нужна.
  • Timeouts: join(timeout), Lock.tryLock(timeout).
Q: Можно ли задать timeout для synchronized?

Нет. Таймаут есть у Lock.tryLock(time, unit) и join(timeout).

Q: Может ли deadlock возникнуть только из synchronized-методов (без явных synchronized-блоков)?

Да (искусственно): A.methodA(B b){ b.last(); }, B.methodB(A a){ a.last(); }, все synchronized. Поток 1: a.methodA(b) — держит монитор a, ждёт b. Поток 2: b.methodB(a) — держит b, ждёт a ⇒ возможен deadlock.

Q: Как найти deadlock в Java-программе?

Thread dump и мониторинг: jstack, jcmd, jconsole, Java Mission Control (JMC), VisualVM; на Linux kill -3 <pid>. Ищем потоки, заблокированные длительное время.

Q: Deadlock vs livelock?
  • Deadlock: потоки заблокированы (Blocked/Waiting), ничего не делают.
  • Livelock: поток не заблокирован, активно работает, но без прогресса (никогда не завершается).
Q: Объясните LivelockWithLocks.

T1 берёт lock1, T2 — lock2; каждый спит 50 мс, затем tryLock() другого lock'а неудачен ⇒ отпускает свой и повторяет. Действуя синхронно, они бесконечно уступают друг другу ("cannot acquire lock2, releasing lock1."). Лечение: случайная задержка перед повтором, единый порядок захвата.

Q: Какой livelock чаще встречается на практике?

Бесконечные повторы неудачного действия: повторная отправка сообщения как единственный вариант, повтор неудачного доступа к диску. Это проблема error handling, бывает и в однопоточных программах.

Q: Как обнаружить livelock?

Те же инструменты, что для deadlock; искать потоки, постоянно активные в одних и тех же строках кода. Часто очень сложно.

Q: Что не так: List<String> list = Collections.synchronizedList(new ArrayList<>()); if (!list.contains("foo")) list.add("foo");

Каждый вызов атомарен, но связка check-then-act — нет: два потока могут оба увидеть, что "foo" нет, и оба добавить ⇒ дубликат. Исправление: synchronized (list) { if (!list.contains("foo")) list.add("foo"); }.

Q: Что не так с synchronized (foo) { foo = new Foo(); }?

Меняется объект, на котором синхронизируются: другие потоки будут синхронизироваться на новом объекте ⇒ mutual exclusion теряется. Не менять монитор-объект (лучше final поле).

Q: Почему плохо, когда много synchronized-методов класса синхронизируются на одном объекте?

Все они используют монитор this ⇒ независимые операции блокируют друг друга, теряется параллелизм. Часто лучше отдельные lock-объекты.

Q: Как решаются race conditions (по слайдам "Other problems")?

Синхронизация или atomic objects; thread-safe объекты полезны, но не решают всё; volatile для переменных, используемых несколькими потоками (inconsistent states).

Q: Что такое функциональное программирование и как оно помогает concurrency?

Программа из чистых функций: выход зависит только от входа, нет состояния и side effects. Функции — first-class citizens. Нет shared mutable state ⇒ нет race conditions ⇒ легко распараллелить. Haskell — чисто функциональный; Scala — с функциональными элементами.

Q: Что такое Stream в Java? Хранит ли он данные?

Обёртка вокруг источника данных (List, массив, Supplier...), делающая его доступным для функциональных операций. Данные не хранит и не изменяет. Не путать с I/O-streams.

Q: Что значит, что streams lazy? Какая операция не lazy?

Вычисляется только необходимое и только при terminal operation (поэтому возможны бесконечные Stream.iterate(2, i -> i*2) с limit). sorted() не lazy — нужно увидеть все элементы.

Q: Как сделать stream параллельным? Что используется внутри?

list.parallelStream() (или .parallel()). Внутри — fork/join framework (common pool); данные делит Spliterator (итератор по chunk'у).

Q: Arrays.asList(1,2,3,4).parallelStream().forEach(System.out::println) — в каком порядке?

В произвольном (недетерминированном). Для исходного порядка — forEachOrdered().

Q: map vs flatMap?
  • map — 1 элемент → 1 элемент.
  • flatMap — 1 элемент → stream из 0..n элементов, результат "сплющивается" (Stream<List<String>> → Stream<String>).
Q: forEach vs peek?

Оба применяют функцию к каждому элементу, но forEach — terminal (завершает stream), peek — intermediate (stream продолжается; удобно для отладки).

Q: Что вернёт IntStream.of(1,2,3,4).flatMap(v -> Arrays.asList(v*v, v*v*v, v+1).stream().mapToInt(Integer::intValue))?

1, 1, 2, 4, 8, 3, 9, 27, 4, 16, 64, 5.

Q: Arrays.asList(1,2,3,4,5).stream().reduce(0, (a,b) -> a+b) — результат? Что важно для reduce в parallel?
  1. В parallel stream операция должна быть ассоциативной, а identity (0) — нейтральным, иначе результат зависит от разбиения.
Q: Что не так: List<Integer> out = new ArrayList<>(); nums.parallelStream().map(x -> x*2).forEach(out::add);

Side effect в общий не thread-safe ArrayList из нескольких потоков ⇒ race condition (потерянные элементы, исключения), плюс порядок произволен. Правильно: .collect(Collectors.toList()).

Q: Что такое Future / Promise / Delay / Deferred?

По сути одно и то же (детали зависят от языка): объект-placeholder для результата, который ещё не готов. Используются в concurrency, сетевых операциях и т.д.

Q: Future vs CompletableFuture?
  • Future (Java 5): read-only ссылка на ещё не вычисленное значение; только get/isDone/cancel.
  • CompletableFuture (Java 8): Java-аналог Promise — можно завершить вручную (complete()), строить цепочки (thenApply, thenCompose, thenCombine, allOf), обрабатывать ошибки. Реализует Future.
Q: Как запустить задачу асинхронно через CompletableFuture и получить результат? 
CompletableFuture<String> f = CompletableFuture.supplyAsync(() -> "Hello");
f.get();   // "Hello"
Q: thenApply vs thenAccept vs thenRun?
  • thenApply(fn) — преобразует результат, возвращает новый CompletableFuture с значением.
  • thenAccept(consumer) — получает результат, ничего не возвращает.
  • thenRun(runnable) — не получает результат и ничего не возвращает.
Q: thenApply vs thenCompose?
  • thenApply(s -> s + " World") — функция возвращает значение.
  • thenCompose(s -> CompletableFuture.supplyAsync(() -> s + " World")) — функция возвращает CompletableFuture; результат "сплющивается" (без CF<CF<String>>) — цепочка асинхронных шагов.
Q: thenCombine vs allOf?
  • thenCombine(other, (a,b) -> ...) — объединяет результаты двух независимых futures (thenAcceptBoth — без результата).
  • allOf(f1, f2, f3) — для многих; возвращает CompletableFuture<Void>, get() ждёт всех (результаты брать из самих f1..f3).
Q: handle vs whenComplete vs exceptionally?
  • handle((res, ex) -> ...) — результат или исключение, может вернуть новый результат.
  • whenComplete((res, ex) -> ...) — то же, но ничего не возвращает (напр. логирование).
  • exceptionally(ex -> ...) — вызывается только при исключении (fallback-значение).
Q: Что такое Project Loom и virtual threads? Для чего они подходят?

Переработка concurrency в Java. Virtual threads — лёгкие потоки внутри JVM; хороши для IO-heavy приложений, менее — для compute-intensive. Structured concurrency упрощает зависимости потоков и обработку ошибок.

Q: Parallel streams vs ExecutorService vs CompletableFuture — когда что?
  • Parallel streams — data parallelism над коллекцией без shared state, минимум кода.
  • ExecutorService — явный контроль пула и набора независимых задач (Runnable/Callable).
  • Fork/join — рекурсивный divide and conquer.
  • CompletableFuture — асинхронные цепочки зависимых шагов, комбинирование результатов, обработка ошибок.

& берёт адрес переменной, * разыменовывает указатель (читает значение по адресу) ⇒ печатает 5.

Оба позволяют менять оригинал. Указатель: передаётся адрес, внутри нужно *y = 6, может быть null. Ссылка: синтаксис как у обычной переменной, псевдоним оригинала. int a=6,b=7; swap(a,b); ⇒ печатает 76.

Требования к T (напр. operator<, distanceFrom в Line<T>) проверяются при инстанцировании.

Лекция 08: OpenMP — Introduction to OpenMP, Loop Parallelism and Scheduling, Synchronization Techniques

Выжимка

Слайды: session9.pdf

(На слайдах заголовок «Week 9: Shared memory parallelism in C++, OpenMP», Stefan Kuhn.)

Пометка [доп.] означает короткое уточнение из общих знаний об OpenMP, которого нет на слайдах или которое там неточно.

1. Контекст: параллелизм в C++

  • Раньше различали shared memory и distributed memory параллелизм. В Java была многопоточность (shared memory).
  • Сам язык C++ не содержит параллелизма в управляющих конструкциях.
  • Варианты:
    • auto-parallelization компилятора (Intel C++ Compiler, GCC) превращает последовательный код в многопоточный;
    • параллельные библиотеки (libstdc++ parallel mode);
    • «родные» потоки — pthreads (POSIX threads);
    • на практике чаще всего используют OpenMP.

2. Что такое OpenMP

  • API для параллельного выполнения, de-facto standard для shared-memory параллелизма (multithreading) в C, C++ и Fortran.
  • Текущая спецификация 6.0, сайт openmp.org. Portable между компиляторами.
  • Архитектура (слои):
    • User layer: End User → Application;
    • Programming layer: Directives/Compiler, OpenMP library, Environment variables;
    • System layer: OpenMP Runtime library, OS/system support for shared memory and threading;
    • HW: Proc1…ProcN над Shared Address Space.
  • Программирование идёт в основном через preprocessor directives #pragma omp ... («pragma» в C — общий термин для расширений).
  • Programs should compile without OpenMP: если игнорировать #pragma omp, получится корректная последовательная программа.
  • Нужен флаг компилятора: -fopenmp (gcc). Заголовок #include <omp.h>.

3. parallel: параллельный регион

#include "omp.h"
void main() {
  #pragma omp parallel          // parallel block с числом потоков по умолчанию
  {
      int ID = omp_get_thread_num();
      printf(" hello(%d) ", ID);
      printf(" world(%d) \n", ID);
  }
}
  • Возможный вывод: hello(1) hello(0) world(1) world(0) hello(3) hello(2) world(3) world(2). Порядок недетерминирован, строки перемешиваются.
  • Каждый поток выполняет копию кода блока (модель fork-join; в Java поток явно создают с отдельной функцией run).
  • Число потоков по умолчанию равно числу ядер. Задать вручную: omp_set_num_threads(4);. Это C-функция, а не директива. [доп.] Также num_threads(n) clause и переменная окружения OMP_NUM_THREADS.
  • Полезные функции: omp_get_thread_num() (ID потока, у master 0), omp_get_num_threads() (число потоков в команде), omp_get_num_procs().

4. Data sharing: shared / private / firstprivate / lastprivate

  • Переменные, объявленные вне блока, по умолчанию shared (общие).
  • Переменные, объявленные внутри блока, private (у каждого потока своя копия).
  • Переменные функций, вызванных из параллельного блока, тоже private (они на стеке потока).
  • Явно: #pragma omp parallel shared(n, a) private(b).
  • private: копия не инициализирована, её нужно инициализировать внутри блока.
  • firstprivate: каждая private-копия инициализируется исходным значением переменной.
  • lastprivate: после цикла значение копируется обратно в исходную переменную. На слайде сказано «from the last finishing thread»; [доп.] точнее, берётся значение из последней по порядку итерации (sequentially last iteration), а не от потока, который закончил последним.
  • Private pointer без выделения памяти внутри региона приводит к segmentation fault (копия указателя не инициализирована).
  • Примеры:
    float s[8]; s[0] = calculateBase(...);
#pragma omp parallel for firstprivate(s)   // у каждого потока копия s с s[0] = база
for (int i = 0; i < n; i++) { s[..] = ..; .. = ..s[..]; }

#pragma omp parallel for lastprivate(tmp)
for (int i = 0; i < n; i++) {
    tmp = x[i]*x[i]*3.1415;
    z[i] = tmp*x[i] + y[i];
    t[i] = tmp*y[i];
}
printf("tmp = %f\n", tmp);                  // значение из итерации i = n-1

5. Barrier и nowait

  • Race conditions возможны, как в Java, и обрабатываются вручную.
  • В конце параллельного блока есть implicit barrier («automatic join»): программа продолжается, только когда все потоки закончили.
  • Барьер можно убрать с помощью nowait. [доп.] nowait — это clause worksharing-конструкций (#pragma omp for nowait, sections nowait, single nowait). Неявный барьер в конце самого parallel убрать нельзя.
  • Явный барьер внутри региона: #pragma omp barrier. Все потоки ждут друг друга в этой точке.

6. parallel for: параллелизм циклов

#pragma omp parallel for
for (i = 1; i < 13; i++) {
    c[i] = a[i] + b[i];
}
  • Итерации распределяются между потоками. Loop scheduling можно настроить.
  • Работает только для «настоящих» for-циклов (canonical form: известное число итераций, простой инкремент, без break).
  • Итерации должны быть независимы. Этот цикл нельзя распараллелить как есть:
    j = 5;
for (i = 0; i < MAX; i++) { j += 2; A[i] = big(j); }  // loop-carried dependency через j
    [доп.] Исправление: убрать зависимость, j = 5 + 2*(i+1), тогда A[i] = big(j) с j private.
  • Переменная цикла i в parallel for автоматически private.

Reduction

Наивная сумма даёт race condition на ave:

double ave = 0.0, A[MAX];
#pragma omp parallel for reduction(+:ave)
for (i = 0; i < MAX; i++) ave += A[i];
ave = ave / MAX;
  • Каждый поток получает private-копию ave, инициализированную нейтральным элементом операции (0 для +, 1 для *). В конце копии объединяются оператором в исходную переменную.
  • Операторы на слайде: +, -, *, &&, ||, &, |, ^. [доп.] Также min, max.

collapse

#pragma omp parallel for collapse(3) schedule(dynamic)
for (i = 0; i < N; i++)
  for (j = 0; j < N; j++)
    for (k = 0; k < N; k++)
      A[i][j][k] = f(i, j, k);   // f дорогая, время выполнения переменное
  • collapse(3) сливает три вложенных цикла в одно пространство итераций ($N^3 = 1000$). Работы для распределения становится больше, балансировка лучше.
  • schedule(dynamic) здесь нужен, потому что время итераций неравномерно.

Scheduling [доп.: на слайдах только schedule(dynamic) и «loop scheduling can be influenced»]

schedule(kind[, chunk]):

kind Как распределяет Когда использовать
static итерации заранее делятся на блоки (по умолчанию примерно равные куски; с chunk — round-robin по chunk) равная стоимость итераций, минимальный overhead
dynamic поток берёт следующий chunk (по умолчанию 1), когда освободился неравномерная стоимость итераций; overhead выше

7. sections: разный код параллельно

#pragma omp parallel sections
{
    #pragma omp section
    { taskA(); }
    #pragma omp section
    { taskB(); }
}

Каждую section выполняет один поток. Это функциональный (task) параллелизм, а не по данным. Синтаксис: #pragma omp sections [clause[[,] clause]...].

8. Synchronization

critical

float res;
#pragma omp parallel
{
    float B; int i, id, nthrds;
    id = omp_get_thread_num();
    nthrds = omp_get_num_threads();
    for (i = id; i < niters; i += nthrds) {   // на слайде опечатка: i+nthrds
        B = big_job(i);
        #pragma omp critical
        consume(B, res);
    }
}
  • critical — блок, который в каждый момент выполняет только один поток (mutual exclusion).
  • Безымянный critical глобальный: все безымянные critical во всей программе используют один общий lock. Чтобы сделать его «локальным», ему дают имя: #pragma omp critical (foo). Критические секции с разными именами не блокируют друг друга.
  • Цикл for (i = id; i < niters; i += nthrds) — ручное cyclic распределение итераций по ID потока (SPMD-стиль).

atomic

#pragma omp parallel
{
    double tmp, B;
    B = DOIT();
    tmp = big_ugly(B);
    #pragma omp atomic
    X += tmp;
}
  • Быстрее critical (часто аппаратная атомарная инструкция), но только для одного простого оператора обновления одной переменной в памяти.
  • Слайд: «Only allows x++; ++x; x--; --x;, other variants exist». [доп.] Также x binop= expr (+=, -=, *=, /=, &=, |=, ^=, <<=, >>=), и есть формы atomic read/write/capture. Вычисление expr (здесь big_ugly) не защищено и выполняется параллельно.

single / master

#pragma omp parallel
{
    do_many_things();
    #pragma omp single
    { exchange_boundaries(); }   // выполнит ровно один (любой) поток
    do_many_other_things();
}
  • single: блок выполняет один любой поток. В конце implicit barrier (остальные ждут), если нет nowait.
  • master: блок выполняет только master-поток (ID 0), без барьера. [доп.] В OpenMP 5.1+ master deprecated, вместо него masked.
  • Single has an implied barrier, master doesn't.

Locks (низкоуровневые)

omp_lock_t lck;
omp_init_lock(&lck);
#pragma omp parallel private(tmp, id)
{
    id = omp_get_thread_num();
    tmp = do_lots_of_work(id);
    omp_set_lock(&lck);           // захват (блокирующий)
    printf("%d %d", id, tmp);
    omp_unset_lock(&lck);         // освобождение
}
omp_destroy_lock(&lck);

Жизненный цикл: omp_init_lock → omp_set_lock / omp_unset_lock → omp_destroy_lock. Locks — более низкий уровень, чем critical. [доп.] omp_test_lock — неблокирующая попытка захвата.

9. Tasks

Механизм динамического порождения работы, похожий на thread pool. Подходит для рекурсии и нерегулярных структур.

int fib(int n) {
    int i, j;
    if (n < 2) return n;
    else {
        #pragma omp task shared(i) firstprivate(n)
        i = fib(n-1);
        #pragma omp task shared(j) firstprivate(n)
        j = fib(n-2);
        #pragma omp taskwait
        return i + j;
    }
}
  • task создаёт задачу, её выполнит какой-либо поток команды.
  • taskwait ждёт завершения всех дочерних задач текущей задачи.
  • Data sharing работает как раньше. i, j должны быть shared, иначе результат задачи потеряется в private-копии. n — firstprivate, то есть значение захватывается при создании задачи.
  • if clause: #pragma omp task shared(i) if(n > 20). Задача создаётся как отложенная только при n > 20, иначе выполняется сразу (undeferred). Так избегают overhead на мелких задачах.
  • [доп.] fib обычно вызывают внутри #pragma omp parallel + #pragma omp single, чтобы дерево задач породил один поток.

10. Dynamic adjustment of threads

OpenMP может сам менять число потоков (dynamic adjustment). Чтобы отключить:

#include <omp.h>
void main() {
    int num_threads;
    omp_set_dynamic(0);                         // запрет динамической подстройки
    omp_set_num_threads(omp_get_num_procs());   // на слайде: omp_num_procs()
    #pragma omp parallel
    {
        int id = omp_get_thread_num();
        #pragma omp single
        num_threads = omp_get_num_threads();    // записывает один поток
        do_lots_of_stuff(id);
    }
}

omp_get_num_threads() вне параллельного региона возвращает 1, поэтому число потоков узнают внутри региона, в single.

11. Summary (со слайда)

  • OpenMP упрощает multithreading в C/C++/Fortran.
  • Параллельные блоки задаются preprocessor directives. Есть parallel for.
  • Tasks — абстракция над потоками.
  • Race conditions и synchronization нужно обрабатывать вручную (как в Java).

Q: Does the C++ language itself provide parallelism? What options exist?

  • pthreads («родные» потоки);

Q: What is OpenMP?

De-facto стандарт shared-memory параллелизма (multithreading) для C, C++, Fortran. Работает в основном через #pragma omp directives + runtime library + environment variables. Переносим между компиляторами, текущая спецификация 6.0.

Q: Name the layers of the OpenMP architecture.
  • User layer: End User, Application
  • Programming layer: Directives/Compiler, OpenMP library, Environment variables
  • System layer: OpenMP Runtime library, OS support for shared memory & threading
  • HW: processors над Shared Address Space
Q: What happens if you compile an OpenMP program without OpenMP support? What flag enables it in gcc?

Компилятор игнорирует #pragma omp, и получается корректная последовательная программа («programs should compile without OpenMP»). Флаг для gcc: -fopenmp.

Q: What can this program print with 4 threads?

c #pragma omp parallel { int ID = omp_get_thread_num(); printf(" hello(%d) ", ID); printf(" world(%d) \n", ID); }

Каждый из 4 потоков печатает свои hello/world, но порядок недетерминирован и строки перемешиваются. Например: hello(1) hello(0) world(1) world(0) hello(3) hello(2) world(3) world(2).

Гарантировано только, что у каждого потока hello(k) идёт раньше world(k).

Q: How do you set the number of threads? What is the default?

По умолчанию число потоков равно числу ядер. Варианты:

  • omp_set_num_threads(4); — обычная C-функция, не директива;
  • [доп.] clause num_threads(4);
  • [доп.] переменная окружения OMP_NUM_THREADS.
Q: Default data-sharing rules in a parallel region?
  • Переменные, объявленные вне блока, shared.
  • Объявленные внутри блока, private.
  • Локальные переменные функций, вызванных из региона, тоже private.
  • Переменная цикла в parallel for private.
Q: private vs firstprivate vs lastprivate?
  • private: у каждого потока своя копия, не инициализированная.
  • firstprivate: private-копия инициализирована исходным значением.
  • lastprivate: после конструкции значение копируется обратно в исходную переменную. Слайд говорит «from the last finishing thread»; точнее, из последней по порядку итерации.
Q: What is printed?

c double tmp = 0; #pragma omp parallel for lastprivate(tmp) for (int i = 0; i < 4; i++) tmp = i * 10; printf("%f\n", tmp);

30.000000: lastprivate берёт значение из последней итерации (i = 3), независимо от того, какой поток закончил последним. Без lastprivate (просто private) исходный tmp остался бы неизменным (0).

Q: What's wrong with making a pointer private without allocating in the parallel region?

Private-копия указателя не инициализирована (мусор). Разыменование даёт segmentation fault. Нужно выделить память внутри региона или использовать firstprivate, если всем подходит один и тот же адрес.

Q: What is the implicit barrier, and how do nowait and #pragma omp barrier relate to it?
  • В конце параллельного блока (и worksharing-конструкций for, sections, single) есть implicit barrier, «automatic join»: дальше идут, только когда все потоки закончили.
  • nowait убирает барьер. Это clause, например #pragma omp for nowait. Барьер в конце parallel убрать нельзя.
  • #pragma omp barrier ставит явный барьер в любом месте внутри региона.
Q: Why can't this loop be parallelized as is, and how to fix it?

c j = 5; for (i = 0; i < MAX; i++) { j += 2; A[i] = big(j); }

Loop-carried dependency: j в итерации i зависит от предыдущей итерации, а итерации должны быть независимы.

Исправление: вычислять j из i:

#pragma omp parallel for
for (i = 0; i < MAX; i++) { int j = 7 + 2*i; A[i] = big(j); }
Q: What's the problem here and how does OpenMP solve it?

c #pragma omp parallel for for (i = 0; i < MAX; i++) ave += A[i];

Race condition на shared ave: несколько потоков одновременно делают read-modify-write, обновления теряются.

Решение — reduction:

#pragma omp parallel for reduction(+:ave)

Каждый поток копит частичную сумму в private-копии (инициализирована 0), в конце копии складываются в ave.

Q: Which operators can be used in reduction (as listed on the slide)?

+, -, *, &&, ||, &, |, ^ ([доп.] и min, max).

Q: What does collapse(3) do, and why is schedule(dynamic) used in the slide example?
  • collapse(3) сливает 3 вложенных цикла в одно пространство итераций ($N^3$). Работы для распределения больше, баланс лучше.
  • schedule(dynamic) выбран, потому что f(i,j,k) дорогая и её время выполнения переменное. Динамическая раздача выравнивает нагрузку.
Q: Compare schedule(static), schedule(dynamic), schedule(guided).

[доп., на слайде только dynamic]

  • static: итерации заранее делятся на блоки (или chunk round-robin). Минимальный overhead, подходит для равных итераций.
  • dynamic: свободный поток берёт следующий chunk (по умолчанию 1). Хорош для неравномерных итераций, overhead выше.
  • guided: динамически, но chunk уменьшается по мере выполнения. Компромисс.
  • Также auto (решает runtime) и runtime (из OMP_SCHEDULE).
Q: What are sections used for?

Для параллельного выполнения разного кода (функциональный параллелизм). Каждый блок #pragma omp section внутри #pragma omp sections выполняется одним потоком.

Q: What does #pragma omp critical do? What's special about an unnamed critical?

Блок выполняется только одним потоком в каждый момент (mutual exclusion).

Безымянный critical глобальный: все безымянные critical-секции программы используют один общий lock и блокируют друг друга. Именованные (#pragma omp critical (foo)) с разными именами независимы.

Q: atomic vs critical?
  • atomic: быстрее (часто аппаратная инструкция), но только для одного простого оператора обновления одной переменной (x++, --x, x += expr…). Правая часть expr не защищена.
  • critical: произвольный блок кода, но дороже.
Q: In this code, which part runs in parallel and which part is protected?

c #pragma omp parallel { double tmp, B; B = DOIT(); tmp = big_ugly(B); #pragma omp atomic X += tmp; }

DOIT() и big_ugly(B) выполняются параллельно (B и tmp private, объявлены внутри). Атомарно защищено только обновление X += tmp общей переменной X.

Q: What's the bug in this slide loop?

c for (i = id; i < niters; i + nthrds) { ... }

i + nthrds вычисляет значение, но не изменяет i, поэтому цикл бесконечный. Должно быть i += nthrds. Тогда это cyclic-распределение итераций: поток id берёт id, id+nthrds, id+2·nthrds, ….

Q: single vs master?
  • single: блок выполняет один любой поток. В конце implicit barrier (остальные ждут).
  • master: только master-поток (ID 0), без барьера. [доп.] В OpenMP 5.1+ master заменён на masked.
Q: Write the OpenMP lock API lifecycle. 
omp_lock_t lck;
omp_init_lock(&lck);
// в параллельном регионе:
omp_set_lock(&lck);    // захват (ждёт, если занят)
/* критический код */
omp_unset_lock(&lck);  // освобождение
omp_destroy_lock(&lck);

Locks — низкоуровневая альтернатива critical.

Q: What are OpenMP tasks, and what does taskwait do?

Task — единица работы, создаваемая динамически, её выполнит какой-либо поток команды (похоже на thread pool). Подходит для рекурсии и нерегулярной работы.

#pragma omp taskwait ждёт завершения всех дочерних задач текущей задачи.

Q: In the task-based fib, why are i, j shared and n firstprivate?

c #pragma omp task shared(i) firstprivate(n) i = fib(n-1); #pragma omp task shared(j) firstprivate(n) j = fib(n-2); #pragma omp taskwait return i + j;

  • i, j shared: задачи пишут результат в переменные родителя. Если бы они были private, запись потерялась бы.
  • n firstprivate: значение n захватывается при создании задачи.
  • taskwait нужен, чтобы перед i + j обе задачи уже завершились.
Q: What does if(n > 20) do in #pragma omp task shared(i) if(n > 20)?

Задача создаётся как отдельная (отложенная) только при n > 20. Иначе код выполняется сразу, без overhead на создание задачи. Так параллелизм не дробится на слишком мелкие задачи.

Q: How do you prevent OpenMP from dynamically adjusting the number of threads? 
omp_set_dynamic(0);
omp_set_num_threads(omp_get_num_procs());

Реальное число потоков узнают внутри региона (omp_get_num_threads() в #pragma omp single), потому что вне региона функция возвращает 1.

Q: What does omp_get_num_threads() return outside vs inside a parallel region?
  • Вне: 1 (работает только master).
  • Внутри: размер текущей команды потоков.

omp_get_thread_num() даёт ID текущего потока, $0 \ldots n-1$.

Q: Which for loops can #pragma omp parallel for handle?

Только «настоящие» (canonical) for-циклы: известное до входа число итераций, целочисленная переменная цикла, простое условие и инкремент, без break. Итерации должны быть независимы. while и циклы с изменяемой границей не подходят.

Q: OpenMP vs Java threads: how does creating parallel work differ?
  • Java: явно создаёшь Thread/Runnable с отдельной функцией run, вызываешь start/join.
  • OpenMP: помечаешь блок директивой, и каждый поток выполняет копию этого блока (fork-join), join неявный (barrier).

Race conditions и синхронизацию в обоих случаях нужно обрабатывать вручную.

1. GPGPU

Определение. A general-purpose GPU (GPGPU) — GPU, который выполняет non-specialized calculations, то есть задачи, которые обычно выполняет CPU.

Применения: physics calculations, encryption/decryption, scientific computations, cryptocurrencies (Bitcoin), image processing.

GPU vs CPU

  • GPU рендерит изображения быстрее CPU благодаря parallel processing architecture: много вычислений одновременно. Эту особенность используют не только для графики.
  • CPU имеет higher clock speed, поэтому быстрее на отдельных вычислениях и эффективнее в small-scale iterative algorithms.
  • GPU лучше в large-scale parallel computing iterations.
  • Комбинация CPU + GPU даёт лучшую производительность.
  • CPU: few cores, оптимизированы для serial processing или ограниченного параллелизма. GPU: thousands of smaller, more efficient cores.
  • Программа состоит из двух частей:
    • Host code: serial-часть, выполняется на CPU;
    • Kernel code: parallel-часть, выполняется на GPU.

2. CUDA

  • CUDA: parallel computing platform and programming model от NVIDIA для GPGPU.

  • Работает на Windows, Linux, macOS, но only NVIDIA hardware.

  • OpenCL работает почти на любой ОС и большинстве видов железа.

  • Typical program structure (host):

    1. Allocate memory on the GPU
    2. Transfer input data to the GPU
    3. Launch kernel on the GPU
    4. Transfer output data to CPU

    Kernel: __global__ void kernel(...) { /* code executed on the GPU */ }

3. OpenCL

  • OpenCL (Open Computing Language): framework для программ, выполняющихся параллельно на разных compute devices (CPUs, GPUs) от разных вендоров (AMD, Intel, ATI, Nvidia…).
  • Две части кода: Host code (общая структура и вызов kernel) и Kernel code.
  • Framework задаёт язык для kernels, то есть функций, которые выполняются на устройствах.
  • Нужны новейшие драйверы видеокарты с поддержкой OpenCL.

OpenCL Features

  • Стандарт Khronos Group, версии 1.0, 1.1, 1.2, 2.0, 2.1, 2.2. 1.2 остаётся фактическим стандартом (de-facto).
  • Major backers: Apple, AMD, Intel.
  • Alternative to CUDA, designed for "heterogeneous computing".
  • Выполняется на CPUs, GPUs, DSPs, FPGAs.
  • Структура host program + kernels похожа на CUDA.
  • Restrictions: no recursion, variadics, or function pointers; cannot dynamically allocate memory from device.
  • OpenCL working group: AMD, ARM, Intel, NVIDIA, IBM, Samsung, Nokia, Apple, Texas Instruments, EA, Activision Blizzard и др.

CUDA vs OpenCL

CUDA OpenCL
Performance не определена, зависит от качества кода, железа и т.д. то же
Vendor implementation only NVIDIA TONS of vendors (AMD, NVIDIA, Intel, Apple…)

4. Установка и настройка

  • Нужны свежие драйверы, без поддержки OpenCL в драйвере ничего не работает.
  • NVIDIA и AMD выпустили реализации OpenCL для своих GPU, у Intel есть своя. На macOS OpenCL от Apple уже установлен.
    • AMD GPUs/CPUs → AMD APP SDK
    • NVIDIA GPUs → CUDA Toolkit
    • Intel CPUs/GPUs → Intel OpenCL SDK
  • OpenCL работает с любым компилятором, если есть библиотеки. Можно использовать Visual Studio (2022).

5. Programming in OpenCL: основные понятия («Important»)

  • Platform — реализация OpenCL (Intel, Nvidia). Device — реальное железо в машине (GPU…).
  • Для работы с GPU/CPU через OpenCL нужны:
    • Context: одно или несколько devices (GPU, CPU) и память;
      • Program: содержит kernels, которые компилируются для разных devices;
      • Kernel: метод, который выполняется на device (обычно GPU, но может и CPU);
    • Command Queue: управляет выполнением задач и передачей данных между CPU и devices;
    • Buffer: данные, которые обработает kernel или которые нужно передать host↔device:
      • Write to Buffer: передать аргументы в Global Memory устройства;
      • Execute Kernel: поставить параллельное выполнение в очередь;
      • Read from Buffer: получить результат обратно в HOST program.

6. Host program шаг за шагом

Host program управляет выполнением kernels на устройствах. Пишется на C, есть bindings для C++ и Python.

Общий принцип API: функции возвращают значения через аргументы-указатели, а return value (cl_int) — это status/error code (CL_SUCCESS = 0). Функции clCreate* возвращают объект, а статус пишут в последний аргумент &ret.

1. Platform (NVIDIA, AMD, Intel):

cl_int ret = clGetPlatformIDs(1, &platform_id, &ret_num_platforms);
//  1 — input: сколько платформ хотим; &platform_id — output; &ret_num_platforms — output: сколько есть

2. Device (GPU или CPU):

ret = clGetDeviceIDs(platform_id, CL_DEVICE_TYPE_DEFAULT, 1, &device_id, &ret_num_devices);
// типы: CL_DEVICE_TYPE_DEFAULT / _GPU / _CPU / _ACCELERATOR / _ALL

3. Context:

cl_context context = clCreateContext(NULL, 1, &device_id, NULL, NULL, &ret);

4. Command queue:

cl_command_queue command_queue = clCreateCommandQueue(context, device_id, 0, &ret);
// с OpenCL 2.0: clCreateCommandQueueWithProperties(context, device_id, NULL, &ret)

5. Memory buffer objects:

cl_mem a_mem_obj = clCreateBuffer(context, CL_MEM_READ_ONLY,  LIST_SIZE * sizeof(int), NULL, &ret);
cl_mem b_mem_obj = clCreateBuffer(context, CL_MEM_READ_ONLY,  LIST_SIZE * sizeof(int), NULL, &ret);
cl_mem c_mem_obj = clCreateBuffer(context, CL_MEM_WRITE_ONLY, LIST_SIZE * sizeof(int), NULL, &ret);

Флаги задают доступ со стороны kernel: A и B только читаются, C только пишется.

6. Transfer A, B на device:

ret = clEnqueueWriteBuffer(command_queue, a_mem_obj, CL_TRUE, 0, LIST_SIZE * sizeof(int), A, 0, NULL, NULL);
ret = clEnqueueWriteBuffer(command_queue, b_mem_obj, CL_TRUE, 0, LIST_SIZE * sizeof(int), B, 0, NULL, NULL);
// CL_TRUE = blocking; 0 = offset; size; host ptr; 0, NULL, NULL = event wait list / event

7. Load kernel source (kernel в отдельном файле):

FILE *fp = fopen("vector_add_kernel.cl", "r");
if (!fp) { fprintf(stderr, "Failed to load kernel.\n"); exit(1); }
char *source_str = (char*)malloc(MAX_SOURCE_SIZE);
size_t source_size = fread(source_str, 1, MAX_SOURCE_SIZE, fp);
fclose(fp);

8. Program object:

cl_program program = clCreateProgramWithSource(context, 1, (const char **)&source_str,
                                                (const size_t *)&source_size, &ret);

9. Build: online (компиляция kernel во время выполнения программы) или offline (заранее скомпилированная программа, загружается перед запуском):

ret = clBuildProgram(program, 1, &device_id, NULL, NULL, NULL);

10. Kernel object (строка = имя __kernel-функции):

cl_kernel kernel = clCreateKernel(program, "vector_add", &ret);

11. Kernel arguments (индекс = позиция параметра):

ret = clSetKernelArg(kernel, 0, sizeof(cl_mem), (void *)&a_mem_obj);
ret = clSetKernelArg(kernel, 1, sizeof(cl_mem), (void *)&b_mem_obj);
ret = clSetKernelArg(kernel, 2, sizeof(cl_mem), (void *)&c_mem_obj);

12. Execute:

size_t global_item_size = LIST_SIZE;  // всего work-items
size_t local_item_size  = 64;         // work-items в work-group
ret = clEnqueueNDRangeKernel(command_queue, kernel, 1, NULL,
                             &global_item_size, &local_item_size, 0, NULL, NULL);
// 1 = work_dim, NULL = global offset

13. Read result C:

int *C = (int*)malloc(sizeof(int) * LIST_SIZE);
ret = clEnqueueReadBuffer(command_queue, c_mem_obj, CL_TRUE, 0, LIST_SIZE * sizeof(int), C, 0, NULL, NULL);

(Освобождение ресурсов clRelease* — в OpenCL II.)

7. Kernel program

Kernel выполняется на GPU:

__kernel void vector_add(__global const int *A, __global const int *B, __global int *C) {
    int i = get_global_id(0);   // индекс текущего элемента
    C[i] = A[i] + B[i];
}
  • __kernel (или kernel): функция-точка входа, вызываемая с host, возвращает void.
  • __global: указатель на global memory (буферы).
  • get_global_id(0): уникальный индекс work-item в измерении 0.

Traditional loop → data-parallel OpenCL

void trad_mul(int n, const float *a, const float *b, float *c) {
    int i;
    for (i = 0; i < n; i++) c[i] = a[i] * b[i];
}
kernel void dp_mul(global const float *a, global const float *b, global float *c) {
    int id = get_global_id(0);
    c[id] = a[id] * b[id];
}   // execute over "n" work-items

1. Kernel и compute kernel

  • Kernel — программа, которая дублируется на compute devices: множество экземпляров kernel выполняются параллельно и обрабатывают массив данных.
  • Проще говоря, OpenCL kernel — код, предназначенный для выполнения на GPU.
  • Compute shader в OpenGL — тоже вид kernel, но он выполняется внутри 3D graphics pipeline.
  • Compute kernel в OpenCL не является частью 3D graphics pipeline.

2. NDRange и work-items

  • NDRange задаёт число work-items на compute device (N-мерное пространство индексов, N = 1, 2, 3; оси Dimension X/Y/Z).
  • Work-items делятся на work-groups. Это уровень software.
  • Work-group делится на wavefronts. Это уровень hardware (AMD), размер зависит от железа (HW-specific size). [доп.] У NVIDIA аналог — warp (32).
  • Wavefront — группа work-items, которые выполняются одновременно.

Иерархия: NDRange ⊃ work-group ⊃ wavefront ⊃ work-item.

3. Thread structure: built-in функции

Каждый work-item может узнать свой global ID по каждому измерению:

  • get_global_id(dim), get_global_size(dim)
  • Пример для 2D (матрица): get_global_id(0) = row, get_global_id(1) = column.

Или свой ID work-group и ID внутри work-group:

  • get_group_id(dim), get_num_groups(dim), get_local_id(dim), get_local_size(dim)
  • get_global_size(0) == get_num_groups(0) * get_local_size(0)
Function Description
uint get_work_dim() число измерений
get_global_id(uint dim) ID текущего work-item, $[0, WI)$
get_global_size(uint dim) общее число work-items $WI$
get_global_offset(uint dim) offset, заданный в clEnqueueNDRangeKernel
get_group_id(uint dim) ID текущей work-group, $[0, WG)$
get_local_id(uint dim) ID work-item внутри группы, $[0, WI/WG)$
get_local_size(uint dim) work-items в группе $= WI/WG$
get_num_groups(uint dim) число work-groups $WG$

[доп.] Без offset: get_global_id(d) = get_group_id(d) * get_local_size(d) + get_local_id(d).

  • Buffer object — блок памяти, выделенный OpenCL-программой. Обычно хранит входные и выходные данные work-items.
  • Constant memory — часть памяти устройства, read-only (__constant).
  • Global memory — часть памяти устройства. Любой work-item может читать и писать любое место. Объём узнают через clGetDeviceInfo() (CL_DEVICE_GLOBAL_MEM_SIZE).

5. Synchronization

Одна из самых сложных задач параллельного программирования — управлять порядком выполнения потоков. Синхронизация часто означает serialization: поток ждёт другой поток или завершения процедуры.

Два типа синхронизации:

  1. Among work-items within a work-group (atomics, fences, barriers).
  2. Among command queues within a context (events, несколько kernels).

5.1 Atomics

  • Обеспечивают memory ordering и синхронизацию атомарных операций: пока один поток читает или пишет атомарную переменную, атомарная операция не даёт другому потоку вмешаться.
  • Проблемный пример:
    // Thread A
x--;
// Thread B may change the value of x before the next line is executed.
if (x > 0) { /* To do */ }
    Для таких случаев существуют atomic variables и atomic-функции. [доп.] Например atomic_inc(&x), atomic_add(&x, v), atomic_dec, atomic_cmpxchg; в OpenCL 2.0 есть atomic_int + atomic_fetch_sub. Решение примера: int old = atomic_dec(&x); if (old - 1 > 0) ..., то есть использовать возвращённое значение, а не перечитывать x.
  • atomic_work_item_fence(flags, ...) — memory fence. Флаги CLK_GLOBAL_MEM_FENCE и CLK_LOCAL_MEM_FENCE. Эквивалент старых mem_fence(), read_mem_fence(), write_mem_fence().

5.2 Barrier

  • Barrier: work-item ждёт, пока все work-items (его work-group) дойдут до того же барьера, затем все продолжают.
  • work_group_barrier();: work-items в work-group должны выполнить его, прежде чем любой поток продолжит.
  • barrier(CLK_LOCAL_MEM_FENCE); — два флага:
    • CLK_GLOBAL_MEM_FENCE: для global memory;
    • CLK_LOCAL_MEM_FENCE: для local memory.
  • Разница (по слайду):
    • work_group_barrier() синхронизирует поток выполнения (Execution) work-items внутри work-group;
    • barrier(CLK_LOCAL_MEM_FENCE) синхронизирует доступ к local memory (Memory) внутри work-group.
    • Авторитетный источник — Khronos man page barrier.html. [доп.] По спецификации оба делают и execution barrier, и memory fence по указанным флагам. work_group_barrier — имя из OpenCL 2.0, barrier — из 1.x.
  • [доп.] Барьер должен встретиться всем work-items группы. Барьер внутри ветки if, которую проходят не все, — undefined behaviour (обычно deadlock).

5.3 Atomic vs Barrier

  • Atomic operations управляют тем, как несколько процессов одновременно обращаются к одной памяти и изменяют её. Целостность данных обеспечивается тем, что конкретную операцию в каждый момент выполняет только один.
  • Barrier — точка синхронизации внутри группы процессов (work-group): все заканчивают свою часть, прежде чем двигаться дальше. Сохраняется правильный порядок операций.
  • Коротко: atomics защищают одновременный доступ к памяти, barriers задают порядок/фазы выполнения внутри группы.

5.4 Events

  • Events синхронизируют команды в command queue: управляют потоком выполнения и гарантируют, что определённые операции завершены, прежде чем начнутся следующие.
  • Host-код выполняется последовательно, так зачем events? Они нужны, когда используются несколько command queues, связанных с разными devices или contexts.
  • [доп.] Последние три аргумента clEnqueue*: num_events_in_wait_list, event_wait_list, &event. Ещё есть clWaitForEvents, clFinish(queue), clFlush(queue).

6. Multiple kernels

  • Kernel (главная функция GPU) вызывается из host-кода на CPU.
  • Host может запускать несколько kernels, с одинаковой или разной функциональностью.
  • Схема: load_problem() → kernel() [execute_kernel → device: kernel_start…kernel_end] → sync() [finish] → get_results(), затем Kernel 2.
  • Граница между kernel-запусками даёт глобальную синхронизацию (не только внутри workgroup). Barrier синхронизирует лишь work-group, а следующий kernel начинается, когда предыдущий завершён целиком.

7. Release the memory

После обработки освобождают объекты, kernels и program:

clReleaseMemObject(bufC);                 // cl_mem
clReleaseKernel(kernel_1);                // cl_kernel
clReleaseProgram(program);                // cl_program
clReleaseCommandQueue(command_queue);     // cl_command_queue
clReleaseContext(context);                // cl_context

[доп.] Обычно освобождают в порядке, обратном созданию (сначала kernel/buffers, в конце context), предварительно вызвав clFinish(queue).

Q: Can a barrier synchronize work-items from different work-groups? How do you get global synchronization?

Нет, barrier действует только внутри одной work-group.

Глобальная синхронизация: разбить задачу на несколько kernel-запусков. Следующий kernel начинается после завершения всех work-items предыдущего (слайд «Multiple kernels: global (not only workgroup) synchronization»).

Q: What's wrong with this kernel?

c __kernel void k(__global int *a) { if (get_local_id(0) < 16) { a[get_global_id(0)] = 0; barrier(CLK_GLOBAL_MEM_FENCE); } }

Barrier находится внутри ветки, которую проходят не все work-items группы. Барьер должен быть выполнен всеми work-items work-group, иначе undefined behaviour (обычно deadlock или зависание). Барьер нужно вынести из if.

Q: What are events in OpenCL used for?

Для синхронизации команд в command queue: управление потоком выполнения, гарантия, что одни операции завершились до начала других. Через event_wait_list и выходной event в clEnqueue*.

Q: Host code executes sequentially, so why do we need events?

Команды в очередь только ставятся (enqueue выполняется асинхронно). Events нужны, когда используются несколько command queues, связанных с разными devices или contexts: зависимости между такими очередями сам порядок host-кода не обеспечивает.

Q: Describe the "multiple kernels" execution flow.

Host: load_problem() → kernel() (execute_kernel на device: kernel_start … kernel_end) → sync() (finish) → get_results() → затем то же для Kernel 2.

Kernels могут быть одинаковыми или разными, и все вызываются из host-кода CPU.
