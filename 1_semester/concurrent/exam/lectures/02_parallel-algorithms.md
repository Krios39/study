## Идея

- Алгоритм — "конечная последовательность строгих инструкций" ⇒ мышление об алгоритмах обычно **последовательное**.
- Чтобы использовать параллельные компьютеры, алгоритм должен быть параллельным; иногда это легко, часто — нет. Реализация на конкретном языке — следующий шаг.
- Различать: **problem** (найти простые 2..n) → **algorithm** (Sieve of Eratosthenes, другие) → **implementation** (serial, parallel...). Реализации отличаются структурами данных, управляющими конструкциями.

## Пример: Sieve of Eratosthenes

Последовательный псевдокод:
```
A[2..n] = true
for i = 2,3,... not exceeding n:
    if A[i]:
        for j = i², i²+i, i²+2i, ... ≤ n: A[j] = false
return all i with A[i] true
```
- Даже "let A be an array ... initially all set to true" неявно последовательно — это про реализацию?
- C-реализация: malloc, проверка NULL, цикл инициализации, внешний цикл до sqrt(N), внутренний — помечает кратные.

**Что можно распараллелить:**
- malloc/инициализацию/проверку NULL — трудно.
- Инициализацию списка нулями — можно (вопрос, стоит ли).
- Пометка кратных: "каждое число параллельно" — **проблема**: следующее число для вычёркивания известно только после вычёркивания предыдущим (зависимость).
- Альтернатива — **разбить данные на chunks**; вычёркивание одного и того же числа параллельно в каждом chunk; нужна коммуникация, чтобы найти следующее число.
- Общая стратегия: **один процесс делает 2..sqrt(N)**, остальные — оставшиеся числа ⇒ меньше коммуникации.

**Shared memory вариант:**
```
Thread 0: if A[i] true → Broadcast i to other threads; cross out multiples
Thread > 0: in its block, cross out all multiples of i
```
- Один массив; thread 0 делает 2..sqrt(n) и рассылает (broadcast) каждое простое; в конце в массиве остаются только простые.
- Для части 2..sqrt(n) ускорения **нет**; для остального — зависит от числа процессоров ("немного как в Amdahl's law").

**Distributed memory вариант:**
- Единой структуры данных нет.
- **Каждый процесс сам делает часть 2..sqrt(n)** (массив A) и вычёркивает в своём сегменте B = (L, H]; затем отправляет B процессу 0, который объединяет.
- Дублирование 2..sqrt(n) кажется неэффективным, но всё идёт параллельно и **экономит коммуникацию**.
- Разбиение sqrt(n)+1..n: равные chunks хороши, если процессы равной мощности; блоками или **interleaving** chunks; обработать случай, когда деление "не ровное".

## Foster's Methodology (Ian Foster, 1995)

Четыре шага: **Partitioning → Communication → Agglomeration → Mapping** (PCAM). Полезные шаги, но **не механический рецепт**.

### 1. Partitioning
- **Domain decomposition** — разбить **данные** на много мелких одинаковых кусков; найти самый большой/часто используемый объект данных, разбить его, каждому куску — primitive task. Пример: трансформация 3D-объекта по пикселю. Идеально для **data parallelism**.
- **Functional decomposition** — разбить **функции** на отдельные задачи, применяемые к части или всем данным. Пример: обработка аудио тремя разными операциями на разном железе над одними данными. Для **functional parallelism**.
- Критерии:
  - задач хотя бы **на порядок больше**, чем процессоров (гибкость);
  - избегать избыточных вычислений и хранения;
  - primitive tasks примерно **одного размера** (иначе дисбаланс);
  - число задач — **возрастающая функция размера задачи** (рост задачи ⇒ больше задач, а не крупнее);
  - рассмотреть несколько альтернативных разбиений (и domain, и functional).

### 2. Communication
- Какая коммуникация нужна? **Local** (несколько задач) или **global** (все)? Есть ли паттерн (сетка: клетка общается с соседями)?
- Критерии: все задачи делают примерно одинаковое число коммуникаций; каждая общается с **малым числом соседей**; коммуникации могут идти **concurrently**; задачи могут вычислять concurrently.

### 3. Agglomeration
- До этого: много задач и (в distributed) много коммуникаций, без привязки к системе.
- Объединяем 2+ задачи в более крупные ⇒ меньше задач, больше размер, лучше производительность, проще код. **Tradeoff**.
- Критерии: уменьшить коммуникацию за счёт **locality**; дублирование вычислений/данных должно окупаться и не ломать scalability; задачи с похожей стоимостью вычислений/коммуникации; число задач всё ещё растёт с размером задачи; достаточно concurrency для текущих и будущих машин; меньше задач нельзя без дисбаланса; разумная цена модификации существующего последовательного кода.

### 4. Mapping
- Назначение задач процессорам; может быть не нужно, если делается автоматически.
- Цель — минимизировать время выполнения ⇒ **максимизировать загрузку процессоров**; часто общающиеся задачи — с низкой стоимостью коммуникации; load balancing алгоритмы.
- Критерии: рассмотрены варианты one task per processor и multiple tasks per processor; **static и dynamic** распределение; при centralized load balancing — менеджер не bottleneck; при dynamic — оценены издержки стратегий.

## Прочее

- **Embarrassingly parallel** — легко распараллеливаемые задачи: независимые поиски (биоинформатика, BLAST), фракталы (Mandelbrot — каждый пиксель независим).
- Проблемы concurrent программ: **starvation, race conditions, deadlocks** (подробно — в лекциях по языкам).
- Все ли задачи решаются быстрее параллельно? Зависит от определения. Вероятно, все алгоритмы распараллеливаемы, но **не все хорошо**. Класс **NC** — задачи, решаемые за **полилогарифмическое время** на параллельном компьютере с **полиномиальным числом процессоров**. Вопрос **P = NC** открыт.

## Parallel modelling (process calculi)

- **CCS** (Calculus of Communicating Systems), Robin Milner. Конкурент — **CSP** (Hoare). Моделирует компоненты, их наблюдаемое поведение и взаимодействие.
- Пример: спецификация `A := a.b.A` (бесконечно a, затем b). Компоненты `B := a.B`, `C := b.C`; `(B | C)` — a и b **в неопределённом порядке** (не соответствует спецификации).
- С обменом сообщениями (без shared memory): `B' := c.d.b.B'`, `C' := c.a.d.C'`, `A' := (B' | C')\{c,d}` — синхронизация по c, затем a, затем по d, затем b. Можно формально доказать `A == A'`. `\{c,d}` — restriction (скрытие каналов).
- **CSP** — вдохновил **Go**; реализации pyCSP, js-csp, CSP for Java. Именованные каналы: `query!i` (отправка) и `query?i` (приём) по каналу query. Есть операторы parallel, choice, restriction. Есть и CCS с value passing.
- Диаграммы (Foster): базовые действия задачи — read/write local memory, send message, receive message, create new tasks (suspending until they terminate), terminate. Всё ad hoc, **стандарта нет**.

## Summary
- Большинство алгоритмов сформулированы последовательно.
- Foster: partitioning, communication, agglomeration, mapping.
- Можно ли полезно распараллелить все алгоритмы — открытый вопрос.
