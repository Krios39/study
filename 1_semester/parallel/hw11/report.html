Exercise 11.4: words without punctuation, in lowercase

Only the map method of TokenizerMapper was changed. The reducer, the combiner and main are as before.

private static final Pattern SEPARATORS = Pattern.compile("[^\\p{L}\\p{N}']+");
private static final Pattern EDGE_APOSTROPHES = Pattern.compile("^'+|'+$");

public void map(Object key, Text value, Context context
                ) throws IOException, InterruptedException {
  String line = value.toString().toLowerCase(Locale.ROOT).replace('\u2019', '\'');
  for (String token : SEPARATORS.split(line)) {
    String clean = EDGE_APOSTROPHES.matcher(token).replaceAll("");
    if (!clean.isEmpty()) {
      word.set(clean);
      context.write(word, one);
    }
  }
}
  • Lowercase. toLowerCase(Locale.ROOT), so the result does not depend on the system locale.
  • Splitting. Everything that is not a letter or a digit (\p{L}, \p{N}) separates words. This also splits No?--never into two words, which plain whitespace tokenisation did not.
  • Apostrophes. They are kept inside a word, so don't and it's stay one word instead of becoming don + t. The typographic apostrophe ’ is first replaced by '. Apostrophes at the start or end, which are single quotation marks, are removed.
  • Empty tokens (a line that is only punctuation) are not emitted.
  • Both patterns are compiled once per class, not once per line.

Exercise 11.5: matrix-vector multiplication $b = Ax$

Class MatrixVector, arguments matrix_folder vector_file output. Every line of every file in the matrix folder is one row in the form i,A(i,0),A(i,1),....

Design

  • Vector. main reads the vector file through the Hadoop FileSystem API. Values may be separated by commas, spaces or newlines. It stores them as one comma-separated string with conf.set("vector_values", ...) before Job.getInstance(conf, ...). The job takes a copy of the configuration, so a value set afterwards would not reach the tasks.
  • Mapper Mapper<Object, Text, IntWritable, DoubleWritable>. setup() parses the vector into a double[] once per task. map() parses one row, computes the dot product $b_i = \sum_j A_{ij} x_j$ and emits (i, b_i). If the row length differs from the vector length, the task fails with a message that names the row.
  • Reducer Reducer<IntWritable, DoubleWritable, IntWritable, DoubleWritable> sums the values of a key. Each row appears once, so this is effectively the identity. Summing also keeps the job correct if one row were ever split into several partial products.
  • Rows are independent, so the map step is fully parallel. Hadoop gives each matrix file (and each block of a large file) its own map task. The output is sorted by row index because IntWritable keys are sorted in the shuffle.

Bonus: improving WordMedian

WordMedian computes the median length of the words in the input. The mapper emits (length, 1) for every token, and the reducer (also used as the combiner) sums them into a histogram. After the job, main reads the histogram and walks it to the middle. While testing it, I found several real bugs. This is a different kind of change from 11.4: 11.4 changed what counts as a word, while here the tokenisation is unchanged and the computation itself is fixed. The original file is kept in original/WordMedian.java.

Changes

  • run() uses getConf(), so the generic options are respected.
  • readHistogram reads all part-r-* files with globStatus and merges them into a TreeMap<Integer, Long>. Each reducer's file is sorted only within itself, and the map restores the global order of lengths.
  • medianOf computes the total $N$ from the histogram itself and takes the values at ranks $\lfloor (N+1)/2 \rfloor$ and $\lfloor N/2 \rfloor + 1$, which are the same rank for odd $N$. It returns their average. This is the textbook definition and needs no special cases.
  • Counts are LongWritable/long.
  • Exit codes: 2 for usage errors, 1 if the job fails, 0 on success. main passes the code to System.exit.

Questions about the combiner

Why is IntSumReducer also used as the combiner?

A combiner runs on the output of one map task, before the shuffle, and sees only the pairs of that task. IntSumReducer can play this role because of two properties:

  • Addition is associative and commutative. Summing the 1s of each map task first and then summing the partial sums gives the same total as summing all the 1s at once: $\sum_{\text{all}} 1 = \sum_{\text{tasks}} \sum_{\text{task}} 1$. The grouping and the order do not matter.
  • Its input and output types are the same (Text, IntWritable in and out). These are also the map output types, so the reducer cannot tell whether a value is an original 1 or a partial sum produced by the combiner.

What are the advantages?

  • Less data in the shuffle. This is the most expensive phase: data is written to local disk, sent over the network and merged. In the run on the books, the combiner reduced 337 321 map output records to 60 321 (5.6× fewer), and 3.25 MB of map output to 0.87 MB of shuffle data. After 11.4 the reduction was 340 196 → 33 128 records (10×).
  • Less work and memory for the reducers. The reducer of the receives 5 partial sums (one per map task) instead of 18 701 ones.
  • Less skew. Frequent words would otherwise send far more data to their reducer than rare words. With a combiner, every key sends at most one record per map task (per spill).
  • Spills and merges on the map side are smaller.

Can every reducer be used as a combiner?

No. Hadoop treats the combiner as an optional optimisation. It may run it 0, 1 or several times on any subset of the values of a key: per spill, and again during merges. The final result must not depend on that. A reducer is a valid combiner only if:

  • its output key/value types equal its input types, which are the map output types;
  • the operation gives the same result when applied to partial groups and then to the partial results. In practice this means it is commutative and associative, like sum, max, min, set union or counting by summing counts;
  • it has no side effects that must happen exactly once.

Counterexamples:

  • Average. A reducer that outputs the mean of its values cannot be a combiner: the mean of partial means is wrong when the groups have different sizes. For $(1, 2)$ and $(3)$, the mean of the means is $(1.5 + 3)/2 = 2.25$, but the true mean is 2. WordMean avoids this by emitting sums and counts, which can be added, and divides only at the end.
  • Median, or the number of distinct values. These cannot be computed from partial results at all.
  • A reducer that changes types. Example: one that writes Text such as "the: 18701".
  • A reducer that counts how many values it received instead of adding them. As a combiner, it would turn 100 ones into 1.

A side note on 11.5: MatrixVector also sets its summing reducer as the combiner, and this is correct for the same reasons as in WordCount. But every row index occurs only once, so there is nothing to combine (combine input = combine output). A combiner only helps when keys repeat within one map task.

Limitations
  • All runs used Hadoop local mode (one JVM, LocalJobRunner) in a container, not a real cluster. The number of map tasks is real, but they do not run on separate machines.
  • The vector in 11.5 is sent through the job configuration, as the assignment requires. That is fine for thousands of elements, but for very long vectors the distributed cache (job.addCacheFile) would be the right tool.
  • The 11.4 tokeniser is a reasonable heuristic, not a full English tokeniser. Hyphenated words such as well-known become two words, and the possessive 's stays part of the word (adam's).
