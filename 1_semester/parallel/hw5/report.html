Why JavaScript: I work as a JavaScript developer, so I decided to experiment and do this assignment in plain JS in the browser instead of a dedicated engine. I wanted to find out what JavaScript is actually capable of here, and how realistic and how easy it is to use it for parallel computing (Web Workers on the CPU, shaders on the GPU) and for shader graphics.

Scope: I chose tasks A and C and added a small CPU-vs-GPU benchmark as the bonus. Everything lives in one self-contained file, index.html (plain JavaScript + WebGL2, no libraries). Task B (Godot port) is not part of this report.

Exercise A: Piet Mondrian painting

Implementation Strategy:

The painting is stored as plain data: a list of rectangles [x, y, w, h, colour] in the range 0..1 with the origin at the top-left. JavaScript uploads this list to the shader as the uniform arrays uRect[N] and uCol[N], and the fragment shader loops over it for every pixel. The requested function is rect(st, pos, size, aa): it returns 1.0 inside a rectangle and 0.0 outside, so moving or placing a rectangle means changing only pos and size. The colour blocks are drawn first and the black lines on top, which gives the characteristic thick grid.

Shader code (the full source is in index.html):

// 1.0 inside the rectangle, 0.0 outside, soft edge of width ~uAA
float rect(vec2 st, vec2 pos, vec2 size, float aa){
  vec2 lo = smoothstep(pos - aa, pos + aa, st);
  vec2 hi = 1.0 - smoothstep(pos + size - aa, pos + size + aa, st);
  vec2 m = lo * hi;
  return m.x * m.y;
}

void main(){
  vec2 st = gl_FragCoord.xy / uRes;
  st.y = 1.0 - st.y;                       // flip: GL origin is bottom-left
  vec3 c = uPaper;
  for (int i = 0; i < N; i++)
    c = mix(c, uCol[i], rect(st, uRect[i].xy, uRect[i].zw, uAA));
  c += (hash(gl_FragCoord.xy) - 0.5) * uGrain;   // paper grain
  outColor = vec4(c, 1.0);
}
// the composition itself is just data (T = line thickness)
const SHAPES=[
  [V1+T, H1+T, V2-V1-T, H2-H1-T, 'red'],
  [V2+T, 0,    1-V2-T,  H1,      'yellow'],
  [0,    H2+T, V1,      1-H2-T,  'blue'],
  [V3+T, H3+T, 1-V3-T,  1-H3-T,  'blue'],
  [V1, 0,  T,    1,     'black'],   // ... plus 6 more black lines
  ...
];

Three renderers of the same painting:

  • GLSL (WebGL2): the solution to the task as stated.
  • JavaScript on the CPU: the identical rect() logic evaluated per pixel over ImageData. It is there to make the point that a shader is just "a function from pixel position to colour" that the GPU happens to run in parallel; the demo prints the measured CPU time under the canvas.
  • Pure CSS: a 4x4 display: grid with a black background and gap producing the lines. No JavaScript, a joke version (its composition is its own, since a uniform gap means every line runs edge to edge). I tried it just for fun: I had seen cases where people build whole pages and even games in pure CSS, without JavaScript, and wanted to see how close CSS alone gets to the painting. It has no practical value for this assignment, I simply decided to keep it.

What I had to study:

  • Shape from math, not from geometry: in the Shapes chapter of The Book of Shaders a rectangle is a mask built from step(). I replaced step() with smoothstep() to get anti-aliased edges and a tunable softness. Multiplying the lower-left and upper-right masks acts as a logical AND.
  • Compositing with mix(): mix(c, colour, mask) paints a shape over whatever is already there, so the draw order is simply the order of the loop.
  • Coordinate systems: gl_FragCoord starts at the bottom-left, while I wanted to write the composition top-down as on paper, hence st.y = 1.0 - st.y (the CPU twin does the same with its row index).
  • Passing data to a shader: uniform arrays with a compile-time size (the #define N is injected from JavaScript), plus how to find uniform locations for array names.
  • WebGL2 plumbing: compiling and linking with error reporting, and drawing one full-screen triangle generated from gl_VertexID so that no vertex buffer is needed.
  • Pseudo-random grain: the classic fract(sin(dot(p, ...)) * 43758.5453) hash, used to give the paper a slight texture.
Exercise C: Physics simulation with shaders (Gray-Scott reaction-diffusion)

Why this simulation:

I chose the Gray-Scott reaction-diffusion model because it is the cleanest example of "computation lives in a texture". Every cell only needs its eight neighbours, so every pixel can be updated independently and in parallel, which is exactly what a fragment shader does. It also has a very rich parameter space: two numbers, the feed rate $f$ and the kill rate $k$, switch the system between spots, stripes, labyrinths and splitting cells. That makes an "enhancement" visible in a single picture instead of requiring a table of numbers.

The model:

Two chemicals $A$ and $B$ diffuse over a grid and react as $A + 2B \to 3B$; $A$ is fed in at rate $f$ and $B$ is removed at rate $f + k$:

$$\frac{\partial A}{\partial t} = D_A \nabla^2 A - AB^2 + f\,(1 - A), \qquad \frac{\partial B}{\partial t} = D_B \nabla^2 B + AB^2 - (k + f)\,B$$

The Laplacian is the usual 3x3 stencil (centre -1, edges 0.2, corners 0.05), with $D_A = 1$, $D_B = 0.5$ and one explicit Euler step per pass.

Implementation Strategy (GPGPU through WebGL2):

  • State: one RGBA32F texture; R holds $A$, G holds $B$, B is a wall mask. 32-bit floats are needed because the per-step changes are tiny and half precision would stall the pattern.
  • Ping-pong: a fragment shader reads texture 0 with texelFetch and writes the next state into texture 1 through a framebuffer; then the roles swap. A feedback loop (reading and writing the same texture) is not allowed, which is why two textures are needed.
  • JavaScript's role: it only runs the frame loop (several simulation steps per frame), turns mouse movement into a brush segment, sets uniforms, and finally draws the state to the screen with a second shader.
  • Boundaries: the grid wraps around (a torus) using integer modulo on the texel coordinates.

Enhancements and their effect:

  1. Parameter map. Instead of one global $(f, k)$, the shader can compute $k$ from the x coordinate and $f$ from the y coordinate of each pixel ($f \in [0.010, 0.080]$, $k \in [0.045, 0.070]$). One frame then shows a whole slice of the parameter space, and the hover readout in the demo prints the $(f, k)$ under the cursor. Effect: the different regimes appear side by side with the borders between them, which is much easier to study than switching sliders one value at a time.
  2. Walls drawn with the mouse. A wall flag lives in the B channel of the state. Neighbours that are walls either absorb (they count as $A = 1, B = 0$, so $B$ is drained at the wall) or reflect (a wall neighbour is replaced by the cell's own value, i.e. zero flux). Effect: reaction fronts stop at or slide along obstacles, and a gap in a wall acts as a nozzle (see the map figure below).
  3. Anisotropic diffusion. The horizontal and vertical edge weights become $0.2\,(1 + a)$ and $0.2\,(1 - a)$ for an anisotropy $a \in [-0.8, 0.8]$. Their sum stays the same, so the stencil is still normalised. Effect: diffusion is faster along one axis and the stripes line up along that axis.
    To check this with a number and not only by eye, I ran the coral preset for 20 000 steps and measured the ratio of the average vertical to the average horizontal brightness gradient (about 1 means no preferred direction, above 1 means horizontal stripes): $a = 0$ gives 0.95-1.07, $a = 0.6$ gives 1.5-1.7 (stripes run horizontally, the fast direction), and $a = -0.6$ gives 0.63-0.66 (stripes run vertically). The effect is clear in the numbers but only moderate to the eye: the pattern is still a labyrinth, just with a preferred direction.
    At $a = 0.8$ the pattern breaks down completely: within about 3 000 steps $B$ fills almost the whole grid and only thin, jagged fronts remain. Here the vertical weight $0.2 \cdot 0.2 = 0.04$ is smaller than the diagonal weight 0.05, so the 3x3 stencil is no longer a good approximation of the Laplacian, and this is most likely a numerical artefact rather than physics. The useful range of the slider is therefore about $|a| \le 0.6$.
  4. Rendering. Three views: a thermal palette, a plain grayscale one, and a "relief" view that treats $B$ as a height field, builds a normal from the finite differences and applies diffuse plus specular lighting. It changes nothing in the physics, but it makes the thickness of the fronts visible (compare the two coral figures).
  5. Interactive controls: presets, sliders for $D_A$, $D_B$ and the number of steps per frame, grid size 256/512/1024, pause, reset that keeps the walls, and a seeding brush.

What the figures show:

  • Coral preset: it grows into a maze of stripes with dead ends, branching and occasional closed loops, which matches the "coral" name of the preset.
  • Parameter map: on the left, where $k$ is smallest, $B$ floods almost the whole region and the front simply expands; towards the right, where $k$ is larger, the same seeds stay as isolated spots and small rings, with elongated fingers in the transition zone. The chemistry is identical everywhere, only $(f, k)$ changes with position.
  • Walls: the flooded region on the left stops at the absorbing wall, and the fingers on the right are concentrated around the gap, which is the only place where activity can pass.
  • Absorbing vs reflecting walls: I repeated the same setup (parameter map, the same two walls with a gap, 15 000 steps) with both wall types, see the two figures below. With absorbing walls $B$ is drained at the wall, so a thin depleted strip runs along both sides of it (the bright rim in the relief view) and the patterns keep a small distance from the wall. With reflecting walls nothing is lost at the wall: the flooded region and the stripes touch it directly, stripes often meet it at a right angle (the typical picture for a zero-flux boundary), and the flood that passes the gap spreads up along the far side of the upper wall instead of staying near the gap.
  • Preset names: "mitosis" fits well. After about 4 000 steps every seed has split into small groups of spots, and the spots keep dividing until, after 20 000 steps, the whole grid is a dense packing of spots. "Maze" gives a labyrinth of stripes, but it looks very similar to the coral preset: both values lie in the same stripe regime, so the names are only approximate (which is why the demo labels the presets "approx.").

Core of the simulation shader (the full source is in index.html):

// neighbour value; walls either absorb (A=1,B=0) or reflect (copy of centre = zero flux)
vec2 nb(ivec2 q, vec2 centre){
  vec4 v = texelFetch(uState, (q + uSize) % uSize, 0);
  if (v.b > 0.5) return (uReflect == 1) ? centre : vec2(1.0, 0.0);
  return v.rg;
}

void main(){
  ivec2 p = ivec2(gl_FragCoord.xy);
  vec4 c = texelFetch(uState, p, 0);
  float wall = c.b;
  vec2 ab = c.rg, nx = vec2(1.0, 0.0);

  if (wall < 0.5) {
    float wh = 0.2 * (1.0 + uAniso), wv = 0.2 * (1.0 - uAniso);
    vec2 lap = -ab
      + wh * (nb(p + ivec2(-1, 0), ab) + nb(p + ivec2(1, 0), ab))
      + wv * (nb(p + ivec2(0, -1), ab) + nb(p + ivec2(0, 1), ab))
      + 0.05 * (nb(p + ivec2(-1,-1), ab) + nb(p + ivec2(1,-1), ab)
              + nb(p + ivec2(-1, 1), ab) + nb(p + ivec2(1, 1), ab));

    float f = uF, k = uK;
    if (uMap == 1) {                       // parameter map
      vec2 uv = (vec2(p) + 0.5) / vec2(uSize);
      k = mix(uKRange.x, uKRange.y, uv.x);
      f = mix(uFRange.x, uFRange.y, uv.y);
    }
    float A = ab.x, B = ab.y, r = A * B * B;
    nx = ab + uDt * vec2(uDa * lap.x - r + f * (1.0 - A),
                         uDb * lap.y + r - (k + f) * B);
    nx = clamp(nx, 0.0, 1.0);
  }
  // ... brush (seed B / draw wall / erase wall) ...
  o = vec4(nx, wall, 1.0);
}

Bonus: the same simulation on CPU Web Workers vs the GPU

Objective:

To see what "one thread per pixel" actually buys, I ran the identical Gray-Scott step (same stencil, $f = 0.0545$, $k = 0.062$, $D_A = 1$, $D_B = 0.5$, same start state) in two ways: on the CPU with a pool of Web Workers, and on the GPU with the pixel shader from Exercise C.

CPU parallelisation strategy:

  • Domain decomposition: the grid is cut into horizontal strips, one per worker.
  • Halo with temporal blocking: each worker receives its strip plus 10 extra rows above and below and runs 10 steps without any communication. Every step invalidates one more outer row, so after 10 steps exactly the core rows are still correct. Only then are the strips copied back and the next round starts. This replaces a message exchange on every step by one on every tenth step.
  • No shared memory: SharedArrayBuffer requires cross-origin isolation, which a page opened from file:// does not have, so data is copied with postMessage (transferable buffers). That copy is part of the measured CPU time.
  • GPU timing: a 1-pixel readPixels at the end forces the queued work to finish; without it the timer would only measure command submission.

Correctness check:

The strip decomposition was compared with a naive reference that wraps around in both directions (verify_strips.js, 64x64 grid, 30 steps). For 1, 3, 4 and 7 strips the maximum absolute difference was exactly 0, so the halo scheme reproduces the sequential result bit for bit.

Empirical Measurements:

Machine: 14 logical cores (navigator.hardwareConcurrency), integrated Intel GPU (WebGL renderer: ANGLE, Direct3D 11), Chromium-based browser. Grid 512 x 512, 100 steps. The CPU numbers jumped quite a lot between runs (one worker took anywhere from 734 to 1351 ms), so the table shows the median of 5 runs. The GPU time was stable (94-98 ms).

Analysis:

  • The workers scale, but far from ideally. 8 workers give 3.5x instead of 8x, and going from 8 to all 14 logical cores makes it slower (2.8x). The main reason is the halo: every strip carries 2 x 10 extra rows that are computed only to be thrown away. With 8 strips of 64 rows that is about 30% redundant work, with 14 strips of about 36 rows it is already more than 50%. On top of that, every round the main thread cuts the grid into jobs, the data is copied to the workers and back (no SharedArrayBuffer on file://), and the strips are stitched together on one thread. This serial part does not shrink when workers are added (Amdahl's law).
  • Not all cores are equal. The 14 logical cores are not 14 identical fast cores, and the browser, the OS and the GPU driver also need CPU time, so the last workers add little. The best result came from 8 workers on all three grid sizes except the smallest one.
  • The run-to-run noise is a CPU effect. Turbo frequency, heat and background load change the CPU timing by almost 2x between runs, while the GPU stayed within a few percent.
  • Even an integrated GPU wins. The shader is 8x faster than one worker and 2.3-3.2x faster than the best worker configuration, with a fraction of the code complexity: no strips, no halos, no copying. Every pixel is simply its own thread.
  • The GPU likes bigger problems. Its throughput grows from 207 to 333 million cell updates per second when the grid grows from 256 to 1024, because the fixed cost of each draw call is spread over more pixels. The CPU throughput per configuration stays roughly flat. With a discrete GPU the difference would be much larger.
  • For JavaScript in general: Web Workers are easy to start, but without shared memory the communication cost dominates quickly. For a stencil computation like this one the GPU is clearly the right tool, even from plain JavaScript.

Hurdles, alternatives considered and why I chose this approach

Hurdles I ran into:

  • WebCL does not exist anymore. The task mentions WebCL, but no current browser supports it. The way out was to do general-purpose computation with WebGL2 fragment shaders: the state of the simulation is a texture, and "drawing" one full-screen triangle runs the update for every pixel in parallel.
  • A shader cannot read and write the same texture. This is not allowed (feedback loop), so the simulation uses two textures and swaps them after every step (ping-pong).
  • Rendering into float textures is an extension. WebGL2 can create RGBA32F textures but cannot draw into them without EXT_color_buffer_float. With 8-bit or half precision the tiny per-step changes of Gray-Scott get rounded away and the pattern stalls, so the demo checks for the extension and shows an error instead of silently producing garbage.
  • Two coordinate systems. gl_FragCoord starts at the bottom-left, while the Mondrian composition and the mouse events use the top-left. Forgetting the flip mirrors the painting and makes the brush draw in the wrong place.
  • Measuring GPU time is tricky. WebGL calls only queue work, so a plain timer measured almost nothing. A 1-pixel readPixels at the end forces the GPU to finish before the timer stops.
  • Web Workers from a local file. A page opened by double-click (file://) cannot load a separate worker script, so the worker code is built from the same function as a string and started through a Blob URL. The same page also has no cross-origin isolation, so SharedArrayBuffer is unavailable and data has to be copied between threads. To pay for the copy less often, each worker gets 10 extra halo rows and runs 10 steps per round instead of 1.
  • Checking that the parallel CPU version is correct. Off-by-one errors in the halo are easy to make and hard to see in a picture, so I wrote verify_strips.js, which compares the strip version with a simple sequential one in Node.

Alternatives I considered:

  • WebGPU compute shaders. This is the modern successor of WebCL and the closest match to "parallel computing": real compute kernels, storage buffers, workgroups and shared memory. I stayed with WebGL2 because the Book of Shaders and the Amanda Ghassaei examples are built on it, and because it runs in every browser. A WebGPU version would be the natural next step.
  • Libraries (three.js, regl, p5.js, gpu.js). three.js even has a ready-made GPUComputationRenderer for ping-pong simulations, and gpu.js turns a JS function into a shader automatically. I decided against them on purpose: the goal was to see how much raw JavaScript and WebGL can do and what the GPU plumbing actually looks like, not to hide it behind a library.
  • Modifying an existing simulation instead of writing one. The task allows both. Writing Gray-Scott from scratch was small enough (the core shader is about 30 lines) and made it easier to add walls, the parameter map and anisotropy without fighting someone else's code structure.
  • A local server with SharedArrayBuffer. Serving the page with COOP/COEP headers would let workers share memory and avoid the copies. I chose a single index.html that opens with a double click and needs no setup, and accepted the copy cost (it is measured and visible in the benchmark).
  • step() instead of smoothstep() for the rectangles. step(), as in the book, gives jagged edges. smoothstep() gives anti-aliased edges and a softness slider for almost no extra cost.

Conclusion on JavaScript:

For shader graphics JavaScript turned out to be a very practical choice: the shader itself is the same GLSL as anywhere else, and JS only needs a few dozen lines of setup. For parallel computing it is realistic too, but with caveats: on the GPU you have to think in textures and draw calls (WebGL) or move to WebGPU, and on the CPU Web Workers work well only if you keep communication rare, because without SharedArrayBuffer every exchange is a copy.
