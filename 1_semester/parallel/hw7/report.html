Exercise 7.1: Parallel matrix multiplication using ring communication

Algorithm (task7_1.py, ring_matrix_multiplication)

  • Rank $p$ owns $A_p$ = rows $p n \ldots (p+1) n - 1$ of $A$ (shape $n \times N$, stationary) and initially $B_p$ = the matching column block of $B$ (shape $N \times n$), with $n = N/P$. Both are converted to contiguous float64 buffers.
  • It allocates C_local of shape $n \times N$: the complete row block $p$ of $C$.
  • At step $s = 0, \ldots, P-1$ the rank holds the original block $B_q$ with $q = (p - s) \bmod P$ and computes $C_{p,q} = A_p B_q$ ($n \times n$), written directly into columns $q n \ldots (q+1) n - 1$ of C_local.
  • After every step except the last, the current block is passed to rank $(p+1) \bmod P$ and the next one is received from rank $(p-1) \bmod P$ with one comm.Sendrecv. Two buffers are used and swapped, so the caller's B_colbl is never overwritten.
  • After $P$ steps every block of the row is filled, and comm.Gather stacks the $P$ row blocks into the $N \times N$ matrix $C$ on rank 0 (row blocks are contiguous, so no reordering is needed). Other ranks return None.
  • The course test calls the function ring_matrix_multiplier, so this name is provided as an alias.

The trace for $P = 5$ from the assignment follows directly from $q = (p - s) \bmod P$: in step 0 every rank computes its diagonal block $C_{p,p}$, in step 1 rank 0 computes $C_{0,4}$, rank 1 $C_{1,0}$ and so on, and after 5 steps every rank has visited all 5 column blocks exactly once.

Correctness tests (a7_test.py)

All ranks generate the same full matrices from a fixed seed and take their own blocks. Rank 0 compares the result with A @ B using np.testing.assert_allclose(rtol=1e-10, atol=1e-12). Cases: $N = P$ (one row per rank), identity times random, random times identity, zero times random, a matrix of known integers times its transpose, the random $n = 3$ case of the course test, a dense $64P \times 64P$ case and, for $P = 1$, a $2 \times 2$ example checked by hand. Every test also checks that the input block was not modified. The same cases run for all square implementations; four non-square cases are added for Bonus B. The tests were run on the laptop ($P = 1, 2, 4$) and on the server ($P = 1, 2, 3, 4, 8, 16$; $P = 3$ checks a ring with an odd number of ranks).

Question 7.1a: Why is one Gather at the end sufficient?

Every block $C_{p,q}$ is computed exactly once, by the rank that owns row block $p$, and it is final at that moment: no later step changes it, and no other rank needs it during the computation (the ring only moves blocks of $B$, never blocks of $C$). The result simply accumulates in C_local, which after $P$ steps holds the complete row block. Gathering after every step would send the same total amount of data, but as $P$ times more, smaller messages with $P$ times the latency, and it would add a collective synchronisation of all ranks to every step, so ranks could no longer proceed at their own pace between the neighbour exchanges.

Question 7.1b: Why does Sendrecv help avoid deadlocks?

In the ring every rank sends to its right neighbour and receives from its left neighbour at the same time. With a naive blocking Send followed by Recv, every rank first calls Send. A blocking send may only return when the data has been delivered or buffered; for large messages MPI uses a rendezvous protocol and waits until the receiver has posted the matching Recv. But every rank is still inside its own Send, nobody has reached Recv, and all ranks wait for each other forever. Such code often works for small blocks (they fit into the internal eager buffer) and then hangs once the matrices get larger, which makes the bug dangerous. Sendrecv hands both operations to MPI at once, so the library can progress the send and the receive together and no cyclic wait can occur. The alternatives would be ordering by rank parity (even ranks send first, odd ranks receive first) or nonblocking calls, as in Exercise 7.2.

Exercise 7.2: Communication-calculation overlap

Implementation (task7_2.py, ring_matrix_multiplication_nb)

  • Double buffering: B_current = B_colbl.copy() and B_next = np.empty_like(B_current).
  • On every step except the last: post Irecv into B_next from the left neighbour, post Isend of B_current to the right neighbour, then compute $A_p \cdot$ B_current into the correct columns of C_local, then MPI.Request.Waitall on both requests and swap the buffers.
  • On the last step the final block is computed without posting another exchange.
  • Buffer safety: during the multiplication B_current is only read, which is allowed while it is the buffer of a pending Isend; it is not overwritten until the send has completed and the buffers are swapped. B_next is not read before its Irecv has completed. A single in-place buffer would not work here, because the incoming block would overwrite the block that is being multiplied and sent.

7.2a: Equivalence

For every test case and every $P$ the test prints a direct comparison of the blocking and nonblocking results on rank 0: all of them were bitwise identical on both machines. This is expected, because both versions perform exactly the same multiplications in the same order; only the timing of the communication differs.

Answer. The $P = 1$ column is the control: with one rank there is no communication, both versions run the same single multiplication, so any difference there is pure measurement noise.

  • On the laptop overlap cannot be measured. Even at $P = 1$ the two versions differ by 10 to 19%, and all differences at $P = 2$ and $4$ go in both directions within this range.
  • On the server the noise floor is about 1% for $N \ge 1024$, so small effects become visible. When computation dominates (large $N$, $P \le 8$) the two versions are equal within 0 to 4%: there is little communication to hide. When $P$ grows to 16 to 64 and the communication share rises, the nonblocking version is faster in most cases, by 1 to 14% and by 20% at $N = 4096$, $P = 32$. The exceptions are $N = 4096$ and $8192$ at $P = 64$, where it is 2 to 9% slower; with all 64 vCPUs busy there is no idle core left for the operating system and MPI progress, and the extra request handling no longer pays off. ($N = 512$ is too short, 2 to 8 ms per run, for the percentages to be reliable; even its $P = 1$ control differs by 13%.)
  • Why the gain is small even where it exists: for large $N$ one step computes much longer than it communicates (for $N = 4096$, $P = 16$: about 0.27 GFLOP per step against a 2 MB block), so even perfect overlap can only save a few percent. In addition, starting a nonblocking operation does not guarantee asynchronous progress: blocks of several MB use the rendezvous protocol, and without a separate progress thread Open MPI advances them mainly inside MPI calls, so part of the transfer still happens in Waitall. In shared memory the transfer is also a CPU copy that competes with the multiplication for memory bandwidth.

On the laptop only 2 of the cores are performance cores, so with $P = 4$ at least two ranks run on slower efficient cores, and a 15 W chip also lowers its clock when several cores are busy, while one rank can use the full single-core turbo. The server has identical cores, every rank was pinned to its own core (--bind-to core), and the machine was otherwise idle.

4. Interpretation of the scaling

  • Near-ideal for small $P$: on the server, efficiency at $P = 2$ and $4$ is 86 to 97% for $N \ge 2048$, i.e. for large enough matrices the ring algorithm itself adds almost no cost.
  • Every $N$ has an optimal $P$, and it grows with $N$: $P = 8$ for $N = 512$ and $1024$, $P = 8$ to $32$ for $N = 2048$, $P = 16$ to $32$ for $N = 4096$ and $P = 64$ (or more) for $N = 8192$. Beyond the optimum the time increases again: for $N = 512$, 64 ranks are barely faster than one (1.13 to 1.28x).
  • Why more ranks eventually hurt: (1) the work per step shrinks with $P^2$: at $N = 512$, $P = 64$ every step multiplies an $8 \times 512$ block by a $512 \times 8$ block, which is far too small for BLAS to run efficiently; (2) the number of steps, exchanges and Python loop iterations grows with $P$, each with a fixed latency; (3) every rank must still receive the whole matrix $B$ over the ring (about $N^2$ elements per rank, independent of $P$), so the total traffic $P \cdot N^2$ grows with $P$ and competes for the shared memory system; (4) at $P = 64$ every vCPU of the virtual machine is busy, so the operating system and MPI have no spare core.
  • Superlinear speedup at $N = 8192$, $P = 4$ (5.26x, 131%): a single rank reaches only 31 GFLOP/s at $N = 8192$ against 42 GFLOP/s at $N = 4096$, while with 4 ranks each rank runs at about 41 GFLOP/s. Multiplying with two 512 MB matrices on one core is evidently less cache- and TLB-friendly than working on 4 times smaller blocks, so $T(1)$ is slower than "one quarter of the work" would suggest. The highest absolute performance measured was 575 GFLOP/s at $N = 8192$, $P = 64$ (18.6x).
  • Setup is significant: on the server distributing the matrices takes 1.0 to 3.6 s for $N = 4096$ and 14 to 22 s for $N = 8192$, more than the parallel multiplication itself. If it were included, a single multiplication would not benefit from parallelism at all; the distributed algorithm pays off when the data is already distributed or reused.

5. Analytical questions

How does the ratio of computation to ring communication change with increasing $N$? Each process performs about $2N^3/P$ floating-point operations and sends about $(P-1)N^2/P$ elements, so the ratio is $$\frac{2N^3/P}{(P-1)N^2/P} = \frac{2N}{P-1}$$ operations per transferred element. It grows linearly with $N$ and shrinks as $P$ grows. For $N = 512$, $P = 64$ it is only 16 operations per element, which matches the collapse of the speedup there; for $N = 8192$, $P = 64$ it is 260, and the speedup keeps growing up to 64 ranks. This is exactly the pattern of the optimal $P$ described above: doubling $N$ allows roughly doubling $P$ at the same ratio.

What is the approximate smallest $N$ for which the parallel version is faster? Does the answer change with $P$? On the server the parallel version was already faster at the smallest tested size, $N = 512$, for every $P$ (1.13 to 3.26x), so the break-even point lies below 512 there; the benefit at $N = 512$ is large only for $P = 4$ to $8$. On the laptop it was reliably faster only from $N = 2048$; at $N = 512$ only $P = 4$ helped and at $N = 1024$ nothing did. The answer clearly depends on $P$: for a given $N$ adding ranks helps only up to an optimum, and because the ratio $2N/(P-1)$ falls with $P$, a larger $P$ needs a larger $N$ to be worthwhile.

How do the results compare with the matrix-vector multiplication of Assignment 6?

  • Arithmetic intensity: matrix-vector performs 2 operations per 8-byte matrix element read once, so it is memory-bound; in Assignment 6 one process reached only about 5.6 GFLOP/s ($N = 4096$, 50 products in 0.30 s on the laptop). Matrix-matrix reuses each element $O(N)$ times and reaches 31 to 44 GFLOP/s on one core of either machine, so it is compute-bound.
  • Communication: in Assignment 6 every iteration communicated $O(N)$ values against $O(N^2/P)$ work; here $O(N^2)$ values per process are sent against $O(N^3/P)$ work, so the communication share falls with $N$ instead of staying constant.
  • Scaling: in Assignment 6 the laptop speedup was capped by the shared memory bandwidth (multiplication phase 1.72x at $P = 4$). The matrix-matrix product is not bandwidth-bound: on the server it reaches 3.4 to 3.7x at $P = 4$ and up to 18.6x with 64 ranks. On the laptop it stays at a similar 1.4 to 2x, but for a different reason (heterogeneous, power-limited cores instead of memory bandwidth).
Bonus A: Circulate A instead of B

Design (task7_bonus_a.py, ring_matrix_multiplication_circulate_A): rank $p$ keeps its column block $B_p$ ($N \times n$) stationary and passes row blocks of $A$ around the same ring. At step $s$ it holds the row block that originally belonged to rank $owner = (p - s) \bmod P$, because every step moves blocks one rank to the right; the owner index is therefore computed from $p$ and $s$ exactly as $q$ in Exercise 7.1, and no extra metadata has to be sent. The product $A_{owner} B_p$ is the block $C_{owner,p}$, so each rank fills one column block of $C$ (shape $N \times n$), writing rows $owner \cdot n \ldots (owner+1) n - 1$.

Assembly: column blocks of $C$ are not contiguous in a C-order matrix, so a direct Gather into $C$ is impossible. Rank 0 gathers the $P$ contiguous $N \times n$ blocks into a $(P, N, n)$ array and rebuilds $C$ with blocks.transpose(1, 0, 2).reshape(N, N), i.e. element $(i, p n + j)$ of $C$ comes from block $p$, row $i$, column $j$.

Communication: identical in volume: an $n \times N$ block of $A$ has as many elements as an $N \times n$ block of $B$, the number of exchanges is $P - 1$, and the final gather moves the same $N^2$ elements. The only extra work is the reordering copy of the whole result on rank 0.

Performance: on the laptop it was within the noise of the other versions. On the server, where small differences can be measured, it is in most configurations 2 to 10% slower than the blocking version and up to 18% at $N = 4096$, $P = 64$ (0.537 s vs 0.456 s). This is consistent with the extra reordering copy of $N^2$ elements on rank 0 (128 MB for $N = 4096$), which is serial and therefore weighs more when the parallel part gets shorter. The exceptions are $N = 2048$, $P = 16$ (0.076 s vs 0.084 s) and $N = 4096$, $P = 32$ (0.331 s vs 0.378 s), where the blocking version itself had a slow point. Correctness: all tests passed on both machines.

Bonus B: Rectangular matrices

Design (task7_bonus_b.py, ring_matrix_multiplication_rect): $A$ is $N \times K$, $B$ is $K \times M$, $C$ is $N \times M$.

  • Divisibility: $N \bmod P = 0$ and $M \bmod P = 0$. $K$ can be any positive number, because the inner dimension is never split: every block of $A$ keeps all $K$ columns and every block of $B$ keeps all $K$ rows.
  • Blocks: rank $p$ owns the row block $A_p$ of shape $(N/P) \times K$ and the column block $B_p$ of shape $K \times (M/P)$. The ring rule is unchanged: at step $s$ it computes $C_{p,q} = A_p B_q$ with $q = (p - s) \bmod P$, an $(N/P) \times (M/P)$ block, written into columns $q M/P \ldots (q+1) M/P - 1$ of the local $(N/P) \times M$ result.
  • Communication: the circulating blocks have $K M / P$ elements; the final Gather of row blocks builds the $N \times M$ result on rank 0.
  • The function infers $N$, $K$ and $M$ from the local block shapes and checks that the inner dimensions agree.

Correctness: non-square cases $N = 2P, K = 3, M = 3P$; $N = P, K = 7, M = 2P$; $N = 3P, K = 1, M = P$ (an outer product); $N = 5P, K = 40, M = 2P$, plus all square cases. All passed on the laptop ($P = 1, 2, 4$) and on the server ($P = 1, 2, 3, 4, 8, 16$).

Bonus C: Two-dimensional algorithms (Cannon, SUMMA)

Not implemented; this is a sketch of the two classical 2D algorithms. The $P$ processes form a $\sqrt{P} \times \sqrt{P}$ grid and process $(i, j)$ owns the blocks $A_{ij}$, $B_{ij}$ and computes $C_{ij}$, each of size $(N/\sqrt{P}) \times (N/\sqrt{P})$.

  • Cannon's algorithm: first an initial skew: row $i$ of $A$ is shifted $i$ positions to the left and column $j$ of $B$ is shifted $j$ positions up, so that process $(i, j)$ holds $A_{i,k}$ and $B_{k,j}$ with matching $k$. Then $\sqrt{P}$ steps follow: multiply-accumulate $C_{ij} \mathrel{+}= A \cdot B$, shift $A$ one position left within the process row and $B$ one position up within the process column. These are two rings, one per row and one per column, instead of one global ring.
  • SUMMA: in step $k$ the owner of panel $A_{ik}$ broadcasts it along process row $i$ and the owner of $B_{kj}$ broadcasts it along process column $j$; every process then adds $A_{ik} B_{kj}$ to its $C_{ij}$. It uses row and column broadcasts instead of point-to-point shifts, needs no initial skew, works for rectangular matrices and non-square grids, and is the basis of ScaLAPACK's PDGEMM.

Difference in communication: in the 1D ring every process eventually receives the whole matrix $B$: about $(P-1)N^2/P \approx N^2$ elements, independent of $P$. In Cannon's algorithm each process receives $\sqrt{P}$ blocks of $A$ and $\sqrt{P}$ blocks of $B$ of size $N^2/P$, i.e. about $2N^2/\sqrt{P}$ elements, which falls with $P$, and each message only travels between direct neighbours in the grid. The server measurements show why this matters: the 1D ring stops scaling at 8 to 32 ranks for $N \le 4096$, partly because every rank still has to receive all of $B$. With $P = 64$ Cannon would reduce the data each rank receives from about $N^2$ to $N^2/4$, and the steps from 63 to 8. For $P = 4$, as on the laptop, $2N^2/\sqrt{P} = N^2$ gives no saving, and the extra skew and two sets of exchanges would only add overhead.

Limitations
  • The laptop could only run $P = 1, 2, 4$ without oversubscription, and its heterogeneous, power-managed cores make differences below about 20% unreliable there.
  • The server is a virtual machine: its 64 vCPUs may share physical cores or hardware threads of the host, which can affect the $P = 32$ and $P = 64$ points.
  • Both machines communicate through shared memory within one node; conclusions about overlap and communication cost do not transfer directly to a cluster with a network.
  • The server used 5 repetitions (3 for $N = 8192$) instead of 10, which was enough because its spread was small.
  • A laptop run with $N = 4096$ was started but stopped because a single configuration took 3 to 12 s per run with a very wide spread; $N = 4096$ and $8192$ were measured on the server instead.
  • The timed region includes the Python loop overhead and the final Gather, as required, but not the initial distribution.
