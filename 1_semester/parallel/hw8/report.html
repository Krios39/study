Test environment, build and design choices
  • Machine: laptop with Intel Core Ultra 7 265U (hybrid CPU: 2 performance, 8 efficient and 2 low-power efficient cores, 14 threads), Windows 11, about 32 GB RAM shared by CPU and GPU.
  • GPU: integrated Intel Graphics, OpenCL 3.0 (Intel NEO driver 32.0.101.8826): 64 compute units, maximum work-group size 1024, 64 KB local memory, about 34 GB of (shared) global memory.
  • NPU: Intel AI Boost, used through OpenVINO 2026.4.1 (bonus).
  • Compiler for 8.1 and 8.2: g++ 16.1.0 (MSYS2 UCRT64) with -O3 -march=native -fopenmp -std=c++17, linked statically except for OpenCL.dll, so the executables only need the OpenCL runtime that comes with the graphics driver. OpenCL headers and import library: Khronos packages from MSYS2 (opencl-headers, opencl-icd).
  • Compiler for the bonus: MSVC 14.51 (Visual Studio 2026 Build Tools), because the OpenVINO binaries are built with MSVC and cannot be linked with g++.
  • OpenMP: 14 threads (the default, one per hardware thread).
  • Data: single-precision float matrices (as in the reference loop of the assignment), row-major, filled with uniform random values in $[0, 1)$ from a fixed seed; the same inputs for all versions.
  • Timing: std::chrono::steady_clock on the host. For OpenCL two times are reported: total = buffer allocation, writing A and B, kernel, reading C (what a user of the function waits for), and kernel only = the kernel execution measured on the device with OpenCL profiling events. Every OpenCL configuration is run once as a warm-up (not recorded) and then 3 times; CPU versions 3 times, except the sequential version for $N \ge 2048$ (1 run, it takes 5 to 45 s). Tables show the median.

Why g++ and not Visual Studio for 8.1/8.2? The assignment suggests Visual Studio, and the bonus is built with it. For the main exercises I used g++ because the OpenMP version from Task 2.3.2 uses #pragma omp task, which needs OpenMP 3.0; MSVC's standard /openmp only implements OpenMP 2.0 without tasks. g++ supports both versions of my OpenMP code with the same compiler and flags as the sequential and OpenCL host code, which keeps the comparison fair. The OpenCL code itself is plain OpenCL/C and compiles unchanged with MSVC.

Exercise 8.1: Sequential vs OpenMP vs OpenCL

Implementations (task8_1.cpp, matmul_kernels.cl)

  • Sequential C++: the triple loop in i-k-j order: for every row $i$ and every $k$, the scalar $A_{ik}$ is multiplied with row $k$ of $B$ and added to row $i$ of $C$. The innermost loop runs over contiguous memory, so the compiler vectorises it with AVX2 (checked with -fopt-info-vec; __restrict pointers were needed to remove the aliasing check). It performs exactly the computation of the reference loop in the assignment, only in a cache-friendlier order for row-major storage.
  • OpenMP parallel for: the same loop with the rows of $C$ distributed statically over the threads. Each thread writes only its own rows, so no synchronisation is needed.
  • OpenMP tasks (my solution of Task 2.3.2): the recursive divide-and-conquer algorithm from homework 2, rewritten for float and flat arrays: the three dimensions are halved, the four independent sub-products are created as tasks, taskwait, then the second four; blocks below 32768 multiply-adds are computed directly.
  • OpenCL kernel matmul_tiled: 2D NDRange with one work-item per element of $C$ and 16 x 16 work-groups. The group loads a 16 x 16 tile of $A$ and of $B$ into __local memory, synchronises with barrier, and every work-item accumulates 16 products from local memory; then the next pair of tiles. Each element of $A$ and $B$ is thus read from global memory $N/16$ times instead of $N$ times.
  • Host code: selects the first GPU of all OpenCL platforms (not blindly platform 0), builds the kernel file with the tile size as a compile-time define (-DTS=16, 8 if a device allowed less than 256 work-items per group) and prints the build log if compilation fails. A profiling-enabled command queue gives the kernel time.
  • Correctness: every version is compared with the sequential result (maximum difference divided by the maximum value of $C$). All differences were exactly 0: every version adds the products for one element in the same order of $k$, so even the GPU reproduces the CPU result bit for bit. Exercise 8.2 additionally checks against a double-precision reference.

Discussion

  • OpenCL is by far the fastest: 17 to 19x faster than the sequential code and about 9x faster than the best OpenMP version for $N \ge 2048$ (4096: 2.35 s against 20.6 s). The kernel itself runs at a steady 67 to 69 GFLOP/s from $N = 1024$ upward (107 GFLOP/s at $N = 512$, where everything fits into the GPU caches).
  • Transfers matter for small sizes: at $N = 512$ the copies are only 1 ms, but at $N = 1024$ the total (0.114 s) was 3.6 times the kernel time (0.031 s); allocating buffers and copying 12 MB should take much less, so this one value probably contains a one-off delay of the driver. From $N = 2048$ on, the transfers grow with $N^2$ while the work grows with $N^3$, and they cost only 15 to 20% of the total.
  • The CPU versions are memory-bound: the sequential code reaches 11 GFLOP/s at $N = 512$ (the 1 MB matrix $B$ still fits in the caches), but only 3 to 4 GFLOP/s for larger $N$: for every row of $C$ the whole matrix $B$ is streamed from main memory again. OpenMP parallel for multiplies the arithmetic power but all threads stream $B$ through the same memory interface, so it only reaches 1.8 to 2.2x with 14 threads. At $N = 512$ it is even slower than one thread (and very noisy: 0.029 to 0.389 s), because 0.02 s of work is too little to amortise starting and synchronising 14 threads on a laptop with performance and efficiency cores.
  • The task-based OpenMP version from 2.3.2 is the slowest for small $N$ and only reaches the sequential speed at $N = 2048$ to $4096$ (1.1x). Its leaves are tiny (about 32 x 32 x 32), so the vectorised inner loop is only 32 floats long and the cost of creating and scheduling tens of thousands of tasks dominates; in addition, each taskwait between the two halves of the $k$ range halves the available parallelism. Its recursive blocking would help cache reuse, but with this grain size the overhead wins.
  • Why the GPU wins: 64 compute units execute thousands of work-items at once, and the tiled kernel reuses every loaded element 16 times from fast local memory, which turns a memory-bound problem into a mostly compute-bound one. The GPU shares the same main memory with the CPU, so the advantage comes from the parallel hardware and the data reuse, not from faster memory.
  • How far from the hardware limit? The OpenVINO measurement in the bonus reaches 721 GFLOP/s in float on the same GPU, i.e. my simple tiled kernel uses only about a tenth of what the device can do. The missing steps would be register blocking (each work-item computing several elements of $C$), vector loads and the use of sub-groups.
Exercise 8.2: Two kernels with different efficiency

Design (task8_2.cpp, kernel_A and kernel_B in matmul_kernels.cl)

Both kernels compute $C = A \cdot B$ with a 1D NDRange of $N^2$ work-items, one per element of $C$ (work-item gid computes row gid / N, column gid % N). local_item_size is the work-group size of this 1D range, exactly as in the vector-add example of the course.

  • kernel_A (simple): every work-item reads its whole row of $A$ and column of $B$ directly from global memory. Run with local_item_size = 2 for all sizes.
  • kernel_B (local memory): the $L$ work-items of a group are $L$ neighbouring elements of the same row of $C$, so they all need the same row of $A$. The group loads the row of $A$ in chunks of $L$ values into __local memory (one value per work-item), synchronises, and every work-item uses the whole chunk; the reads of $B$ go to $L$ consecutive columns, so they are coalesced. Each value of $A$ is read from global memory once per group instead of $L$ times. Run with $L = 8, 32, 64$ for $N = 1024, 2048, 4096$; the local buffer size is passed at run time with clSetKernelArg(kernel, 4, L * sizeof(float), NULL).
  • Host flow: for every size: write A and B, run kernel_A, read C back to the host; then write A and B again, run kernel_B, read C. So kernel A returns its output before kernel B starts, and the host communicates synchronously with each kernel (blocking writes and reads).
  • Checks: the host verifies that $L$ does not exceed the device limit (1024) and divides $N$. Every result is checked against 256 random elements recomputed on the CPU in double precision (relative error about $10^{-6}$, the expected float rounding) and the two kernels are compared with each other (identical).

Discussion

  • kernel_B is faster everywhere, and the gap grows with $N$: 1.6x at 1024, 5.1x at 2048, 8.8x at 4096. kernel_A even gets slower per operation as $N$ grows (9.8 to 4.4 GFLOP/s), while kernel_B gets faster (15.9 to 38.7 GFLOP/s).
  • Why kernel_A is slow: Intel GPUs execute work-items in SIMD groups of 8 to 32 lanes. A work-group of only 2 work-items occupies a whole hardware thread with just 2 active lanes, so most of the vector units stay idle. In addition, every work-item streams a whole row of $A$ and column of $B$ from global memory without any sharing, so for larger $N$ the data no longer fits in the GPU caches and memory traffic dominates.
  • Why kernel_B is faster: larger groups fill the SIMD lanes, the $L$ work-items share one load of $A$ through local memory, and neighbouring work-items read neighbouring addresses of $B$ (coalesced access). The larger $L$, the more reuse of $A$, which is why its efficiency grows from $L = 8$ to $L = 64$.
  • Two effects are mixed: as specified, kernel_B differs from kernel_A both in the code (local memory) and in the work-group size, so the measured ratio is the sum of both. The work-group size alone already explains a large part (idle SIMD lanes at $L = 2$), the local memory adds the reuse of $A$.
  • Both are slower than the 2D tiled kernel of 8.1 (67 to 69 GFLOP/s): kernel_B only reuses $A$, while the tiled kernel reuses both $A$ and $B$ in a 16 x 16 tile.
  • Transfers: the difference between total and kernel time is the synchronous host communication (allocating buffers, writing 2 matrices, reading 1). It is 0.02 to 0.75 s here and becomes negligible compared with the slow kernel_A at larger $N$, but is up to 30% of kernel_B's total at $N = 1024$.
Bonus 8: Matrix multiplication on CPU, GPU and NPU with OpenVINO

Implementation (task8_bonus.cpp): an OpenVINO model with two f32 parameters of shape 2048 x 2048 and one MatMul node is compiled for every available device. The same input tensors (uniform random values, fixed seed) are used for all devices. After one warm-up inference, 20 inferences are timed and the median is reported. The CPU result (f32) is the reference for the error of the other devices. The GPU is measured twice: with its default settings and with ov::hint::inference_precision = f32, because by default the OpenVINO GPU plugin silently computes in f16. The NPU only supports f16 inference. OpenVINO 2026.4.1 found all three devices.

Discussion

  • NPU and GPU are the fastest devices: the NPU (16.5 ms) and the GPU in f16 (18.1 ms) are about 4.5x faster than the CPU running OpenVINO on all cores (78 ms). Between NPU and GPU f16 the difference is within the spread of the NPU runs (14 to 28 ms; in an earlier test run with only 5 repetitions the NPU median was even 34 to 64 ms), so they should be considered roughly equal for this size.
  • Precision is part of the comparison: the NPU and the default GPU compute with half-precision inputs. With the same f32 precision as the CPU, the GPU needs 23.8 ms, 1.3x more than in f16, and is still 3.3x faster than the CPU. The NPU error (4.7e-4) is much smaller than the GPU f16 error (6.1e-3), which suggests that the NPU accumulates the products at higher precision; both are acceptable for neural-network inference, the main use of the NPU, but not for exact numerical work.
  • Libraries vs my own code: on the CPU, OpenVINO (oneDNN with cache blocking, AVX2 micro-kernels and all cores) is 68x faster than my sequential loop and 38x faster than my OpenMP version. On the GPU, the optimised OpenVINO kernel in f32 is about 11x faster than my tiled OpenCL kernel. This shows how much performance depends on blocking for caches and registers, not only on parallelism.
  • Compile time: compiling the model for GPU and NPU takes about 1.2 to 1.4 s (several seconds on the very first run before the driver cache was filled), against 0.03 s on the CPU. For a single multiplication this setup would cost far more than the computation; the accelerators pay off when the compiled model is reused many times, which is exactly the inference scenario they are designed for.
  • Energy: not measured, but the NPU is designed to run such workloads at a fraction of the power of the GPU, so reaching the GPU's speed is a good result for it.
Summary and limitations
  • For $N = 4096$ the OpenCL version needs 2.35 s including all transfers, the best OpenMP version 20.6 s and the sequential version 44.8 s: the GPU is 19x faster than sequential and about 9x faster than OpenMP on this laptop.
  • Good GPU performance requires the right work-group size and data reuse in local memory: the same multiplication was 8.8x faster with kernel_B than with kernel_A, and the tiled kernel was faster still.
  • The CPU and the integrated GPU share main memory, the CPU has heterogeneous cores and the laptop adjusts its clock to temperature and power, so individual runs vary (for example OpenMP at $N = 512$: 0.029 to 0.389 s); medians of only 3 runs (1 for the long sequential runs) were used to keep the total run time reasonable.
  • Only one GPU and one machine were available; a discrete GPU with its own memory would have much higher transfer costs over PCIe but also much higher compute and memory bandwidth.
