Task 2.2: OpenMP Matrix Multiplication Scaling & Scheduling

Environment & Setup:

  • Compiler: MinGW-w64 g++ (GCC) with flags -O3 -fopenmp -Wall -Wextra
  • OpenMP Specification: _OPENMP = 202111 (OpenMP 5.2)
  • Thread Affinity: OMP_PLACES=cores and OMP_PROC_BIND=close were set. Note: MinGW GCC runtime on Windows returned libgomp: Affinity not supported on this configuration, falling back to OS-level thread scheduling.
  • Matrix Size & Memory Fix: Evaluated at $NRA = 500$, $NCA = 500$, $NCB = 500$. With fixed stack arrays, three $500 \times 500$ matrices of double require $\approx 6\text{ MB}$, exceeding the default Windows stack size ($1\text{ MB}$) and causing an immediate silent crash / stack overflow. To resolve this, memory allocation was rewritten using dynamic heap memory via malloc()/free() with flat 1D indexing.
  • Timing Methodology: 1 warm-up run + 5 measured runs; reported median time. Matrix initialization, verification, and console printing are excluded from timing via omp_get_wtime().

Deliverable Question 1: How do threads get scheduled?

The code uses #pragma omp for schedule(static, 10). The outer loop of 500 rows is split into chunks of 10 rows and distributed to threads in a round-robin fashion (Thread 0 takes rows 0–9, Thread 1 takes 10–19, etc.). Since each row requires the exact same amount of multiplication steps, all threads get an even amount of work without any extra scheduling overhead.

Deliverable Question 2: Did you gain any (average) speedup?

Yes, increasing the thread count consistently makes the program faster. We get almost ideal scaling on 2 threads (1.96×), reaching 3.24× on 6 threads. However, scaling slows down after 2 threads for two simple reasons:

  • Short Runtime: The whole computation takes only 17–55 milliseconds, so thread creation, synchronization, and barrier overhead start to eat up a noticeable chunk of the runtime.
  • Cache Misses: In the classic $i \to j \to k$ loop order, elements of matrix $B$ are accessed down columns rather than along rows, which causes frequent CPU cache misses and saturates memory bandwidth when several threads run in parallel.

Correctness Verification: Output matrix $C$ was verified using the closed-form summation formula:

$$c_{i,j} = \sum_{k=0}^{NCA-1} (i + k)(k \cdot j) = j \left[ i \sum_{k=0}^{NCA-1} k + \sum_{k=0}^{NCA-1} k^2 \right]$$

All matrix values matched the expected results within a $10^{-3}$ tolerance (Correct: YES on all runs).

Exercise 2.3: Recursive Matrix Multiplication (Cache-Oblivious vs. Naive)

Overview & Algorithm Analysis:

  • Dynamic Allocation: Matrices are allocated dynamically using Allocate2DArray() (contiguous row buffer with row pointer table in 2DArray.h), completely eliminating the stack memory limits encountered in Exercise 2.2.
  • Cache-Oblivious Divide-and-Conquer: matmultr divides matrices into quadrants ($2 \times 2$ block partition) until the submatrix footprint drops below GRAIN = 32768 ($\approx 256\text{ KB}$), where it switches to matmultleaf. This keeps active data within L2/L3 cache lines.
  • Dependency / Data Race Observation: The 8 recursive calls are not mutually independent. Pairs update identical target quadrants of matrix $C$:
    • $C_{00} = A_{00}B_{00} + A_{01}B_{10}$
    • $C_{01} = A_{00}B_{01} + A_{01}B_{11}$
    • $C_{10} = A_{10}B_{00} + A_{11}B_{10}$
    • $C_{11} = A_{10}B_{01} + A_{11}B_{11}$
    To parallelize this safely with OpenMP tasks without data races, execution must be split into two disjoint 4-task phases separated by a #pragma omp taskwait barrier.

Deliverable Observations & Performance Analysis:

  • Small to Medium Matrices ($N = 500, 1000$): The recursive approach clearly outperforms the naive triple loop, delivering an algorithmic speedup of 1.7× and up to 2.7× purely through memory hierarchy efficiency. In matmult1, the column-strided traversal of matrix $B$ ($B[k][j]$) triggers non-stop cache misses once the matrix exceeds cache capacity. By breaking the matrix into sub-blocks smaller than GRAIN = 32768, matmultr ensures that working submatrices fit entirely into L2/L3 cache, maximizing spatial and temporal locality.
  • Large Matrices ($N = 1500$): The speedup degrades to 1.0× (5.131 s vs 4.930 s). At dimensions of $1500 \times 1500$, non-power-of-two matrix subdivisions create odd partitioning sizes and a significantly deeper recursion tree. The recursion call overhead, function frame setup, and index recalculation begin to rival the benefits of cache reuse. Furthermore, at this matrix size, the total memory working set exceeds available last-level cache, making main RAM memory bandwidth the governing bottleneck for both implementations.
Task 2.3.1: Testing the Serial Program (Algorithmic Speedup)

1. Algorithmic Speedup Calculation:

Using the provided formula for algorithmic speedup:

$$S_{\text{algorithmic}} = \frac{T_{\text{naive serial}}}{T_{\text{recursive serial}}}$$
Matrix Size ($M \times N \times P$) Naive Serial Time ($T_{\text{naive}}$) Recursive Serial Time ($T_{\text{recursive}}$) $S_{\text{algorithmic}}$
$500 \times 500 \times 500$ 0.096 s 0.055 s 1.75×
$1000 \times 1000 \times 1000$ (default) 0.908 s 0.331 s 2.74×
$1500 \times 1500 \times 1500$ 4.930 s 5.131 s 0.96×

For the default $1000 \times 1000$ case, the recursive implementation yields a ~2.74× speedup over the naive 3-loop implementation purely algorithmically, prior to any OpenMP parallelization.

2. Explanation of the Speedup:

Both algorithms execute the exact same number of floating-point arithmetic operations ($\Theta(N^3)$ multiplies and adds). The performance difference is entirely caused by cache locality and memory hierarchy behavior (Cache-Oblivious Design):

  • Naive 3-loop (matmult1) has poor cache locality: In C/C++, matrices are stored in row-major order. The innermost loop calculates A[i][k] * B[k][j]. While A[i][k] accesses contiguous memory along a row, B[k][j] accesses elements down a column with a large stride ($N \times 8\text{ bytes}$). For a $1000 \times 1000$ matrix, one row is $\approx 8\text{ KB}$, and the entire matrix is $8\text{ MB}$ (exceeding L1 and L2 cache sizes). Every increment of $k$ triggers a cache line fetch from slow memory/L3 cache, causing catastrophic L1/L2 cache misses.
  • Recursive divide-and-conquer (matmultr) achieves cache reuse: The algorithm recursively subdivides matrices into smaller quadrants until the subproblem size drops below GRAIN = 32768 elements ($\approx 256\text{ KB}$). Submatrices of this size fit entirely within the fast CPU L2/L1 cache. Once loaded into cache, the sub-blocks are reused repeatedly by matmultleaf() without fetching data back and forth from main RAM, drastically cutting down memory bus stalls.
Task 2.3.2: Parallelisation using OpenMP Tasks

Parallel Work-Sharing Strategy:

  • Task Tree Construction: The parallel region is spawned via #pragma omp parallel, with the root call to matmultrec() initiated inside a #pragma omp single directive so that exactly one thread creates and enqueues initial tasks.
  • Data Race Resolution (Two-Phase Execution): At each recursive branch, pairs of recursive calls accumulate into the exact same quadrant of matrix $C$ ($C_{00}, C_{01}, C_{10}, C_{11}$). Spawning all 8 tasks simultaneously results in severe concurrent write hazards (data races). To ensure memory correctness, the 8 subproblems are divided into two rounds of 4 independent tasks separated by an explicit #pragma omp taskwait barrier:
    • Round 1: 4 parallel tasks update $C_{00} \mathrel{+}= A_{00}B_{00}$, $C_{01} \mathrel{+}= A_{00}B_{01}$, $C_{10} \mathrel{+}= A_{10}B_{00}$, $C_{11} \mathrel{+}= A_{10}B_{01}$.
    • #pragma omp taskwait
    • Round 2: 4 parallel tasks update $C_{00} \mathrel{+}= A_{01}B_{10}$, $C_{01} \mathrel{+}= A_{01}B_{11}$, $C_{10} \mathrel{+}= A_{11}B_{10}$, $C_{11} \mathrel{+}= A_{11}B_{11}$.
    • #pragma omp taskwait

Deliverable Question: What happens on omitting the line #pragma omp single?

Omitting #pragma omp single immediately before spawning tasks breaks the task producer-consumer model:

  • Task Explosion & Redundant Computation: Without single, every thread in the team independently calls matmultrec() and constructs its own complete recursion tree. With $p$ threads, $p$ duplicate task hierarchies are spawned simultaneously ($p \times$ more tasks), overflowing OpenMP task queues and causing huge scheduler overhead.
  • Data Race & Matrix Corruption: All duplicate tasks concurrently write and accumulate products into the same memory addresses of matrix $C$. Verification immediately fails (CheckResults flags severe mismatches), yielding completely corrupted matrix values.

The #pragma omp single directive guarantees that only one thread serves as the initial task producer, allowing the remaining threads to act strictly as workers picking up tasks from the runtime queue.
