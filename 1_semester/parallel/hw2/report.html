Exercise 2.1: OpenMP Tutorial & Learning Blog

Learning Log & How I Proceeded:

I worked through the LLNL OpenMP tutorial by Blaise Barney, focusing on shared-memory multi-threading in C/C++. Since my primary background is in full-stack software development rather than low-level HPC, learning to parallelize code via pragmas instead of managing raw worker threads or event loops was a fresh perspective. I set up my local environment on Windows with MinGW GCC (passing -fopenmp) and stepped through the fundamental concepts: fork-join thread pool models, variable scoping, and work-sharing loops.

Key Concepts Mastered:

  • Fork-Join Execution Model: The master thread spawns a pool of worker threads upon entering #pragma omp parallel and joins back after the region ends.
  • Data Scoping (shared vs private): Misconfiguring variable scope is the fastest route to subtle race conditions. Global or loop control variables must be explicitly marked private(tid, i) or declared locally inside the parallel block, while read-only or accumulator matrices are passed as shared.
  • Loop Scheduling (schedule(static, chunk) vs dynamic): In static scheduling, the compiler partitions iterations in fixed chunks ahead of time, which has virtually zero overhead for balanced workloads like matrix multiplication. dynamic handles unbalanced workloads via a shared work queue at the cost of runtime synchronization.
  • Tasks & Barriers (task, taskwait, single): Discovered how task parallelism allows recursive divide-and-conquer algorithms to run in parallel without requiring rigid loop bounds, provided dependencies are gated by barriers.
  • Essential Runtime APIs: Tested thread identification and timers: omp_get_thread_num(), omp_get_num_threads(), omp_set_num_threads(), and wall-clock benchmarking using omp_get_wtime().

Encountered Roadblocks & Solutions:

  • Unordered console output: When running the Hello World example, printf() outputs from threads appeared interleaved and out of order. At first it looked like a bug, but it is just threads concurrently competing for standard output (stdout).
  • Windows / MinGW Affinity limits: Passing OMP_PLACES=cores produced runtime warnings (libgomp: Affinity not supported) because MinGW's GCC wrapper on Windows does not support POSIX thread affinity flags. I had to let the Windows kernel scheduler manage core assignments.
  • Stack exhaustion: Discovered early that declaring fixed 2D arrays on the stack easily crashes Windows executables (1 MB stack limit), which required switching to dynamic heap allocations via malloc().

Tips for Fellow Students:

  1. Always compile from an active terminal prompt (PowerShell / Bash) rather than clicking the .exe, otherwise the window closes instantly upon termination.
  2. Pay close attention to loop index scoping: failing to make loop variables private will instantly corrupt multi-threaded loops.
  3. Never leave printf calls inside timed parallel sections; terminal I/O completely serializes execution and ruins benchmark numbers.

Task 2.2: OpenMP Matrix Multiplication (omp_mm.c)

For this task, I compiled the provided omp_mm.c on Windows using MinGW-w64 g++ -O3 -fopenmp -Wall -Wextra (_OPENMP = 202111).

Setting OMP_PLACES=cores and OMP_PROC_BIND=close immediately threw warnings from MinGW runtime (libgomp: Affinity not supported on this configuration), so the thread affinity had to rely on the standard Windows OS scheduler.

Stack overflow encounter: When increasing dimensions to 500 as recommended, the executable silently crashed on launch. Since Windows limits the default thread stack to just 1 MB, allocating three 500x500 double arrays locally (~6 MB) blew up the stack before reaching main(). To fix this without messing with linker flags, I rewrote array allocation in heap using malloc() with flat 1D indexing, which worked cleanly.

Scheduling & Scaling observations:

The loop splits work via schedule(static, 10). Out of 500 rows, blocks of 10 rows are handed out sequentially (thread 0 gets rows 0-9, thread 1 gets 10-19, and so on). Because each row has the same computational cost, work distribution is perfectly balanced.

We do get a speedup (peaking at ~3.24x on 6 cores), but scaling falls off noticeably past 2 threads. The entire calculation takes only 17-55 ms, so thread synchronization and fork/join overhead become significant. On top of that, accessing matrix B column-wise triggers lots of cache misses, causing threads to bottleneck on memory access.

Exercise 2.3: Recursive Matrix Multiplication (Cache-Oblivious vs. Naive)

Overview & Algorithm Analysis:

  • Dynamic Allocation: Matrices are allocated dynamically using Allocate2DArray() (contiguous row buffer with row pointer table in 2DArray.h), completely eliminating the stack memory limits encountered in Exercise 2.2.
  • Cache-Oblivious Divide-and-Conquer: matmultr divides matrices into quadrants ($2 \times 2$ block partition) until the submatrix footprint drops below GRAIN = 32768 ($\approx 256\text{ KB}$), where it switches to matmultleaf. This keeps active data within L2/L3 cache lines.
  • Dependency / Data Race Observation: The 8 recursive calls are not mutually independent. Pairs update identical target quadrants of matrix $C$:
    • $C_{00} = A_{00}B_{00} + A_{01}B_{10}$
    • $C_{01} = A_{00}B_{01} + A_{01}B_{11}$
    • $C_{10} = A_{10}B_{00} + A_{11}B_{10}$
    • $C_{11} = A_{10}B_{01} + A_{11}B_{11}$
    To parallelize this safely with OpenMP tasks without data races, execution must be split into two disjoint 4-task phases separated by a #pragma omp taskwait barrier.

Deliverable Observations & Performance Analysis:

  • Small to Medium Matrices ($N = 500, 1000$): The recursive approach clearly outperforms the naive triple loop, delivering an algorithmic speedup of 1.7× and up to 2.7× purely through memory hierarchy efficiency. In matmult1, the column-strided traversal of matrix $B$ ($B[k][j]$) triggers non-stop cache misses once the matrix exceeds cache capacity. By breaking the matrix into sub-blocks smaller than GRAIN = 32768, matmultr ensures that working submatrices fit entirely into L2/L3 cache, maximizing spatial and temporal locality.
  • Large Matrices ($N = 1500$): The speedup degrades to 1.0× (5.131 s vs 4.930 s). At dimensions of $1500 \times 1500$, non-power-of-two matrix subdivisions create odd partitioning sizes and a significantly deeper recursion tree. The recursion call overhead, function frame setup, and index recalculation begin to rival the benefits of cache reuse. Furthermore, at this matrix size, the total memory working set exceeds available last-level cache, making main RAM memory bandwidth the governing bottleneck for both implementations.

Why recursive is faster at 1000x1000: Even without OpenMP, the recursive algorithm is ~2.74x faster solely due to CPU cache behavior. The naive loop jumps through matrix B by columns with big strides (8 KB per jump for N=1000), thrashing L1/L2 caches. The recursive approach cuts matrices down until blocks fit into GRAIN = 32768 (~256 KB), allowing the CPU to reuse cached submatrices in fast memory.

At 1500x1500 the advantage disappears (0.96x). Odd matrix sizes make recursive splitting uneven, recursion call overhead stacks up, and the working set exceeds L3 cache capacity, hitting main memory bandwidth limits either way.

Task 2.3.2: Parallelisation using OpenMP Tasks

To parallelize matmultrec(), we wrap the root call in #pragma omp parallel with #pragma omp single, then spawn subproblems via #pragma omp task.

Because pairs of calls update the same quadrants of matrix C (e.g., both A00*B00 and A01*B10 write to C00), running all 8 tasks at once creates a blatant data race. To avoid this, execution is split into two phases of 4 independent tasks separated by #pragma omp taskwait.

What happens without #pragma omp single?
If we omit #pragma omp single, every active thread executes the root call and starts recursively spawning tasks. With 6 threads, we get 6 identical task trees running simultaneously. They overwrite each other's accumulations in matrix C (causing CheckResults to fail) and choke the CPU with task scheduling overhead.
