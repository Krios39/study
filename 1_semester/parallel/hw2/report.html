Exercise 2.1: OpenMP Tutorial & Learning Blog

Learning Log & How I Proceeded:

I worked through the LLNL OpenMP tutorial by Blaise Barney, focusing on shared-memory multi-threading in C/C++. Since my primary background is in full-stack software development rather than low-level HPC, learning to parallelize code via pragmas instead of managing raw worker threads or event loops was a fresh perspective. I set up my local environment on Windows with MinGW GCC (passing -fopenmp) and stepped through the fundamental concepts: fork-join thread pool models, variable scoping, and work-sharing loops.

Key Concepts Mastered:

  • Fork-Join Execution Model: The master thread spawns a pool of worker threads upon entering #pragma omp parallel and joins back after the region ends.
  • Data Scoping (shared vs private): Misconfiguring variable scope is the fastest route to subtle race conditions. Global or loop control variables must be explicitly marked private(tid, i) or declared locally inside the parallel block, while read-only or accumulator matrices are passed as shared.
  • Loop Scheduling (schedule(static, chunk) vs dynamic): In static scheduling, the compiler partitions iterations in fixed chunks ahead of time, which has virtually zero overhead for balanced workloads like matrix multiplication. dynamic handles unbalanced workloads via a shared work queue at the cost of runtime synchronization.
  • Tasks & Barriers (task, taskwait, single): Discovered how task parallelism allows recursive divide-and-conquer algorithms to run in parallel without requiring rigid loop bounds, provided dependencies are gated by barriers.
  • Essential Runtime APIs: Tested thread identification and timers: omp_get_thread_num(), omp_get_num_threads(), omp_set_num_threads(), and wall-clock benchmarking using omp_get_wtime().

Encountered Roadblocks & Solutions:

  • Unordered console output: When running the Hello World example, printf() outputs from threads appeared interleaved and out of order. At first it looked like a bug, but it is just threads concurrently competing for standard output (stdout).
  • Windows / MinGW Affinity limits: Passing OMP_PLACES=cores produced runtime warnings (libgomp: Affinity not supported) because MinGW's GCC wrapper on Windows does not support POSIX thread affinity flags. I had to let the Windows kernel scheduler manage core assignments.
  • Stack exhaustion: Discovered early that declaring fixed 2D arrays on the stack easily crashes Windows executables (1 MB stack limit), which required switching to dynamic heap allocations via malloc().

Tips for Fellow Students:

  1. Always compile from an active terminal prompt (PowerShell / Bash) rather than clicking the .exe, otherwise the window closes instantly upon termination.
  2. Pay close attention to loop index scoping: failing to make loop variables private will instantly corrupt multi-threaded loops.
  3. Never leave printf calls inside timed parallel sections; terminal I/O completely serializes execution and ruins benchmark numbers.

Task 2.2: OpenMP Matrix Multiplication (omp_mm.c)

Setup & Environment: Compiled on Windows with MinGW-w64 g++ -O3 -fopenmp -Wall -Wextra (_OPENMP = 202111).

When running with OMP_PLACES=cores and OMP_PROC_BIND=close, the MinGW runtime threw warnings (libgomp: Affinity not supported on this configuration), so thread placement was left to the standard Windows OS scheduler.

How threads get scheduled: The loop uses static scheduling: schedule(static, 10). The 500 rows are chopped into chunks of 10 rows and distributed among available threads in round-robin fashion (thread 0 gets rows 0-9, thread 1 gets 10-19, etc.). Since multiplying each row takes roughly the same number of operations, work gets split evenly without any dynamic scheduling overhead.

Speedup analysis: Scaling starts off strong on 2 cores (~1.96x, almost linear), but flattens out on 4 and 6 cores, maxing out at 3.24x. Two things cause this drop in efficiency: first, the total runtime is tiny (under 50 ms), so thread creation and barrier synchronization take up a noticeable portion of the clock cycles. Second, multiplying matrices in simple i-j-k order accesses matrix B down columns, which constantly causes cache misses and makes threads fight over RAM bandwidth.

Exercise 2.3: Recursive Matrix Multiplication (Overview & Memory Handling)

Setup & Memory Allocation:

In this exercise, we switched from stack-based arrays to dynamic allocation using Allocate2DArray() from the provided 2DArray.h. It allocates a continuous buffer for the entire data block plus an array of row pointers, completely avoiding the Windows stack size limits that caused crashes in Exercise 2.2.

How the Recursive Algorithm Works:

Instead of running three nested loops over the entire matrix, matmultr() splits matrices into four sub-blocks (quadrants) and calls itself recursively. Once the submatrix size drops below GRAIN = 32768 elements (~256 KB), it stops dividing and computes the sub-block directly via matmultleaf(). This keeps active working data small enough to fit inside fast CPU cache levels rather than constantly thrashing main memory.

The Data Race Dependency in Recursion:

The mathematical formula for multiplying 2x2 block matrices requires 8 multiplications:

  • C00 = A00*B00 + A01*B10
  • C01 = A00*B01 + A01*B11
  • C10 = A10*B00 + A11*B10
  • C11 = A10*B01 + A11*B11

Looking at the equations, these 8 calls are not mutually independent: each quadrant of matrix C gets updated by two separate multiplications. If we were to run all 8 tasks in parallel without coordination, they would try to write to the same memory addresses at the same time. To make this thread-safe later in OpenMP, the calculations have to be split into two separate 4-task rounds separated by a synchronization barrier.

Why recursive is faster on 1000x1000 (before any OpenMP):
Both algorithms do the exact same arithmetic ($O(N^3)$ operations), so the speedup comes purely from how CPU cache works. In the naive loop, jumping down columns of matrix B means skipping $N \times 8$ bytes in memory on every step. For a 1000x1000 matrix, that completely wrecks spatial locality and CPU cache lines get thrown away before reuse. The recursive method chops matrices into quadrants until sub-blocks drop under GRAIN = 32768 elements (~256 KB). Blocks of that size stay entirely inside L2 cache, allowing the CPU to reuse them without constantly stalling on reads from RAM.

At 1500x1500 the speedup disappears completely (0.96x). The matrix no longer divides neatly by powers of two, recursion tree overhead builds up, and the working data becomes too large even for L3 cache, meaning memory bandwidth becomes the main limiter either way.

Task 2.3.2: Parallelisation using OpenMP Tasks

To parallelize the recursive code, I wrapped the initial call in #pragma omp parallel + #pragma omp single, and then turned the recursive branches into #pragma omp task.

Avoiding data races & variable scoping:
Pairs of recursive calls write into the exact same quadrant of matrix C (for instance, both A00*B00 and A01*B10 accumulate into C00). Spawning all 8 tasks simultaneously creates an obvious race condition. To solve this safely, execution is split into two distinct rounds of 4 independent tasks, separated by #pragma omp taskwait.

Task scoping note: Unlike #pragma omp for (where loop variables must be manually declared private to prevent races), OpenMP treats local stack variables passed into #pragma omp task (like mid_m, mid_n, mid_p) as firstprivate by default. Each task captures its own snapshot of these coordinates automatically, so explicit scoping clauses are not needed here.

What happens if we omit #pragma omp single?
If you remove #pragma omp single, every thread in the team runs the root call independently and builds its own full recursion tree. With 6 threads, you end up spawning 6 times as many tasks. They all try to add values into the same elements of matrix C at the same time, which immediately corrupts the data (making CheckResults fail with numerical mismatches) and slows everything down due to task queue thrashing.
