Task 2.2: OpenMP Matrix Multiplication Scaling & Scheduling

Environment & Setup:

  • Compiler: MinGW-w64 g++ (GCC) with flags -O3 -fopenmp -Wall -Wextra
  • OpenMP Specification: _OPENMP = 202111 (OpenMP 5.2)
  • Thread Affinity: OMP_PLACES=cores and OMP_PROC_BIND=close were set. Note: MinGW GCC runtime on Windows returned libgomp: Affinity not supported on this configuration, falling back to OS-level thread scheduling.
  • Matrix Size & Memory Fix: Evaluated at $NRA = 500$, $NCA = 500$, $NCB = 500$. With fixed stack arrays, three $500 \times 500$ matrices of double require $\approx 6\text{ MB}$, exceeding the default Windows stack size ($1\text{ MB}$) and causing an immediate silent crash / stack overflow. To resolve this, memory allocation was rewritten using dynamic heap memory via malloc()/free() with flat 1D indexing.
  • Timing Methodology: 1 warm-up run + 5 measured runs; reported median time. Matrix initialization, verification, and console printing are excluded from timing via omp_get_wtime().

Deliverable Question 1: How do threads get scheduled?

The code uses #pragma omp for schedule(static, 10). The outer loop of 500 rows is split into chunks of 10 rows and distributed to threads in a round-robin fashion (Thread 0 takes rows 0–9, Thread 1 takes 10–19, etc.). Since each row requires the exact same amount of multiplication steps, all threads get an even amount of work without any extra scheduling overhead.

Deliverable Question 2: Did you gain any (average) speedup?

Yes, increasing the thread count consistently makes the program faster. We get almost ideal scaling on 2 threads (1.96×), reaching 3.24× on 6 threads. However, scaling slows down after 2 threads for two simple reasons:

  • Short Runtime: The whole computation takes only 17–55 milliseconds, so thread creation, synchronization, and barrier overhead start to eat up a noticeable chunk of the runtime.
  • Cache Misses: In the classic $i \to j \to k$ loop order, elements of matrix $B$ are accessed down columns rather than along rows, which causes frequent CPU cache misses and saturates memory bandwidth when several threads run in parallel.

Correctness Verification: Output matrix $C$ was verified using the closed-form summation formula:

$$c_{i,j} = \sum_{k=0}^{NCA-1} (i + k)(k \cdot j) = j \left[ i \sum_{k=0}^{NCA-1} k + \sum_{k=0}^{NCA-1} k^2 \right]$$

All matrix values matched the expected results within a $10^{-3}$ tolerance (Correct: YES on all runs).
