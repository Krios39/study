Exercise 4.1.1: Trapezoidal integration with collectives

Implementation & Validation Strategy:

The manual point-to-point message passing (using comm.Send and comm.Recv) was completely removed. After each process computes its local trapezoidal integral, the results are aggregated using a collective reduction. Furthermore, to ensure mathematical correctness, a sequential reference calculation was added exclusively to Rank 0. The parallel result is compared against this serial reference using numpy.isclose(). If the validation fails (exceeding the floating-point tolerance), the program immediately aborts with a non-zero exit status via sys.exit(1).

The answer (Collective Communication Role):

I used the MPI.Reduce collective combined with the MPI.SUM operator. This collective efficiently gathers the locally computed integral values from all parallel ranks and automatically calculates their sum directly onto the root rank (Rank 0). This effectively replaces the manual point-to-point receive loop with a single, highly optimized internal MPI operation.

Exercise 4.1.2: Parallel repeated matrix-vector multiplication

Implementation & Validation Strategy:

The square matrix $A$ was distributed row-wise across the available processes, while the initial vector $x$ was broadcasted to all ranks. During each iteration $K$, each process computes the dot product of its local rows of $A$ against the full current vector $x$. To ensure mathematical correctness without explicitly forming the matrix power $A^K$, a sequential reference loop was executed exclusively on Rank 0. The aggregated parallel result was then validated against this serial reference using numpy.allclose(), with a strict rule to terminate the program via sys.exit(1) if the values diverged.

The answer (Choice of Collectives):

I distributed the matrix $A$ across processes by rows using MPI.Scatter, while giving every process a full copy of the initial vector $x$ via MPI.Bcast. Inside the iteration loop, after each process computes its local segment of the new vector, I used the MPI.Allgather collective. This collective is structurally necessary here because it gathers the newly computed segments from all ranks and immediately reconstructs the complete, updated vector onto every single process simultaneously, seamlessly satisfying the data dependencies for the next $j+1$ multiplication step.

Exercise 4.2: Row-block implementation

Implementation & Testing Strategy:

The solution distributes the matrix strictly by contiguous row blocks. Before any allocation occurs, the code explicitly validates the assignment preconditions: it checks if $P \le N$ and $N \pmod P == 0$. If these conditions are violated, the root rank logs a clear error message and raises a ValueError to halt execution immediately. The solution was successfully validated against the provided a4_test.py script for $P=1, 2, 4, 8$. To execute the test for 8 processes on my local machine, I utilized the --oversubscribe flag.

Design Note:

Initially, the root rank distributes matrix A using MPI.Scatter so each rank allocates and receives only its contiguous (N//P) x N row block. The initial vector x is shared to all ranks using MPI.Bcast. During each iteration, every rank computes the dot product of its local row block and the current full vector x, yielding a local segment of the new vector. Because the next iteration requires the complete updated vector, these local segments are concatenated and shared globally using the MPI.Allgather collective.

Before an iteration, every rank holds its fixed matrix block and the full current vector x. After the iteration's Allgather, all ranks simultaneously possess the fully updated vector $x_{j+1}$. As required by the contract, the function returns the fully computed vector on Rank 0, and explicitly returns None on all non-root ranks. This design is strictly correct because it satisfies data dependencies for consecutive multiplications without requiring full matrix replication.

Exercise 4.3: Reproducible strong-scaling experiment

1. System Configuration & Parameters

  • Problem Size: $N = 4096$ (Matrix footprint: ~134 MB), Iterations $K = 50$. Justification: cleanly divides by 1, 2, 4, and 8, and provides sufficient workload to minimize MPI timer resolution noise without exceeding memory limits.
  • Execution Environment & Limits: Local WSL Ubuntu instance. The hardware allocation is strictly limited to 4 physical cores. Consequently, testing $P=16$ and $P=32$ was physically impossible, and the $P=8$ run explicitly required the --oversubscribe flag.
  • Software Stack: OpenMPI v4.1.x, mpi4py v3.1.x, NumPy v1.26.x (float64).
  • Thread Controls: OMP_NUM_THREADS=1, OPENBLAS_NUM_THREADS=1, MKL_NUM_THREADS=1 exported to prevent uncontrolled nested parallelism.

4. Scaling Analysis & Limits

The benchmark demonstrates classic memory-bound scaling limits. Moving from $P=1$ to $P=2$ yields a reasonable kernel speedup of 1.64x. However, at $P=4$, the speedup heavily plateaus at 1.95x, dropping parallel efficiency below 50%. This saturation occurs because computing the dot product of a 134 MB matrix heavily taxes the CPU's memory bus bandwidth; adding more processes parallelizes the arithmetic but creates a queue for RAM access. Additionally, the MPI.Allgather operation introduces cumulative communication overhead.

At $P=8$, performance actively degrades (runtime increases). This slowdown is directly caused by the physical limits of the execution environment: forcing 8 MPI ranks to run on a restricted number of physical WSL cores (4) via the --oversubscribe flag introduces severe OS-level context-switching overhead, entirely negating any theoretical parallel gains.

Bonus Exercise 4.4: Row-cyclic distribution & Variable-count (Scatterv)

Implementation Strategy & Proof of Arbitrary N:

The divisibility assumption (N % P == 0) was successfully removed by transitioning from standard collectives to their vector counterparts (MPI.Scatterv and MPI.Allgatherv). By calculating specific counts and displacements arrays, the load is balanced gracefully, assigning (N // P) + 1 rows to the early ranks when a remainder exists. To prove this, I executed a test run with $N=65$ on $P=4$ (where $65 \pmod 4 = 1$), explicitly logging the allocated row counts to verify that Rank 0 handled 17 rows while the rest handled 16.

Performance Comparison vs. Row-Block Layout (N=4096, P=4)

Testing both implementations with identical parameters ($P=4, N=4096, K=50$) reveals that the Row-Cyclic distribution inherently exhibits poorer performance across both metrics for this specific dense problem:

  • Distribution Cost (0.0284s vs 0.0147s): The cyclic distribution cost (End-to-End minus Kernel time) is nearly double that of the block layout. MPI requires contiguous memory buffers for communication. Because a cyclic layout means a rank's rows are scattered throughout the original matrix, Rank 0 must allocate a temporary buffer and physically copy the rows into contiguous chunks per rank before invoking Scatterv. This introduces a heavy memory copying overhead that the row-block layout avoids.
  • Repeated-Multiplication Performance (0.1575s vs 0.1539s): Inside the iteration loop, the local matrix-vector dot product runs at the same BLAS-optimized speed. However, Allgatherv concatenates the results in rank-order, effectively scrambling the vector. To prepare the vector for the next iteration, every rank must execute a manual unpacking loop to interleave gathered_y back into x_full, adding consistent computational overhead to the kernel.

Conclusion: A row-cyclic layout is an excellent strategy for sparse matrices where computational cost per row varies wildly. However, for a dense matrix where every row takes exactly the same time to compute, the cyclic layout introduces strict memory-reordering penalties with zero load-balancing benefits, rendering the contiguous row-block layout superior.
