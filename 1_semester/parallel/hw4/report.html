Exercise 4.1.1: Replace point-to-point communication with collectives

Implementation & Validation Strategy:

The manual point-to-point message passing (using comm.Send and comm.Recv) was completely removed. After each process computes its local trapezoidal integral, the results are aggregated using a collective reduction. Furthermore, to ensure mathematical correctness, a sequential reference calculation was added exclusively to Rank 0. The parallel result is compared against this serial reference using numpy.isclose(). If the validation fails (exceeding the floating-point tolerance), the program immediately aborts with a non-zero exit status via sys.exit(1).

The answer (Collective Communication Role):

I used the MPI.Reduce collective combined with the MPI.SUM operator. This collective efficiently gathers the locally computed integral values from all parallel ranks and automatically calculates their sum directly onto the root rank (Rank 0). This effectively replaces the manual point-to-point receive loop with a single, highly optimized internal MPI operation.

Exercise 4.1.2: Parallel repeated matrix-vector multiplication

Implementation & Validation Strategy:

The square matrix $A$ was distributed row-wise across the available processes, while the initial vector $x$ was broadcasted to all ranks. During each iteration $K$, each process computes the dot product of its local rows of $A$ against the full current vector $x$. To ensure mathematical correctness without explicitly forming the matrix power $A^K$, a sequential reference loop was executed exclusively on Rank 0. The aggregated parallel result was then validated against this serial reference using numpy.allclose(), with a strict rule to terminate the program via sys.exit(1) if the values diverged.

Raw Terminal Output:

user@DESKTOP-AJAG7QD:/mnt/c/учёба/study/1_semester/parallel/hw4$ mpiexec -n 4 python3 task4_1_2.py 1000 10
[Rank 0] Validation passed! Parallel result perfectly matches serial reference for N=1000, K=10.

The answer (Choice of Collectives):

I distributed the matrix $A$ across processes by rows using MPI.Scatter, while giving every process a full copy of the initial vector $x$ via MPI.Bcast. Inside the iteration loop, after each process computes its local segment of the new vector, I used the MPI.Allgather collective. This collective is structurally necessary here because it gathers the newly computed segments from all ranks and immediately reconstructs the complete, updated vector onto every single process simultaneously, seamlessly satisfying the data dependencies for the next $j+1$ multiplication step.

Design Note:

Initially, the root rank distributes matrix A using MPI.Scatter so each rank allocates and receives only its contiguous (N//P) x N row block. The initial vector x is shared to all ranks using MPI.Bcast.

During each iteration, every rank computes the dot product of its local row block and the current full vector x, yielding a local segment of the new vector. Because the next iteration requires the complete updated vector, these local segments are concatenated and shared globally using the MPI.Allgather collective.

Before an iteration, every rank holds its fixed matrix block and the full current vector x. After the iteration's Allgather, all ranks simultaneously possess the fully updated vector $x_{j+1}$. This design is strictly correct because it satisfies data dependencies for consecutive multiplications without requiring full matrix replication or explicitly computing the matrix power $A^K$.

Exercise 4.3: Reproducible strong-scaling experiment

1. System Configuration & Parameters

  • Problem Size: $N = 4096$ (Matrix footprint: ~134 MB), Iterations $K = 50$.
  • Memory & Justification: $N=4096$ was chosen because it cleanly divides by all tested process counts (1, 2, 4, 8) and provides a sufficient computational workload (134 MB easily fits in memory but puts pressure on the L3 cache). $K=50$ ensures the timed region lasts long enough ($\sim 0.1-0.3$ seconds) to minimize MPI timer resolution noise.
  • Execution Environment: Local WSL Ubuntu instance.
  • MPI & Python: OpenMPI via mpi4py, NumPy float64 arrays.
  • Launch Command: mpiexec -n <P> python3 task4_3.py (used --oversubscribe for $P=8$ due to physical core limits).
  • Thread Controls: OMP_NUM_THREADS=1, OPENBLAS_NUM_THREADS=1, MKL_NUM_THREADS=1 exported to prevent nested parallelism.

3. Performance Plots

4. Scaling Analysis & Limits

The benchmark demonstrates classic memory-bound scaling limits. Moving from $P=1$ to $P=2$ yields a reasonable kernel speedup of 1.64x. However, at $P=4$, the speedup heavily plateaus at 1.95x, dropping parallel efficiency below 50%. This saturation occurs because computing the dot product of a 134 MB matrix heavily taxes the CPU's memory bus bandwidth; adding more processes parallelizes the arithmetic but creates a queue for RAM access. Additionally, the MPI.Allgather operation introduces cumulative communication overhead at the end of every iteration.

At $P=8$, performance actively degrades (runtime increases, reducing speedup to 1.56x). This slowdown is directly caused by the hardware limitations of the execution environment: forcing 8 MPI ranks to run on a restricted number of physical WSL cores via the --oversubscribe flag introduces severe OS-level context-switching overhead, entirely negating any theoretical parallel gains. The gap between Kernel and End-to-End time remains small but consistent, representing the fixed network overhead of the initial MPI.Scatter and MPI.Bcast distribution.

Performance Comparison vs. Row-Block Layout

Testing both implementations with identical parameters ($P=4, N=4096, K=50$) reveals that the Row-Cyclic distribution inherently exhibits poorer performance across both metrics for this specific dense problem:

  • Distribution Cost (0.0284s vs 0.0147s): The cyclic distribution cost (End-to-End minus Kernel time) is nearly double that of the block layout. MPI requires contiguous memory buffers for communication. Because a cyclic layout means a rank's rows are scattered throughout the original matrix (A[i::P]), Rank 0 must allocate a temporary buffer and physically copy the rows into contiguous chunks per rank before invoking Scatterv. This introduces a heavy memory copying overhead that the row-block layout entirely avoids.
  • Repeated-Multiplication Performance (0.1575s vs 0.1539s): Inside the iteration loop, the local matrix-vector dot product runs at the same BLAS-optimized speed as the block version. However, Allgatherv concatenates the results in rank-order (Rank 0's results, then Rank 1's, etc.), effectively scrambling the vector. To prepare the vector for the next iteration, every rank must execute a manual unpacking loop to interleave gathered_y back into x_full. This continuous memory restructuring on every single iteration adds overhead to the kernel execution time.

Conclusion: A row-cyclic layout is an excellent strategy for sparse matrices where computational cost per row varies wildly (preventing stragglers). However, for a dense matrix where every row takes exactly the same time to compute, the cyclic layout introduces strict memory-reordering penalties with zero load-balancing benefits, rendering the contiguous row-block layout superior.
