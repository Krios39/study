Exercise 4.1.1: Replace point-to-point communication with collectives

Implementation & Validation Strategy:

The manual point-to-point message passing (using comm.Send and comm.Recv) was completely removed. After each process computes its local trapezoidal integral, the results are aggregated using a collective reduction. Furthermore, to ensure mathematical correctness, a sequential reference calculation was added exclusively to Rank 0. The parallel result is compared against this serial reference using numpy.isclose(). If the validation fails (exceeding the floating-point tolerance), the program immediately aborts with a non-zero exit status via sys.exit(1).

With n = 10000 trapezoids, our estimate of the integral from 0.0 to 1.0 is [0.33333334]

The answer (Collective Communication Role):

I used the MPI.Reduce collective combined with the MPI.SUM operator. This collective efficiently gathers the locally computed integral values from all parallel ranks and automatically calculates their sum directly onto the root rank (Rank 0). This effectively replaces the manual point-to-point receive loop with a single, highly optimized internal MPI operation.

Exercise 4.1.2: Parallel repeated matrix-vector multiplication

Implementation & Validation Strategy:

The square matrix $A$ was distributed row-wise across the available processes, while the initial vector $x$ was broadcasted to all ranks. During each iteration $K$, each process computes the dot product of its local rows of $A$ against the full current vector $x$. To ensure mathematical correctness without explicitly forming the matrix power $A^K$, a sequential reference loop was executed exclusively on Rank 0. The aggregated parallel result was then validated against this serial reference using numpy.allclose(), with a strict rule to terminate the program via sys.exit(1) if the values diverged.

Raw Terminal Output:

user@DESKTOP-AJAG7QD:/mnt/c/учёба/study/1_semester/parallel/hw4$ mpiexec -n 4 python3 task4_1_2.py 1000 10
[Rank 0] Validation passed! Parallel result perfectly matches serial reference for N=1000, K=10.

The answer (Choice of Collectives):

I distributed the matrix $A$ across processes by rows using MPI.Scatter, while giving every process a full copy of the initial vector $x$ via MPI.Bcast. Inside the iteration loop, after each process computes its local segment of the new vector, I used the MPI.Allgather collective. This collective is structurally necessary here because it gathers the newly computed segments from all ranks and immediately reconstructs the complete, updated vector onto every single process simultaneously, seamlessly satisfying the data dependencies for the next $j+1$ multiplication step.

Exercise 4.2: Row-block implementation

Implementation & Testing Strategy:

The solution was rigorously validated against the provided a4_test.py script across multiple valid process counts ($P=1, 2, 4, 8$) that cleanly divide the fixed matrix size $N=64$. Because my local environment has a limited number of physical CPU cores, attempting to spawn more than 4 processes initially triggered an OpenMPI allocation error (prte-rmaps-base:alloc-error). To successfully execute the test for 8 processes, I utilized the --oversubscribe flag, which forces MPI to map multiple virtual processes onto the available physical cores.

Design Note:

Initially, the root rank distributes matrix A using MPI.Scatter so each rank allocates and receives only its contiguous (N//P) x N row block. The initial vector x is shared to all ranks using MPI.Bcast.

During each iteration, every rank computes the dot product of its local row block and the current full vector x, yielding a local segment of the new vector. Because the next iteration requires the complete updated vector, these local segments are concatenated and shared globally using the MPI.Allgather collective.

Before an iteration, every rank holds its fixed matrix block and the full current vector x. After the iteration's Allgather, all ranks simultaneously possess the fully updated vector $x_{j+1}$. This design is strictly correct because it satisfies data dependencies for consecutive multiplications without requiring full matrix replication or explicitly computing the matrix power $A^K$.
