Test environment and benchmark configuration
  • CPU: Intel Core Ultra 7 265U (laptop, hybrid design with performance and efficiency cores). Inside WSL, lscpu reports 1 socket, 7 cores per socket, 2 threads per core, so 7 physical cores are available to MPI.
  • OS: Ubuntu running under WSL 2 on Windows 11. All processes run on one node and communicate through shared memory.
  • MPI: Open MPI v5.0.10 (Debian package), used through mpi4py with the uppercase buffer methods only.
  • NumPy / BLAS: NumPy for Python 3.14 linked against OpenBLAS 0.3.34 (scipy-openblas, DYNAMIC_ARCH). All data is np.float64.
  • Thread settings: OMP_NUM_THREADS=1, OPENBLAS_NUM_THREADS=1, MKL_NUM_THREADS=1, so every MPI process uses exactly one thread and there is no hidden second level of parallelism.
  • Process counts: $P = 1, 2, 4$. $P = 8$ was attempted, but Open MPI refused to start it (prte-rmaps-base:alloc-error) because only 7 physical cores are visible. Running it with --oversubscribe would break the "do not oversubscribe" rule of the assignment, so $P = 8$ and $P = 16$ were not measured.
  • Timing method: every timed region starts and ends with comm.Barrier() and MPI.Wtime(). Each process measures its own time and the maximum over all processes is taken with comm.Reduce(..., op=MPI.MAX). Each configuration is run once as a warm-up (also checked against NumPy, not recorded) and then 10 times; tables report the median, plots also show min..max.
  • Time split: setup = broadcasting $N$ and distributing $A$ and $x$ once (for the column versions this includes transposing $A$ on rank 0); mult = the $K$ multiplications including all communication and the final collection of $y$ on rank 0; total = setup + mult.
  • Benchmark matrix: a random matrix divided by $N$ (fixed seed), so that $A^K x$ stays bounded.
  • Noise: a first benchmark series (5 runs per configuration) showed up to 2.6x differences between identical configurations, so it was discarded. All numbers below come from a second series with 10 runs per configuration and less background load on the laptop.
Exercise 6.1: Repeated matrix-vector multiplication with column-block distribution

Warm-up: what must move

  • Row-block: process $i$ owns $N/P$ complete rows, so it needs the whole $x$ and produces $N/P$ final elements of $y$. The pieces of different processes are different elements of $y$, so they only have to be concatenated: Allgather.
  • Column-block: process $i$ owns $N/P$ complete columns and only the matching segment $x_i$. Because $y = \sum_i A_i x_i$, its local product $z_i = A_i x_i$ has full length $N$ but is only a partial sum of every element of $y$. The contributions overlap and must be added: Allreduce(op=MPI.SUM).
  • The 4x4 example: $z_0 = [3, 11, 19, 27]$ and $z_1 = [7, 15, 23, 31]$ are summed to $y = [10, 26, 42, 58]$. Allreduce gives both processes the complete $y$, but they do not need all of it: process 0 only needs $y[0:2]$ and process 1 only $y[2:4]$ as their next input. That is exactly what Reduce_scatter_block delivers (Bonus 6b).
  • Where $x$ lives: before an iteration process $i$ holds only its segment $x_i$ ($N/P$ elements). After the local product it holds a length-$N$ partial result $z_i$. After Allreduce every process holds the full new vector, keeps its own segment y[i*N/P:(i+1)*N/P] and the cycle repeats.

Implementation (task6_1.py, Ax_columnblock)

  • Distribution, once before the loop: consecutive columns of a C-order NumPy matrix are not contiguous in memory, so a plain Scatter of column blocks is impossible. Rank 0 builds np.ascontiguousarray(A.T): row block $i$ of $A^T$ is exactly column block $i$ of $A$ and it is contiguous, so one Scatter distributes all column blocks. Each process keeps local_AT ($N/P \times N$) and multiplies with the view local_AT.T, which BLAS handles as a transposed matrix-vector product without copying. $x$ is distributed with a second Scatter.
  • Loop: np.dot(local_AT.T, x_local, out=z), then Allreduce(z, y, op=MPI.SUM) and x_local[:] = y[lo:hi].
  • Last iteration: only rank 0 needs the complete answer, so the last Allreduce is replaced by Reduce(..., root=0), which saves one broadcast of $N$ values.
  • $K = 0$: no multiplication and no distribution of $A$; rank 0 returns a copy of $x$.
  • Preconditions: rank 0 checks that $A$ is $N \times N$ and $x$ has length $N$, then broadcasts $N$. All ranks raise ValueError together if $N \bmod P \ne 0$, so no rank is left waiting inside a collective.
  • The row-block function from Exercise 4.2 was moved into the same file with the same signature, so both are tested and timed by identical code.

Correctness tests (a6_test.py)

All four implementations (row-block, column-block, cell-block and the Reduce_scatter_block variant) are tested on the 4x4 example from the assignment and on identity, zero, diagonal and dense random matrices of size 8x8 and 64x64, each with $K = 0, 1, 2, 5, 10$. Only rank 0 receives $A$ and $x$, the other ranks get None. The result on rank 0 is compared with repeated sequential NumPy multiplication using np.testing.assert_allclose(rtol=1e-10, atol=1e-12); bitwise equality is not expected because the summation order differs. The cell-block version is skipped for $P = 2$ because it needs a square number of processes.

The answer (Collective operations):

The row-block algorithm uses Bcast (whole $x$) and Scatter (row blocks) once, and Allgather between iterations, because every process computes different, already final elements of $y$ and everybody needs the whole vector in the next iteration. The column-block algorithm uses two Scatter calls once (column blocks via $A^T$, and segments of $x$), and Allreduce(SUM) between iterations, because every process holds a partial sum of all elements of $y$ and the partial sums have to be added; the last iteration uses Reduce to rank 0. Concatenation versus addition follows directly from what is split: splitting the rows splits the output, splitting the columns splits the inner sum of the product.

4. Discussion

Both methods do about $N^2/P$ multiply-adds per iteration. Why can their runtimes differ?

  • Setup dominates the difference. In the multiplication phase both algorithms are almost equally fast ($P = 4$: 0.173 s row vs 0.182 s column). The total differs by a factor of 2.6 because the column version needs 0.31 to 0.40 s for the distribution against 0.02 to 0.04 s for the row version. The reason is np.ascontiguousarray(A.T) on rank 0: transposing 134 MB reads the matrix with a stride of 32 KB between consecutive elements, which defeats the caches and the hardware prefetcher. The row version scatters the matrix in the order it already has in memory.
  • Different communication volume. Allgather moves $N/P$ elements from every process, while Allreduce combines a full length-$N$ vector from every process and also performs the additions. At $N = 512$, where communication is a visible part of a 20 µs iteration, the column version is about 2x slower per multiplication (0.034 ms vs 0.018 ms); at $N = 2048$ it is still 10 to 30% slower in Experiment C. At $N = 4096$ a 32 KB vector is negligible next to 134 MB of matrix data and the difference disappears in the noise.
  • Different number of collectives. The column version needs one more collective at setup (a second Scatter for $x$) and a Reduce at the end; this is small but counts at small $N$.

Which communication operation does each method use between iterations? Row-block: Allgather (concatenation of final segments). Column-block: Allreduce(SUM) (addition of partial sums), with Reduce in the last iteration.

When does increasing $P$ stop helping?

  • Memory bandwidth. A matrix-vector product performs only 2 floating-point operations per 8-byte matrix element, so its speed is limited by how fast the matrix can be read, not by arithmetic. From the row-block numbers: one multiplication takes 5.95 ms at $P = 1$ (about 22 GB/s) and 3.46 ms at $P = 4$ (about 39 GB/s). Four times more cores give less than twice the memory throughput because all cores share the same memory controller. This is why the multiplication speedup is only 1.72x at $P = 4$ (efficiency 43%).
  • Cache effects confirm it. In Experiment B the same 4 processes read the matrix at about 116 GB/s for $N = 512$ (2 MB) and 69 GB/s for $N = 1024$ (8 MB), where the per-process blocks fit into the caches, but only 37 to 38 GB/s for $N = 2048$ and $4096$, where they do not.
  • Communication that does not shrink. In the column version every process sends and receives a full length-$N$ vector per iteration regardless of $P$, so its share grows as the computation per process shrinks.
  • Hardware. Only 7 physical cores are visible in WSL, and the cores of the Core Ultra 7 265U are not identical. Some ranks can land on slower efficiency cores, and the others then wait for them at every collective (the time of the slowest rank counts). Running more processes than physical cores would only add context switches.

Does the method that is fastest for one $N$ or $P$ remain fastest for all sizes? For the total time the row-block method was fastest in every measured configuration, because its distribution is 7 to 15 times cheaper. Looking only at the multiplication phase, the ranking is not stable: row-block wins clearly at small $N$ (512, 1024), where the smaller Allgather matters, while at $N = 2048$ and $4096$ all variants are within about 5%, which is inside the run-to-run noise. Experiment C shows that a larger $K$ amortises the setup (the column version's setup share falls from 98% at $K = 1$ to 38% at $K = 100$), but because the column version is not faster per iteration either, it never overtakes the row version on this machine.

Exercise 6.3: Two-dimensional (cell-block) matrix distribution

Implementation (task6_3.py, Ax_cellblock, steps 6.3a and 6.3b)

  • Process grid: $P = p \times p$, Create_cart([p, p], reorder=False), so world rank $r$ has grid coordinates $(i, j)$. Two subcommunicators are created: row_comm (processes $(i, 0..p-1)$, rank inside = $j$) and col_comm (processes $(0..p-1, j)$, rank inside = $i$).
  • Distribution, once: rank 0 copies block $A_{ij}$ ($N/p \times N/p$) and segment $x_j$ for every rank into contiguous send buffers and distributes them with two Scatter calls. Process $(i, j)$ needs exactly $x_j$, because $A_{ij}$ only touches the columns of block $j$.
  • One multiplication (6.3a): $z_{ij} = A_{ij} x_j$; the output block $y_i = \sum_j z_{ij}$ is a sum over the process row, computed with row_comm.Reduce. For a 2x2 grid this is literally $y_0 = A_{00} x_0 + A_{01} x_1$ and $y_1 = A_{10} x_0 + A_{11} x_1$.
  • Repeated multiplications (6.3b): in the next iteration process $(i, j)$ needs $x_j^{new} = y_j$, but $y_j$ is produced in process row $j$. The row sum is therefore reduced onto the diagonal process $(i, i)$, which then broadcasts it down its own process column with col_comm.Bcast(root=j): the diagonal process $(j, j)$ owns $y_j$, and every process in column $j$ needs it. Each iteration costs one Reduce and one Bcast, both on messages of only $N/p$ elements.
  • Final result: in the last iteration the row sums go to column 0 instead, and col_comm.Gather in column 0 assembles the complete $y$ on process $(0, 0)$, which is rank 0.
  • Tested together with the other methods for $P = 1$ and $P = 4$ (all cases PASS, see Exercise 6.1).

The answer (When is a 2D distribution useful?):

In a 1D distribution every process has to receive or contribute a vector of length $N$ in each iteration (the whole $x$ for row-block, a whole partial $y$ for column-block), so the communication per process does not shrink with $P$. In a 2D distribution every message has only $N/\sqrt{P}$ elements and involves only the $\sqrt{P}$ processes of one row or column. With thousands of processes on a real network this difference is decisive, and it is why large-scale libraries such as ScaLAPACK use 2D block(-cyclic) layouts; for matrix-matrix operations a 2D layout also reduces how much data each process has to fetch. For a dense matrix-vector product on a single node with $P = 4$ none of this matters: the work is bound by memory bandwidth, the vector is tiny compared with the matrix, and the extra collective per iteration plus the more complex block packing make 2D slightly slower. A 2D layout should therefore not be assumed to be faster automatically.

The answer:

  • Small messages (1 and 100 elements): Allreduce is 1.2 to 2.4x faster. The time is pure latency, and Reduce + Bcast means two collectives, i.e. two synchronisations and roughly twice as many communication steps (about $2\log_2 P$ instead of $\log_2 P$ with recursive doubling).
  • Medium messages (10 000 elements): at $P = 2$ the two are equal within noise (the minimum values are 14.1 and 14.5 µs; the median even slightly favours Reduce + Bcast). At $P = 4$ Allreduce is 1.7x faster.
  • Large messages (1 000 000 elements = 8 MB): Allreduce is 1.3x faster at $P = 2$ and 2x faster at $P = 4$. For large data the MPI library can use bandwidth-optimal algorithms (for example reduce-scatter followed by allgather, or a ring), where every process sends and receives only about $2n(P-1)/P$ elements and the additions are spread over all processes. With Reduce + Bcast all data flows through the root, which has to receive, add and then send the whole vector again, so the root becomes the bottleneck and the gap grows with $P$.
  • Why the result depends on the library and hardware: MPI libraries choose different algorithms per collective, message size and process count (Open MPI switches algorithms at internal size thresholds; MPICH or Intel MPI use other rules). Here all processes are on one node and communicate through shared memory; on a cluster with a network the latency/bandwidth ratio and the topology are different, so the crossover points would move. In these measurements Allreduce was never clearly slower, so it is the right default.
Bonus 6b: Communication optimisation with Reduce_scatter_block

Implementation (task6_bonus_b.py, Ax_columnblock_rsb): the distribution is the same as in the column-block version. In each iteration Allreduce plus "take my segment" is replaced by a single Reduce_scatter_block(z, x_local, op=MPI.SUM): the length-$N$ partial results are summed and each process receives only the $N/P$ elements it needs as its next input. No process stores the full vector during the loop; at the end Gather assembles $y$ on rank 0. It passed the same tests as the other methods for $P = 1, 2, 4$.

Comparison: where communication is a noticeable part of an iteration ($N = 512$) the Reduce_scatter_block version is 1.7x faster than Allreduce and almost reaches the row-block version (0.0010 s vs 0.0009 s): each process receives $N/P$ instead of $N$ summed values, and the broadcast part of Allreduce is skipped. From $N = 1024$ upward an iteration is dominated by reading the matrix and both variants are equal within noise; in the strong-scaling series at $P = 4$ the variant was even slightly slower (0.214 s vs 0.182 s), which is inside the spread of the runs.

When avoiding replicated vectors helps: when the vector is large relative to the local computation, i.e. with many processes (the local work $N^2/P$ shrinks while a replicated vector stays at $N$), on networks where bandwidth is expensive, and when memory is tight, since every process stores $N/P$ instead of $N$ values. On a single node with 4 processes and a memory-bound kernel the benefit only shows for small matrices.

Limitations
  • Only $P = 1, 2, 4$ could be measured without oversubscribing the 7 physical cores visible in WSL, so the scaling curves are short.
  • All runs are on one laptop: communication goes through shared memory, not a network, so communication costs are much lower than on a cluster and the conclusions about collectives may not carry over.
  • The laptop CPU changes its clock with temperature and power state and mixes fast and slow cores. Even with 10 runs, differences below about 10% should not be interpreted.
  • WSL adds a virtualisation layer between MPI and the hardware.
  • Python call overhead is included in every iteration; for small $N$ it is a noticeable part of the measured time.
